# Portal 客户资料与 A/B 线进件完整性设计

## 1. 背景

当前客户 Portal 的“我的资料”仅支持姓名、登录手机号和身份证号。数据库已经保留部分客户身份与扩展资料字段，但 Portal 没有完整录入入口，B 线销售人工进件页面还允许在创建进件时再次填写姓名、手机号和身份证号。

这造成三个问题：

1. A 线客户提交申请时，进件审核需要的居住地址和紧急联系人没有结构化数据；
2. B 线销售可能在进件页面重复录入或覆盖客户资料，客户档案和进件事实缺少唯一数据来源；
3. 审核页面直接读取客户当前资料，客户后续修改可能改变历史进件的审核依据。

本设计在不引入 OCR、征信或法大大实名前移的前提下，补齐客户自助资料录入、B 线刷新读取和进件提交快照。

## 2. 目标

1. 客户统一在 Portal 维护进件所需结构化资料；
2. A 线创建自助申请前强制检查客户资料完整性；
3. B 线允许先创建草稿，销售刷新客户最新资料后再提交；
4. 进件提交时冻结客户资料快照，保证历史审核依据不随客户档案变化；
5. 驾驶资格继续由审核人员根据驾驶证材料人工核验；
6. 尽量减少客户录入内容，避免收集当前不参与审核决策的敏感信息。

## 3. 非目标

本轮不包含：

- 身份证或驾驶证 OCR；
- 法大大实名认证节点调整；
- 公安、手机号实名、芝麻信用分、微信支付分或大数据征信接入；
- 职业、工作单位、月收入、社保月数、公积金月数的 Portal 或进件页面展示；
- 销售或审核人员代客户编辑结构化身份资料；
- 新增“客户复核”状态或额外 Journey 节点；
- 修改押金、最终方案、合同签署和现有材料审核业务规则。

数据库中已有但本轮不使用的职业、单位、收入、社保和公积金字段继续保留，不删除、不迁移历史值。

## 4. 核心原则

采用“客户档案是提交前唯一数据源，Application 快照是提交后审核依据”的方案。

- 提交前：Portal 和 B 线草稿读取客户当前档案；
- 提交时：服务端重新校验客户当前档案，并在同一事务内生成进件资料快照；
- 提交后：审核页面默认读取该次进件的冻结快照；
- 待补件后重提：用客户最新档案生成下一版快照，并通过审计日志保留前后差异。

不采用以下方案：

- 审核始终读取实时客户档案，因为后续修改会破坏历史审核依据；
- 每次进件单独填写一套客户资料，因为会重复录入并产生多个事实来源。

## 5. 进件资料字段

### 5.1 进件前必填

| 数据域 | 字段 | 规则 |
| --- | --- | --- |
| 客户 | 姓名 | 必填；不得为 Portal 自动生成的占位姓名 |
| 客户 | 登录手机号 | 必填；大陆 11 位手机号；必须与短信验证登录手机号一致 |
| 身份 | 身份证号 | 必填；沿用现有大陆身份证格式校验 |
| 居住地址 | 省 | 必填 |
| 居住地址 | 市 | 必填 |
| 居住地址 | 区县 | 必填 |
| 居住地址 | 详细地址 | 必填；去除首尾空白后不得为空 |
| 紧急联系人 | 姓名 | 必填 |
| 紧急联系人 | 手机号 | 必填；大陆 11 位手机号；不得与客户登录手机号相同 |

### 5.2 不采集的结构化驾驶证字段

- 驾驶证号默认与身份证号一致，本轮不要求客户重复填写；
- 驾驶证有效期不要求客户填写；
- 现有 `driverLicenseNo`、`licenseValidUntil` 数据库字段保留，以兼容历史数据和未来能力，但不纳入本轮 Portal 或 A/B 线进件完整性判断。

### 5.3 驾驶资格人工审核

- A 线客户继续上传驾驶证正反面材料；
- B 线由销售或运营上传客户提供的驾驶证材料；
- 审核人员根据材料核对持证人与客户身份、准驾车型、有效期及证件状态；
- 审核结论继续写入现有材料审核状态和审核备注；
- Admin 客户资料板块不再把空白驾驶证号、有效期显示为待填写字段，而是提示“驾驶资格以驾驶证材料人工审核结果为准”。

## 6. 结构化居住地址

`CustomerProfile` 增加以下字段：

- `residenceProvince`；
- `residenceCity`；
- `residenceDistrict`；
- `residenceDetail`。

现有 `residenceAddress` 继续保留，保存资料时由服务端按照“省 + 市 + 区县 + 详细地址”生成完整地址，以兼容旧页面、旧接口和报表。

Portal 使用省、市、区县三级联选择器和一个详细地址输入框。行政区数据随 Web 应用版本化发布，不依赖运行时第三方地址接口。服务端至少校验四个地址字段均非空，并统一生成完整地址；客户端选择器负责限制省、市、区县组合。

历史客户若只有 `residenceAddress` 而没有结构化字段，继续显示原完整地址，但在新进件提交前需要客户重新选择省、市、区县并填写详细地址，避免自动拆分产生错误。

## 7. A 线自助进件

### 7.1 Portal“我的资料”

扩展现有 `/portal/profile` 读写能力，支持本设计中的进件必填字段。

- 登录手机号只读，不允许在资料页修改为其他号码；
- 已保存身份证号继续只显示掩码，客户修改时必须重新输入完整号码；
- 保存资料使用单一数据库事务，任一字段校验失败时不进行部分写入；
- 保存成功后重新返回服务端计算的完整性状态。

### 7.2 商品申请预检

客户从商品详情提交申请时：

1. 前端调用预检接口；
2. 资料缺失时列出缺失项，并携带返回地址跳转“我的资料”；
3. 客户保存后返回原商品和套餐页面；
4. 创建申请接口再次执行相同服务端规则，前端预检不能替代最终校验。

### 7.3 权威提交

A 线创建申请时，服务端在创建 Application 和软锁车辆的业务事务内重新读取客户档案、执行完整性校验并生成 V1 客户资料快照。校验失败时不创建 Application，也不改变车辆状态。

## 8. B 线销售人工进件

### 8.1 创建草稿

- 新建销售人工进件只选择客户并填写现有进件意向字段；
- 移除创建进件页面中的客户姓名、手机号、身份证号编辑项；
- Admin 创建进件接口不再通过 `customerIdentity` 覆盖客户档案；
- 客户资料尚未完整时仍允许保存 `DRAFT`，以便销售先建立跟进记录。

### 8.2 刷新客户资料

草稿和 `NEED_MORE_INFO` 进件详情显示客户当前档案、最后更新时间、资料完整性和缺失字段。

“刷新客户资料”按钮重新请求进件详情并读取客户当前档案：

- 不复制数据；
- 不写数据库；
- 不生成业务状态；
- 不修改已有进件快照；
- 失败时仅提示加载失败，不改变进件状态。

### 8.3 提交

B 线提交接口在事务内重新读取客户当前档案：

- 资料不完整时返回稳定错误码和缺失字段列表，Application 保持原状态；
- 资料完整时生成 V1 快照，并将 Application 提交；
- `NEED_MORE_INFO` 状态重新提交时生成下一版快照。

销售和审核人员不能在进件详情中直接编辑客户结构化资料。客户必须使用进件绑定手机号登录 Portal 完成修改。

## 9. 资料完整性服务

扩展现有客户身份完整性逻辑，形成 Portal、A 线创建和 B 线提交共用的领域规则。

返回结果包含：

- `complete`；
- 稳定错误码；
- 缺失或无效字段列表；
- 面向前端的字段标签和原因。

建议的错误码：

- `CUSTOMER_APPLICATION_PROFILE_INCOMPLETE`；
- `CUSTOMER_APPLICATION_PROFILE_INVALID`；
- 继续使用现有 `CUSTOMER_IDENTITY_PROFILE_MOBILE_MISMATCH` 表示登录手机号不一致。

字段原因沿用或扩展为 `MISSING`、`INVALID`、`PLACEHOLDER`。

## 10. Application 客户资料快照

`Application` 增加可空 JSON 字段 `customerProfileSnapshot`。快照结构至少包含：

```text
snapshotVersion
capturedAt
source = CUSTOMER_PORTAL_PROFILE
customerId
name
mobile
idCardNo
residenceProvince
residenceCity
residenceDistrict
residenceDetail
residenceAddress
emergencyContactName
emergencyContactMobile
```

规则：

- V1 在 A 线创建或 B 线首次提交时生成；
- `NEED_MORE_INFO` 重提时版本递增并覆盖 Application 上的当前审核快照；
- 审计日志保存重提前后的快照差异；
- 客户提交后修改个人资料不会自动更新进件快照；
- 不把职业、单位、收入、社保、公积金或结构化驾驶证字段写入本轮快照。

快照包含进件审核所需敏感信息，只能通过既有 Portal 本人范围或 Admin 进件权限读取，不增加公开接口。

## 11. Admin 审核展示

- `DRAFT`、`NEED_MORE_INFO`：显示“客户当前资料”；
- `SUBMITTED` 及后续状态：显示“Vn 进件提交快照”和生成时间；
- 已提交进件默认不混用客户当前档案；
- 审核人员可查看资料和证件材料、填写审核结果及备注，但不能编辑客户结构化资料；
- 历史进件的 `customerProfileSnapshot` 为空时，显示“历史记录，当前展示客户档案”，不得伪装成提交时快照；
- 不自动回填历史进件快照。

## 12. 权限、审计与隐私

- Portal 客户只能读写自己的客户档案；
- 登录手机号继续通过 CustomerAccount 与已验证手机号绑定；
- Admin 沿用现有客户和进件访问范围，非全局权限用户只能访问其负责客户或进件；
- Portal 保存资料、A 线创建、B 线提交和待补件重提均写入现有审计日志；
- 审计元数据记录操作者、来源、快照版本和时间；
- 本轮不开放职业、收入等未参与审核决策的敏感字段，遵守数据最小化原则。

## 13. 兼容与迁移

数据库迁移只做增量变更：

- `customer_profile` 增加四个可空结构化地址字段；
- `application` 增加一个可空客户资料快照字段；
- 不删除现有字段；
- 不回填无法可靠拆分的历史完整地址；
- 不修改状态枚举。

历史客户和历史进件继续可读。API 与页面对缺失新字段保持空值兼容，但新 A 线申请和 B 线提交必须满足新完整性规则。

Admin 创建进件不再接受并应用客户身份覆盖值。Web 与 API 必须一对一部署，避免旧 Admin 页面向新 API 发送已废弃的进件身份编辑字段。

## 14. 异常处理

- Portal 保存校验失败：保留前端输入，服务端不部分写入；
- A 线创建校验失败：不创建进件、不软锁车辆；
- B 线提交校验失败：保持草稿或待补件状态，并返回缺失项；
- B 线刷新失败：不写数据、不改变进件状态；
- 并发修改：提交事务中的服务端读取和快照是最终事实，页面先前显示仅供提示；
- 历史无快照：明确降级展示客户当前档案；
- 合同接口继续保留客户身份资料存在性的兜底校验，但本轮不新增合同前联系人补录节点，因为紧急联系人已在进件前必填。

## 15. 测试与验收

### 15.1 领域和 API

1. 完整资料通过统一完整性校验；
2. 任一必填字段缺失或格式无效时返回对应字段；
3. 紧急联系人手机号与客户手机号相同时校验失败；
4. Portal 更新在同一事务内写入身份、结构化地址、完整地址和紧急联系人；
5. A 线预检和创建使用相同规则；
6. A 线创建失败时不创建 Application、不改变车辆状态；
7. B 线可创建资料不完整的草稿，但提交失败；
8. 客户补齐后 B 线提交成功并生成 V1 快照；
9. 待补件重提生成下一版快照并写审计差异；
10. 客户后续修改不改变历史快照；
11. Admin 创建进件不能覆盖客户身份资料；
12. 驾驶证结构化字段不参与完整性规则，驾驶证材料仍按现有规则审核。

### 15.2 Web 人工验收

1. Portal 可通过省市区级联和详细地址保存、回显居住地址；
2. Portal 可保存、回显紧急联系人；
3. A 线缺资料时跳转“我的资料”，补齐后返回原商品页面；
4. B 线可先建草稿，客户补齐后点击刷新即可显示最新资料；
5. B 线资料不完整时提交按钮被阻止，并明确显示缺失项；
6. 已提交进件显示快照版本和时间；
7. 客户提交后修改资料，已提交进件仍显示原快照；
8. 驾驶资格区域提示通过驾驶证材料人工审核，不展示空白驾驶证号和有效期。

### 15.3 质量门禁

- Prisma migration status；
- Prisma validate 和 generate；
- API 相关单元、集成测试及 TypeScript 检查；
- Web 相关测试、TypeScript 检查及 lint；
- 迁移后的历史客户、历史进件兼容性检查。

## 16. 交付拆分

本轮保持两个独立交付：

1. 先实施已批准的 Golden Path 通知聚合 UUID 修复，恢复当前 Golden Path 验收；
2. 再实施本设计的客户资料和 A/B 线进件补全，使用独立迁移、分支、PR 和人工验收。

两项工作不合并为同一业务 PR，避免小范围 Journey 阻塞修复与客户资料流程改造相互扩大回归面。
