## 2. Existing Code Capability Review

### 2.1 Provider Selection

`ESignModule` selects the provider by `ESIGN_PROVIDER`.

| Setting | Behavior |
| --- | --- |
| `ESIGN_PROVIDER=mock` or missing | Uses `MockESignProvider` |
| `ESIGN_PROVIDER=fadada` | Uses `FadadaESignProvider` with `FadadaApiClient`, HTTP client, PDF artifact service, and Prisma lookup |
| unknown provider | Throws `ESIGN_PROVIDER_UNSUPPORTED` |

Conclusion: Fadada provider selection is wired.

### 2.2 Create Sign Task

Admin endpoint:

```text
POST /api/contracts/:id/esign-tasks
```

Current Fadada flow:

1. `ESignService.createTaskForContract` creates `ContractESignTask` and customer signer locally.
2. `FadadaESignProvider.createSignTask` loads the contract PDF artifact.
3. It uses local task number as Fadada `contract_id`.
4. It calls `uploaddocs.api`.
5. It builds `extsign_validation.api` GET URL and returns it as `signUrl`.
6. `ESignService` stores:
   - `providerEnvelopeId` = Fadada `contract_id`;
   - `providerTaskId` = Fadada `transaction_id`;
   - task `signUrl`;
   - signer `providerSignerId` = Fadada `transaction_id`;
   - signer `signUrl`.

Important blocker for B5-B:

```text
The current formal business flow passes local Customer.id as Fadada customer_id.
Fadada requires provider customer_id, such as the verified FADADA_TEST_CUSTOMER_ID.
```

Before full signing execution, either a provider customer-id mapping must exist, or a one-off controlled B5-B fixture/override must explicitly bind the local signer to the verified provider customer id without committing PII or secrets.

### 2.3 Sign URL Storage

The current Fadada client no longer prefetches the page interface. It builds the complete signed `extsign_validation.api` GET URL and returns it as `signUrl`.

Conclusion: sign URL semantics are correct for B5.

### 2.4 Callback Mapping And Advancement

Callback endpoint:

```text
POST /api/esign/callback/fadada
```

Lookup order:

1. `transaction_id` -> `ContractESignSigner.providerSignerId`
2. `transaction_id` -> `ContractESignTask.providerTaskId`
3. `contract_id` -> `ContractESignTask.providerEnvelopeId`
4. `contract_id` -> `ContractESignTask.taskNo`

For verified `result_code=3000`, the callback flow:

- marks customer signer `SIGNED`;
- marks task `COMPLETED`;
- marks contract `SIGNED`;
- sets `Contract.signedAt` if empty;
- moves the matching order from `PENDING_SIGN` to `PENDING_PAYMENT`;
- writes callback log and notification.

For `3001` and `3003`, it records failure/rejection without advancing the order.

Conclusion: callback code is ready, but it will only work if B5 creates the task in the same database that receives the Fadada callback.

### 2.5 Signed PDF Archive

Admin archive endpoint:

```text
POST /api/esign-tasks/:id/archive-signed-artifacts
```

Admin preview endpoint:

```text
GET /api/esign-tasks/:id/signed-contract/preview
```

Portal preview endpoint:

```text
GET /api/portal/contracts/:id/signed-document/preview
```

Archive uses `providerEnvelopeId` as Fadada `contract_id`, downloads a signed PDF, stores it in private storage, updates `signedDocumentObjectKey`, and leaves `evidenceObjectKey` unchanged because independent evidence report download remains TODO.

Conclusion: archive path is ready for a controlled post-callback test, but it should be triggered only after the task is completed by a verified callback.

### 2.6 PDF Artifact Requirement

`ContractPdfArtifactService` uses a real `Contract.fileId` or `ContractVersion.fileId` PDF when `FADADA_ENABLED=true`.

The deterministic test fixture is disabled when `FADADA_ENABLED=true`.

Conclusion: B5-B needs a non-sensitive test PDF stored as the contract artifact or contract-version artifact before calling the formal create-sign-task flow.

### 2.7 Schema Impact

Existing fields are sufficient for B5-A planning:

- `ContractESignTask.providerTaskId`
- `ContractESignTask.providerEnvelopeId`
- `ContractESignTask.signUrl`
- `ContractESignTask.signedDocumentObjectKey`
- `ContractESignTask.evidenceObjectKey`
- `ContractESignSigner.providerSignerId`
- `ContractESignSigner.signUrl`
- `ContractESignCallbackLog.payload`

No schema change or migration is needed for B5-A.

For production readiness after B5, a durable provider customer-id mapping is still recommended rather than overloading local UUID fields.

## 3. Recommended Test Data Plan

Do not reuse the R5 standalone smoke sign URL for complete signing.

Recommended B5-B data shape:

| Data item | Requirement |
| --- | --- |
| Environment | Callback URL and business database must match |
| Test customer | Controlled local customer mapped to verified Fadada provider customer id |
| Test signer | Current verified Fadada test signer; record only masked id |
| Test vehicle/order | Controlled test order, not a live customer transaction |
| Contract | Clearly marked test contract / non-formal business contract |
| PDF artifact | Real PDF stored on `Contract.fileId` or `ContractVersion.fileId`; no PII, VIN, plate, ID number, phone, or formal legal terms |
| E-sign task | Created through formal API after provider customer id mapping is resolved |
| Provider IDs | Local task must store Fadada `contract_id` and `transaction_id` |
| Return URL | Portal contract detail/list page, public HTTPS |
| Notify URL | Public HTTPS API callback endpoint pointing at the same DB as the task |

Two acceptable ways to reach B5-B:

### Path A: Preferred Formal Flow

1. Add or configure a safe provider customer-id mapping for the controlled test customer.
2. Use the back-office `POST /api/contracts/:id/esign-tasks` flow.
3. Let the formal provider create the upload and sign URL.
4. Open that formal sign URL only after B5-B approval.

This best exercises production code.

### Path B: Controlled Fixture Flow

Use only if Path A is blocked and explicitly approved.

1. Create a controlled local test fixture in the callback target database.
2. Insert or update only the e-sign test task/signer rows with provider `contract_id`, `transaction_id`, and sign URL from a controlled provider request.
3. Do not touch non-test contracts/orders.

This is useful for callback/archival validation, but it is less representative than Path A.


If using this callback, the test contract/task/order must exist in the production API database and be clearly marked as test data.

If using staging, configure a staging HTTPS callback and return URL first, then create the task in the staging database. Do not mix a local/staging task with the production callback URL.

## 5. B5-B Runbook Draft

This runbook is not approved for execution yet.

### Step 1: Preflight

Confirm:

- `ESIGN_PROVIDER=fadada` in the target API environment.
- Fadada base URL is the approved production host.
- Fadada app id/secret are configured in the target API environment.
- Fadada test signer provider `customer_id` is ready and masked in records.
- Provider customer-id mapping or controlled fixture override is ready.
- `FADADA_SIGN_NOTIFY_URL` matches the target callback endpoint.
- `FADADA_SIGN_RETURN_URL` matches the target Portal.
- API route `POST /api/esign/callback/fadada` is reachable over HTTPS.
- Test PDF artifact exists, is PDF, is <= 20 MB, and contains no sensitive or formal contract content.
- Test contract/order are in safe statuses:
  - contract `GENERATED` or `SIGNING`;
  - order `PENDING_SIGN` if order advancement is part of the approved test.

### Step 2: Create Sign Task

Preferred action:

```text
POST /api/contracts/:id/esign-tasks
```

Verify without opening the sign URL:

- task provider is `FADADA`;
- task status is `WAITING_CUSTOMER`;
- `providerEnvelopeId` present;
- `providerTaskId` present;
- signer `providerSignerId` present;
- task/signer `signUrl` present and is an `extsign_validation.api` GET URL;
- local contract status is `SIGNING`.

If provider customer-id mapping is not resolved, stop before this step.

### Step 3: Manual Signing

Only after approval:

- controlled tester opens the sign URL;
- tester verifies the contract title/content is the non-sensitive test contract;
- tester signs only if approval matrix allows completion;
- tester does not sign if the page shows the wrong signer, wrong contract, unexpected fee/risk, or a non-test document.

### Step 4: Callback

After signing:

- confirm Fadada POSTed to `/api/esign/callback/fadada`;
- confirm `ContractESignCallbackLog` is created;
- confirm callback payload is verified;
- confirm `transaction_id` mapped to signer/task;
- confirm task is `COMPLETED`;
- confirm signer is `SIGNED`;
- confirm contract is `SIGNED`;
- confirm order moved from `PENDING_SIGN` to `PENDING_PAYMENT` only if approved;
- send or replay one duplicate callback only if explicitly approved for idempotency check.

### Step 5: Archive

Only after a completed task:

```text
POST /api/esign-tasks/:id/archive-signed-artifacts
```

Verify:

- `signedDocumentObjectKey` present;
- `evidenceObjectKey` remains unchanged/TODO;
- admin preview streams PDF;
- Portal preview streams PDF for the owning customer;
- no object key, provider download URL, or public OSS URL is exposed.

### Step 6: Post-Check

Compare before/after:

- `Contract.status`
- `Contract.signedAt`
- `ContractESignTask.taskStatus`
- `ContractESignSigner.signerStatus`
- `SubscriptionOrder.orderStatus`
- `PaymentOrder` count/status
- `PaymentRecord` count
- `PaymentWriteOff` count
- receivable bill amount/status

Expected:

- e-sign callback may advance contract and order only if approved;
- archive does not modify contract/order/payment/billing/write-off/ROE/BaaS/depreciation.

## 6. Stop Conditions

Stop immediately if any condition occurs:

1. Sign page shows a non-test contract.
2. Sign page shows the wrong signer.
3. Sign page asks for unexpected identity or payment action.
4. Provider returns digest, permission, whitelist, customer, contract, or file errors.
5. Callback cannot map to a local task.
6. Callback is unverified.
7. Contract/order state does not match the approved transition.
8. Archive downloads a non-PDF or oversized PDF.
9. Any PII, secret, sign URL, provider URL, or object key appears in logs/docs/UI where it should not.
10. Any non-test customer/order/contract is touched.

## 7. Rollback And Mitigation

Provider-side records should not be deleted or hidden as a rollback strategy.

If a test is partially completed:

- keep provider record as audit evidence;
- mark local records as test data in operational notes;
- do not directly edit production DB rows unless a separate approved remediation plan exists;
- if local state advanced unexpectedly, document the callback payload and local state transition before any correction;
- if payment/billing was affected, stop and create a separate incident/remediation plan.
