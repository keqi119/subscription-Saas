# 订阅平台三阶段能力实施路线图

日期：2026-07-30

状态：已批准的设计基线

关联功能设计：[六个月订阅业务自动化设计](./2026-07-29-six-month-subscription-automation-design.zh-CN.md)

## 背景与目标

系统尚未进入实质生产阶段。实施目标不是一次性建设完整运营及财务平台，而是在控制线下作业迁移成本的前提下，分阶段增强三个业务层面：

1. 业务板块能够以订阅合同为中心自动完成正常履约；
2. 运营中台能够管理车辆全生命周期、资本债务、收益权及对外付款；
3. 财务后台能够获得可追溯的经营财务事实、统计和预测，为后续财务一体化提供可靠源数据。

路线图按能力闭环而不是技术层或部门拆分。每个阶段都必须形成独立业务价值，并为下一阶段提供稳定事实，不能只交付不可运营的技术底座。

## 总体分期

| 阶段 | 定位 | 主要使用者 | 核心结果 |
| --- | --- | --- | --- |
| 阶段0 | 新库及车型主数据初始化 | 研发、平台管理 | 全新数据库、车型枚举及旧兼容字段退役 |
| 阶段1 | 订阅业务闭环与运营事实底座 | 业务、运营、资产运营 | 正常合同自动履约，合同收支、车辆状态及直接成本完整 |
| 阶段2 | 资产资本、债务、收益权与对外资金闭环 | 运营、资产运营、财务 | 线下融资、结算及每日付款表进入系统，资本和收益权联动 |
| 阶段3 | 经营财务分析与财务一体化准备 | 管理层、运营财务、财务 | 全局经营指标、资金预测、资产分析及可勾稽会计源数据 |

阶段按验收门槛推进，不以固定日历日期自动切换。前一阶段核心事实不可信时，不启用依赖这些事实的后续指标或自动化。

## 阶段0：新库及车型主数据初始化

阶段0是阶段1A的强制前置门槛，详细规则见[车型主数据干净初始化设计](./2026-07-30-vehicle-model-clean-initialization-design.zh-CN.md)。

阶段0包括：

- 备份并只读隔离当前测试数据库；
- 创建独立的新开发数据库；
- 将GitHub PR #223基于最新主干重新校验并合入；
- 删除Prisma及PostgreSQL `VehicleModel`枚举；
- 另用增量迁移删除`vehicleModel`、`legacyVehicleModel`及旧快照兼容字段；
- 车辆、产品和价格规则统一使用`modelDefinitionId`；
- Quote和Order使用`modelDefinitionIdSnapshot`、`modelCodeSnapshot`及`modelDisplayNameSnapshot`；
- 更新种子、API、Portal、CSV、报表和质量守卫；
- 从零验证完整迁移链、最终种子及车型相关主路径。

阶段0不修改历史迁移，不迁移当前测试业务数据，也不在枚举清理中实现车型包多车型集合。

## 阶段1：订阅业务闭环与运营事实底座

阶段1以订阅合同为业务主线。除终审方案、车辆最终分配、交付证据验收等关键人工审核，以及逾期催收、合同变更和异状处理外，正常流程应能够自动运行。

### 阶段1A：新合同进入运营

覆盖：

- A/B 线申请及材料归集；
- 确定性业务校验和终审方案确认；
- 车辆最终分配；
- 报价、订单、Stage 1 签约及已签文件归档；
- 首期应收、客户付款、支付回调及应收核销；
- 交付工单、Stage 2 签约、交付证据验收；
- 订单、车辆和 Lease 的权威激活；
- 流程通知、异常重试和人工接管。

验收结果是新订单可以稳定从申请进入有效履约状态，合同、签约、收款和交付事实一致。

### 阶段1B：合同持续履约

覆盖：

- 周期账单、客户主动支付及授权代扣；
- 付款通知、失败重试、逾期标记和人工催收任务；
- 车型包、包内换车、运营保障换车及包外差价；
- 提前结束、协议延长和补充协议；
- 里程包、补能包、换车权益和客户积分；
- 里程照片及补能合作商报表的人工抄表；
- 退车、合同结算、退款建议和人工退款结果登记。

验收结果是合同存续期间不依赖线下主表推动账单、权益、变更和结束。

### 阶段1C：车辆资产运营闭环

覆盖：

- 采购入库、待租准备、用车中事务、退车整备和资产处置工单；
- 车辆运营限制及状态影响 Helper；
- 维修、事故、救援、保险、调拨、停运和保障换车；
- 实际成本确认、最终承担方、待追回敞口和实际追回；
- 只追加的车辆成本台账；
- 车辆利用率、停运原因、应收账款、合同回款、单车确认成本及待追回报表。

阶段1必须提前建立以下共用事实，但不启用阶段2的完整资金能力：

- 车辆、订单、订阅合同和客户的期间关系；
- `AssetOwner`、车辆归属期间和关键业务快照；
- 成本、收入、付款和追回的稳定来源键；
- 发生日期、归属账期、确认时间和不可变冲正关系；
- 面向未来资本事件和统一付款来源的扩展边界。

资产运营工单和不可变成本台账属于阶段1。融资偿付计划、租金收入分配和统一对外付款底座不属于阶段1。

### 阶段1指标与退出门槛

阶段1核心指标为：

- 车辆利用率、出租天数、可运营天数及停运原因；
- 应收余额、逾期账龄和回款情况；
- 合同收入、实收和未收金额；
- 单车已确认直接经营成本；
- 客户、保险、供应商或其他责任方待追回敞口。

现有 ROE 在阶段1保留并改名为“单车直接经营试算 ROE”，继续披露实收收入、现有成本参数和静态权益资本假设，不作为阶段1核心验收指标。阶段1不实施全成本管理 ROE。

阶段1完成需要满足：

- 至少 95% 的正常订单除已批准人工节点外不需要运营人工推动；
- 正常合同除已批准人工节点外基本自动运行；
- 关键资金事实不再使用人工勾选替代真实账单和核销；
- 合同收入、应收、收款和车辆直接成本不再依赖线下主表；
- 车辆限制、成本及追回均能追溯到来源业务和证据；
- 阶段1A、1B、1C 可以独立上线，但整体完成时数据必须贯通。

## 阶段2：资产资本、债务、收益权与对外资金闭环

阶段2将当前融资、资产方结算和每日付款线下表格迁入系统。其目标不是建设会计总账，而是让资产资本和真实资金作业产生结构化、可核销、可追溯的运营财务事实。

### 阶段2A：资本债务数据可信化

在现有融资工具、资本事件、车辆融资分配和收益权模型上补齐：

- 融资合同、本金、利率、期限、还款方式和还款日；
- 融资保证金、履约保证金和其他车辆专属受限资金；
- 一份融资覆盖多辆车时的本金金额或比例分配；
- 合同级本金、利息和费用偿付计划；
- 提前还款、展期、利率变更、分配变更和债务重组的计划版本；
- 线下融资表中的有效余额、未来计划及必要附件迁移；
- 融资合同总额、车辆分配额和未偿本金的勾稽。

历史已支付明细不补造业务事件。需要迁移时只保存核对后的期初余额、累计汇总和原始表格附件。

### 阶段2B：对外付款作业闭环

上线统一付款链路：

`来源业务账单 → 每日付款批次 → 财务线下付款 → 运营 T+1 登记付款结果 → 业务核销`

来源包括：

- 融资偿付；
- 资产运营工单费用；
- 租金收入分配；
- 人工确认的客户退款。

能力包括：

- 当日到期、历史未付、部分支付和明确提前付款的滚动汇总；
- 运营核验和提交、财务接收或退回；
- 一笔实际付款结清多张完整账单；
- 单张账单不足额支付时的账单及金额挂起；
- 多付金额形成收款方待分配付款余额；
- 退款、退回、撤销、冲正和重新分配；
- 每日批次级银行流水或付款回单附件；
- 系统内待办、角标和每日异常汇总。

阶段2B 初版不导入完整银行流水。运营在原付款批次中登记账户、收款方、实际扣款日、金额、流水参考号和关联账单。现金流只代表系统内已登记付款，不能发现计划外银行支出。

阶段2B先选择少量融资合同或付款业务并行核对。金额、状态和未偿余额稳定后，线下主表转为只读归档，再逐批扩大范围。

### 阶段2C：收益分配与 ROE 升级

覆盖：

- 以已收并核销租金为基础的车辆级收入分配；
- 同一资产方、同一期间的结算单汇总及付款；
- 退款、冲正或收款调整进入下一结算期；
- 权责发生制经营收入和已确认实际成本；
- “账龄比例 + 单项认定”的坏账拨备；
- 融资本金按实际扣款日减少；
- 期间加权平均权益资本；
- 单车直接经营试算 ROE 的正式升级及新旧口径差异解释。

阶段2只实施租金收入分配，不实施扣除单车实际成本后的净利润分润。后者必须等成本台账达到足够及时性和准确性后另行设计。

固定付款账户和流程稳定后，可以通过银行 API 向同一付款事实模型自动写入结果和候选匹配。银行 API 是阶段2完成后的效率增强项，不是阶段2退出硬门槛。

### 阶段2退出门槛

- 存量有效融资的合同条款、余额及未来计划已完成勾稽；
- 系统能够生成每日应付清单并滚动带出历史未付项目；
- 每笔系统管理的付款可以追溯到来源账单、付款结果和核销；
- 融资本金、利息、保证金和车辆资本占用能够按期间还原；
- 资产方租金收入分配可以从实收租金追溯到结算单和付款；
- 单车直接经营试算 ROE 使用权责收入、坏账拨备、实际成本和期间加权权益资本。

## 阶段3：经营财务分析与财务一体化准备

阶段3建立全局经营财务视图和预测能力，但不建设正式会计总账、税务核算或自动制证。

### 阶段3A：经营财务事实统一

覆盖：

- 月度运营快照及后续版本差异；
- 权责经营收益和收付现金流分开展示；
- 应收账龄、坏账拨备、债务余额和资产方应付；
- 单车、车辆池、产品、资产所有方和全资产组合分析；
- 车辆采购至处置的全生命周期收益结算；
- 指标到合同、账单、工单、付款、追回和资本事件的双向追溯。

### 阶段3B：资金与资产预测

预测基础包括：

- 存量合同的未来应收及已知变更；
- 已确认周期成本和来源业务应付；
- 融资本息偿付计划和保证金退回；
- 车辆利用率、逾期率及残值情景；
- 已知处置计划和预计处置现金流。

输出包括未来现金流、债务到期结构、资金缺口、资产收益变化和实际与预测差异。预测以合同、计划和实际运营数据为主，不使用缺乏依据的维修准备金制造虚假精度。

### 阶段3C：财务一体化准备

建立：

- 业务事件与未来会计科目、核算维度之间的版本化映射；
- 收入、成本、资产、债务及收付款的可勾稽数据包；
- 期间汇总、差异说明和来源凭证链接；
- 面向后续财务系统的稳定导出或接口契约。

阶段3完成边界是会计源数据完整、可映射、可勾稽。不自动生成或推送正式会计凭证，不建设总账、税务申报或会计期间关账。

阶段3仍不增加全成本管理 ROE。待营销成本、客户线索归因、转化率、人力和公司管理成本数据稳定后，再单独评估。

## 全新数据库与测试数据隔离

由于系统尚未进入实质生产，后续阶段使用全新数据库，不为当前测试业务数据设计兼容、回填或修复逻辑。

处理原则：

1. 对当前测试数据库做完整逻辑备份，记录迁移版本、备份时间和校验信息；
2. 原数据库改为只读参考，运行环境不再连接，也不进行双库同步；
3. 新开发数据库使用独立名称和凭证，在阶段0最终Schema上从仓库现有迁移链完整初始化；
4. 新库只导入角色权限、系统配置、产品主数据和受控测试种子；
5. 当前测试订单、合同、融资、付款及核销数据不迁移；
6. 已提交或执行的迁移文件不得修改，后续结构变化继续使用增量迁移；
7. 每次数据库发布仍验证全新建库和从新开发基线升级，但不验证旧测试业务数据兼容；
8. 自动化测试使用独立、可重建的测试数据库。

原测试数据库只读快照保留至阶段1整体验收完成。之后单独决定冷归档或删除，任何删除动作都需要明确批准。

## 跨阶段发布与迁移原则

- 以能力为单位切换，不进行跨三个阶段的大爆炸发布；
- 新能力上线后，新业务直接在系统中产生，不继续新增对应线下主表记录；
- 需要并行核验时必须限定业务范围和退出条件，不进行无限期双录；
- 差异使用可审计调整记录处理，不伪造历史事件；
- 每个后续指标必须建立在已通过退出门槛的事实之上；
- 银行 API、净利润分润、完整财务系统和全成本管理 ROE 均由成熟度触发，不提前加入阶段硬范围。

## 总体验收结果

阶段0及三个业务阶段完成后，系统应形成以下能力链：

`车型主数据及新库初始化 → 订阅合同自动履约 → 车辆资产运营 → 资本债务与收益权 → 对外付款核销 → 经营财务统计与预测`

业务团队获得完整合同履约和应收事实，运营中台获得车辆、工单、成本、资本和结算闭环，财务后台获得结构化付款计划、现金事实、资产债务数据和可勾稽分析。系统为后续银行 API、财务系统接口和更高级经营指标提供稳定边界，但不在本路线图内扩展为完整会计或通用 OA 平台。
