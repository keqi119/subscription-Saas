# Stage 2 全量证据绑定 PDF 设计

日期：2026-07-25

## 决策摘要

Stage 2 车辆交接确认书采用单一 PDF，并覆盖本次交接全部有效证据文件。

- 每一张原始照片都进入签署范围。PDF 嵌入该照片的压缩可视副本，同时列出原始文件编号、原始文件 SHA-256、文件大小和上传时间。
- 每一个原始视频都进入签署范围。PDF 不嵌入视频二进制，而是嵌入关键帧并列出原始文件编号、原始文件 SHA-256、时长、文件大小和上传时间。
- 全部文件进入一份确定性 evidence manifest。用户确认记录、Stage 2 PDF 和后续电子签任务绑定同一个 `manifestHash`。
- 原始照片和视频继续保存在私有对象存储中。PDF 只提供平台受保护的稳定证据包入口，不包含 OSS object key、bucket、临时签名地址或第三方签署地址。
- 任一证据文件新增、替换、删除、失效或重新处理后，旧的用户确认和未签 Stage 2 PDF 都不能继续使用。
- 本设计完成并通过 PDF 视觉验收前，不进入法大大 Stage 2 上传、签署坐标或签署任务映射。

## 问题定义

现有 Stage 2 PDF 只显示证据项、状态、文件数量、文件名和媒体类型。它能够说明系统中存在证据文件，但不能让签署文件本身充分表达用户确认的具体车况，也没有把签署内容与原始图片、视频建立不可变对应关系。

电子签只能证明签署人认可了被签数据电文所载内容。为了让交接确认具有明确证明对象，PDF 必须同时满足：

1. 用户能够在签署材料中直接识别主要车况内容。
2. 每个原始媒体文件都能与签署材料建立不可变关联。
3. 签署后能够调取原始文件并验证其未被替换。
4. 文件数量和体积保持在可生成、可预览、可上传电子签平台的范围内。

## 范围

本次设计包含：

- 原始证据文件 SHA-256 计算与保存。
- 照片展示副本和视频关键帧的生成与私有存储。
- 确定性 evidence manifest 与 `manifestHash`。
- 用户确认与 `manifestHash` 的绑定。
- Stage 2 PDF 的全量照片附件、全量视频清单和关键帧附件。
- PDF 生成的内存、文件体积和失败控制。
- Admin、Field 和 Portal 所需的处理状态与阻断原因。
- PDF 内容、版式、证据覆盖、文件体积和资源消耗验收。

本次设计不包含：

- 将原始视频或其他可执行多媒体对象嵌入 PDF。
- 公开 OSS 地址或把对象存储改成公开读。
- 法大大 Stage 2 上传、签署坐标、签署链接、回调或归档映射。
- 交付确认、租赁开始、计费、短信、微信或财务流程变更。
- 修改照片 10MB、视频 300MB 的单文件上传上限。
- 修改依赖包、Docker、staging 或 production 基础设施。

## 当前容量边界

当前交接证据清单有 14 个证据项：

- 常规证据最多产生 12 个文件。
- 损伤/瑕疵静止近拍最多允许 20 个文件。
- 无可见损伤声明不包含文件。

因此，一次交接最多约 32 个有效证据文件。照片单文件上限为 10MB，视频单文件上限为 300MB。原始文件总量可能达到数 GB，所以 PDF 生成过程不得读取并嵌入原始视频，也不得把全部原始照片同时保存在内存中。

当前 PDF 渲染器把完整输出汇总为一个 Buffer，并设置 20MiB 上限。加入证据附件后应改为临时文件或流式输出。法大大合同上传接口规定单文件不得超过 20MB，但未明确 MB 的十进制或二进制口径，因此平台内部采用 18MiB（18,874,368 字节）硬门槛并以 15MiB（15,728,640 字节）为正常目标值，给接口口径和后续处理保留余量。

## 术语

- **原始文件**：Field 上传并存入私有存储的照片或视频，是计算原始 SHA-256 的对象。
- **展示衍生物**：由原始文件生成、仅用于 Portal 预览和 PDF 展示的压缩照片或视频关键帧。
- **evidence manifest**：列出本次交接全部有效原始文件及其确定性元数据的规范化 JSON。
- **manifestHash**：对规范化 manifest 计算得到的 `sha256:<hex>`。
- **证据包**：原始文件、展示衍生物、manifest、Stage 2 PDF、用户确认记录和后续签署归档之间的逻辑集合。

## 不变量

1. manifest 必须包含生成时全部且仅包含有效状态的证据文件，每个文件恰好出现一次。
2. manifest 中每个文件必须具有原始文件 SHA-256、原始大小、媒体类型、证据项、上传时间和稳定文件编号。
3. 照片没有可视副本、视频没有规定数量的关键帧、媒体探测失败或 SHA-256 缺失时，证据包不得进入用户确认或 PDF 生成。
4. 用户确认记录必须保存确认时的 `manifestHash`。
5. PDF 必须打印证据包编号、manifest 版本、`manifestHash` 和全部文件条目。
6. PDF 中每张照片都必须有可辨识的展示内容；每个视频都必须有关键帧和原始视频信息。
7. 原始媒体不嵌入 PDF。PDF 内的链接只能指向平台受保护的稳定证据包页面，不能包含临时凭证或对象存储内部信息。
8. manifest 生成后发生任何证据变更时，旧 manifest 立即失效；旧用户确认不再满足 PDF readiness，未签 PDF 不得继续签署。
9. 已签 PDF 和其 manifest 不被覆盖。后续更正必须创建新版本并重新确认、重新签署。
10. 法大大后续接收的文件必须与 Admin 视觉验收通过的 Stage 2 源 PDF 是同一份字节内容或可验证的同一文件哈希。

## 媒体预处理

### 执行时机

新文件上传时，API 利用现有磁盘临时文件完成媒体预处理，然后再将文件绑定到证据项。每次请求只处理当前上传的一个文件，避免一次处理整份证据包。

首期不引入新的队列或依赖。处理完成前，Field UI 显示“服务器处理中”；预处理失败时本次上传整体失败，不产生可用于用户确认的半成品证据记录。

对于历史文件或在其他入口绑定、但缺少处理产物的文件，提供幂等的 Admin 重试准备操作。PDF 生成接口不得在请求中临时下载和转码大型原始视频。

### 原始文件哈希

- 使用 Node.js 流式读取临时文件并计算 SHA-256。
- 哈希对象是上传后的原始字节，不是展示副本。
- 持久化格式为 `sha256:<64 位小写十六进制>`。
- 同时记录实际文件大小、探测到的媒体格式和处理时间。

### 照片展示副本

- 处理 EXIF 方向，生成 JPEG 展示副本。
- 默认长边不超过 1600px。
- 默认目标大小为 200KB 至 400KB。
- VIN、仪表里程和损伤近拍允许使用较高清晰度档位，但仍必须受单张展示副本上限控制。
- 若预计 PDF 超过 15MB，按预设档位降低分辨率或 JPEG 质量，不得省略照片、标题、文件编号或哈希。
- PDF 中嵌入展示副本；原始照片继续通过 SHA-256 和 manifest 绑定。

### 视频关键帧

- 使用媒体探测结果记录视频时长和实际容器/编码信息。
- 车辆环绕视频提取 4 张关键帧，建议位置为时长的 10%、35%、60% 和 85%。
- 其他视频提取 2 张关键帧，建议位置为时长的 25% 和 75%。
- 极短视频或无法按比例定位的视频使用可提取的不同时间点，避免重复空白帧。
- 每张关键帧长边不超过 1280px，目标大小为 100KB 至 200KB。
- 关键帧只是签署文件中的可视索引。原始视频本身通过 SHA-256、manifest、用户确认记录和受保护访问入口进入签署范围。

### 媒体处理器

实现使用无 shell 拼接的受控子进程调用预配置的 `ffmpeg`/`ffprobe`，同时处理照片规范化、视频探测和关键帧提取：

- 二进制路径来自明确配置或受控默认路径。
- 参数以数组方式传入，不执行用户提供的命令文本。
- 禁用 stdin，限制处理超时和并发。
- 输入只允许当前请求的已验证临时文件。
- 输出只允许当前请求的专用临时目录。
- 成功、校验失败、超时、存储失败和请求异常均清理临时产物。
- 运行环境缺少可用媒体处理器时，上传失败并返回明确阻断原因，不生成不完整证据。

本次代码不修改 package、Docker 或生产环境。部署媒体处理器属于后续发布前置检查，不在本分支内隐式完成。

## 数据模型

首期复用 `VehicleDeliveryEvidenceFile.metadata` 保存处理结果，避免为本次闭环扩大数据库迁移范围。结构至少包含：

```json
{
  "artifactVersion": 1,
  "sourceSha256": "sha256:<hex>",
  "sourceSizeBytes": 123456,
  "detectedMimeType": "image/jpeg",
  "processingStatus": "READY",
  "processedAt": "2026-07-25T00:00:00.000Z",
  "photoPreviewFileId": "<uuid>",
  "videoDurationMs": null,
  "videoFrameFileIds": []
}
```

照片使用 `photoPreviewFileId`；视频使用 `videoDurationMs` 和有序的 `videoFrameFileIds`。展示衍生物继续作为私有 `FileObject` 保存。API DTO 只暴露安全的业务编号、状态和受保护代理路径，不暴露 bucket、object key 或内部存储路径。

若后续出现跨业务复用、独立生命周期或大规模异步处理需求，再把 metadata 提升为独立证据衍生物模型；本次不提前引入。

## Manifest 设计

manifest 使用显式字段和固定排序，不直接序列化 Prisma 对象。顶层至少包含：

```json
{
  "schemaVersion": 1,
  "evidencePackageId": "<handover-id>",
  "orderId": "<uuid>",
  "workOrderId": "<uuid>",
  "handoverId": "<uuid>",
  "files": []
}
```

文件按证据项固定顺序、上传时间、证据文件 ID 排序。每项至少包含：

- `evidenceType`
- `evidenceItemId`
- `evidenceFileId`
- `fileId`
- `mediaType`
- `originalName`
- `sourceSizeBytes`
- `sourceSha256`
- `uploadedAt`
- `videoDurationMs`
- 展示衍生物的稳定文件 ID 列表

规范化 JSON 使用稳定键顺序和 UTF-8 编码计算 SHA-256。同一组输入必须得到相同的 `manifestHash`，与数据库查询返回顺序无关。

manifest 快照和 `manifestHash` 写入 Stage 2 `Contract.contractSnapshot`。用户确认记录必须能够追溯到同一 `manifestHash`。任何证据生命周期变化都会导致重新计算结果不同，并使旧确认不再满足 readiness。

用户确认的持久化来源为当前确认成功的 `VehicleHandoverReviewAttempt.evidenceSnapshot`。该快照保存完整 manifest、`manifestHash` 和确认时的 artifact 版本；`VehicleHandoverWorkOrder.customerConfirmedAt` 继续只表示确认时间，不单独充当证据版本来源。Stage 2 PDF readiness 必须读取最新确认成功的 review attempt，并校验其 `manifestHash` 与当前有效证据重新计算的结果一致。

## 用户确认

Portal 继续通过客户所有权校验后的代理接口展示全部原始证据或安全预览。确认按钮旁明确说明：

> 本人已查看本次交接证据包所列全部照片和视频，并确认其反映的车辆交接状态。证据包及文件清单构成本车辆交接确认书不可分割的组成部分。

确认请求提交当前页面展示的 `manifestHash`。API 必须重新计算或读取当前有效 manifest 并执行一致性比较：

- 相同：记录客户 ID、确认时间和 `manifestHash`。
- 不同：返回证据已变化，要求刷新、重新查看并重新确认。

单独记录文件预览/播放日志可增强审计，但不得把前端日志当作文件完整性依据。签署范围由 manifest 和原始哈希确定。

## PDF 结构

主文和现有基础表格之后增加：

1. **证据包声明**
   - 证据包编号
   - manifest 版本
   - `manifestHash`
   - 照片数量、视频数量、总文件数
   - 客户确认时间
   - 全量证据确认声明

2. **证据摘要表**
   - 保留 14 个证据项
   - 显示每项状态、文件数量和附件页引用

3. **照片证据附件**
   - 每张有效照片都显示一次
   - 照片统一采用每页最多 4 张的 2×2 布局
   - 每张照片下显示证据项、原始文件名、证据文件 ID、上传时间、原始大小和 SHA-256

4. **视频证据附件**
   - 每个有效视频都显示一次
   - 环绕视频显示 4 张关键帧，其他视频显示 2 张
   - 显示证据项、原始文件名、证据文件 ID、时长、原始大小、上传时间和 SHA-256
   - 显示平台受保护的稳定证据包入口；首期复用绝对化后的 `/portal/handover-reviews/{workOrderId}`，不包含访问令牌
   - 明确注明关键帧用于识别，完整视频以对应 SHA-256 的归档原文件为准

5. **签署区**
   - 客户签署声明明确引用证据包编号和 `manifestHash`
   - 平台签章区继续保留
   - 后续法大大签署坐标只映射到最终视觉验收通过的稳定页位

## PDF 资源控制

- 目标 PDF 大小不超过 15MiB，平台内部硬门槛为 18MiB；法大大外部绝对上限为 20MB。
- 生成前根据全部展示衍生物大小估算输出体积；预计超限时选择更低的预定义图像档位。
- 所有文件始终保留条目和展示内容；容量控制只能降低展示分辨率或 JPEG 质量。
- PDFKit 输出写入专用临时文件或存储流，不再使用 `Buffer.concat` 持有完整 PDF。
- 展示衍生物按 manifest 顺序逐个读取，媒体读取并发限制为 1 至 2。
- 生成后验证 PDF 文件头、实际字节数、页数和可解析性，再上传为 Stage 2 源文件；页数不得超过 100 页。
- 临时 PDF 和临时展示文件在成功、失败和异常退出路径均被清理。

在当前最多约 32 个文件的边界下，预计最终 PDF 为 10MiB 至 15MiB、约 15 至 30 页。该数值是设计目标，不替代真实媒体压力测试。

## 状态与失败处理

需要向 readiness 暴露以下阻断状态：

- 原始 SHA-256 缺失。
- 照片展示副本缺失。
- 视频时长或关键帧缺失。
- 媒体格式探测失败。
- manifest 已变化，客户需要重新确认。
- PDF 预计或实际超过 18MiB，或页数超过 100 页。
- 媒体处理器不可用或处理超时。

失败不能降级为只写文件名的 PDF。Admin 可以重试缺失衍生物准备；重试是幂等的，不能改变原始文件 SHA-256。若原始字节发生变化，必须创建新证据文件版本。

## 安全与隐私

- PDF 不包含 bucket、object key、服务器路径、临时签名 URL、Cookie、Bearer token、Field token 或法大大 provider payload。
- 证据包入口首期复用 `/portal/handover-reviews/{workOrderId}`。PDF 写入配置的公开 Web 基址与该路径组成的绝对地址，访问时再次执行客户所有权校验；Admin 继续使用已有 Admin 证据预览入口。
- 页面访问时可按需生成短期对象存储地址，但短期地址不写入 PDF 或 manifest。
- manifest 可保存内部文件 ID，不保存可绕过应用鉴权的存储地址。
- 受保护的 Stage 2 签署源 PDF 完整展示承租方姓名、手机号、证件号、出租方经办人联系电话和车辆 VIN；Portal、现场任务、审核队列及其他 API DTO 继续沿用脱敏规则。

## 测试设计

### 单元测试

- 原始文件使用流式 SHA-256，结果与已知测试向量一致。
- manifest 字段、排序和规范化编码确定；输入顺序变化不改变 `manifestHash`。
- 每个有效文件恰好进入 manifest 一次；替换、删除或失效文件被排除。
- 任一文件缺少 SHA-256 或展示衍生物时 readiness 被阻断。
- 照片生成正确方向、尺寸和目标体积的 JPEG。
- 环绕视频生成 4 张关键帧，其他视频生成 2 张。
- 媒体处理超时、非法格式和空输出均失败关闭并清理临时文件。
- 客户提交旧 `manifestHash` 时确认失败。

### API 与集成测试

- 新照片和视频上传完成后，证据记录包含 READY 的 artifact metadata。
- 原始媒体和展示衍生物均为私有 FileObject。
- Portal 只能访问所属订单证据，DTO 不泄露存储内部字段。
- 证据变化后旧客户确认不再满足 Stage 2 PDF readiness。
- PDF 生成只读取展示衍生物，不下载原始视频。
- PDF 生成失败不会留下可签署 Contract、孤立源 PDF 或错误 handover 关联。
- PDF 下载继续执行现有 Admin 权限校验。

### PDF 内容与视觉验收

使用包含中文、长文件名、竖图、横图、VIN 细节、里程细节、损伤近照和多段视频的真实尺寸测试集：

- 主文、基础表格、证据声明、14 行摘要、照片附件、视频附件和签署区完整。
- manifest 中每个文件在 PDF 中恰好出现一次。
- 每张照片可辨识，不拉伸、不旋转错误、不裁掉关键内容。
- 每个视频的关键帧、时长、文件编号和 SHA-256 可读。
- 跨页标题、页码、附件引用和签署区无重叠、截断或孤立标题。
- PDF 不超过 18MiB，正常目标不超过 15MiB，页数不超过 100 页。
- 使用 Poppler 渲染全部页面并人工检查首尾页、所有附件页和签署页。
- 使用 PDF 文本提取检查证据包编号、`manifestHash`、全部证据文件 ID 和全部原始 SHA-256。
- 对最大 32 文件压力样本记录生成耗时、输出大小和 Node 进程内存增量。

### 回归测试

- 现有 Stage 2 readiness、客户无异议、Stage 1 已签和禁止重复生成规则继续生效。
- 不创建法大大任务，不调用签署上传或签署链接接口。
- 不修改订单 Stage 1 `contractId`。
- 不触发交付确认、租赁、计费、短信或微信副作用。

## 验收标准

- 用户确认覆盖当前 manifest 中全部有效原始照片和视频。
- PDF 中每张照片有可视副本，每个视频有关键帧和完整文件指纹。
- PDF、用户确认记录和原始证据能够通过同一个 `manifestHash` 相互核对。
- 任一证据变化都会阻止旧确认继续生成或签署 Stage 2 PDF。
- 最大 32 文件压力样本生成成功，输出不超过 18MiB、页数不超过 100 页，且生成过程不读取原始视频进入 PDF。
- PDF 全页视觉验收通过后，才允许启动下一阶段法大大 Stage 2 签署映射设计。
