# 阶段 1 退车证据、合同计价与结算闭环设计

## 1. 文档状态

- 日期：2026-08-26
- 状态：已完成业务设计确认，待实施计划
- 对应验收问题：`ACC-20260826-05`、`ACC-20260826-06`
- 适用基线：`Staging-20260824-b6558b6`
- 上游基线：
  - `2026-08-18-stage1-capability-boundary-audit-revised-baseline-design.zh-CN.md`
  - `2026-08-21-stage1-p0-return-recovery-settlement-implementation-plan.md`

## 2. 背景与现有底座

现有 `SubscriptionClosureCase` 已具备正常结束、提前结束、追回、物理控制、检查、不可变文档修订、不可变结算修订、库存释放、审批和命令收据等后端能力。订单页目前主要提供旧退车操作和 Closure 只读投影，未把后端能力组织成可操作的三阶段闭环。

当前最直接的问题是损伤照片要求业务人员输入 URL；虽然资产工单证据已经支持 `FileObject`、文件摘要、证据类型和替代关系，但退车损伤仍把 `photoUrls` 作为 JSON 字段接收。与此同时，交付/退回差异、合同条款、责任、账单、客户意见和最终处置之间缺少结构化关联。

## 3. 已确认业务口径

1. 退车分为车辆取回取证、异状认定与合同计价、结算与订单完结三个大节点。
2. 客户同意、拒绝或未响应都不能阻断车辆取回、整备和库存处置。
3. 运营闭环与债权状态分离：车辆已取回、合同已终止并完成必要证据后，订单可以运营完结。
4. 争议或司法追偿中的应收不能伪装为已支付或已核销。
5. 只有实际付款、法院执行到账、和解减免或经审批的坏账核销才能消灭债权。

## 4. 目标

1. 用受控文件上传替代新退车损伤记录中的 URL 文本。
2. 对车况、钥匙、行驶证、充电设备和随车附件逐项确认并固化证据。
3. 建立交付基线与退车事实的结构化差异。
4. 每个收费项可追溯到合同版本、具体条款、差异事实、证据和计算过程。
5. 支持客户同意、部分/全部异议和未响应。
6. 支持主动支付、人工确认付款、押金抵扣/退款、审批减免、坏账和司法追偿。
7. 车辆库存释放和订单运营完结不等待争议或诉讼结束。
8. 全过程保持不可变修订、幂等、权限和审计。

## 5. 非目标

1. 不在阶段 1 建设完整法务案件管理或法院文书自动交换系统。
2. 不自动识别照片损伤等级；损伤认定仍由授权人员确认。
3. 不删除或覆盖已有 `photoUrls` 历史数据。
4. 不允许通过人工改小账单金额代替减免或坏账审批。

## 6. 三阶段编排

```text
阶段一：车辆取回与证据固化
  -> 阶段二：差异、责任、合同计价与账单发布
  -> 阶段三：客户反馈、收款/处置与运营完结
```

三个阶段由同一个 `SubscriptionClosureCase` 关联，但分别保存进度、完成时间、责任人和阻断原因。任何财务等待不得把车辆重新投影为仍由客户控制。

## 7. 阶段一：车辆取回与证据固化

### 7.1 退车交接工单

创建或复用 Closure 关联的退车交接工单。确认清单至少包括：

- 外观、内饰和可见结构状态
- 电池、充电口和充电设备
- 实际里程
- 主钥匙、备用钥匙及数量
- 行驶证、登记/保险等车辆文件
- 随车工具、三角警示牌、充气/补胎设备等附件
- 客户遗留物
- 违章初查
- 清洁和维修需求
- 其他合同约定的交还项目

每一项保存结构化状态：`NORMAL`、`MISSING`、`DAMAGED`、`NOT_APPLICABLE`、`PENDING_VERIFICATION`，并允许填写备注和绑定证据。

### 7.2 受控文件采集

复用 Field Handover 的上传、进度、预览、失败提示和替代交互。新证据必须通过文件接口写入 `FileObject`，再绑定到工单检查项或损伤项。

证据事实包括：

- `fileId`
- `contentSha256`
- MIME 类型、原始文件名和文件大小
- 上传人和上传时间
- 可用时的拍摄时间、设备和位置元数据
- 车辆、订单、Closure Case、工单和检查项
- 证据类型
- `supersedesEvidenceId`

原始证据不可覆盖。更正通过新证据替代旧证据，旧证据仍可审计和导出。

### 7.3 损伤证据模型

`VehicleReturnDamage.photoUrls` 进入历史兼容模式。新增损伤与 `AssetWorkOrderEvidence` 或专用关联表的多对多绑定。每个损伤至少要求：

- 损伤类型、等级、描述和位置
- 责任初判
- 一份全景或上下文证据
- 一份近景证据；确实无法取得时必须填写例外原因并审批

API 不再接受业务人员任意提交的新外部 URL。历史 URL 在界面只读展示，并标识“历史外部引用，完整性未验证”。

### 7.4 退车清单文档

生成版本化 `RETURN_MANIFEST` PDF，内容包括：

- 车辆、订单、合同和双方身份摘要
- 取回时间、地点和人员
- 完整检查清单
- 钥匙、行驶证和附件交还结果
- 损伤及证据索引
- 客户意见或拒签事实
- 文档修订号、清单哈希和证据清单哈希

正常场景由客户和平台签署。客户拒签、不在场或失联时，平台记录原因、通知事实、现场人员和补充证据，允许继续确认物理控制；文档明确标识为单方取证版本，不伪造客户签名。

### 7.5 物理控制与库存

确认平台取得车辆控制权后：

- 设置 `physicalControlledAt`。
- 订单进入退回待处理的运营状态。
- 车辆进入检查/整备状态。
- 完成必要检查后可释放为维护或可用库存。
- 上述操作不等待客户确认费用或完成付款。

## 8. 阶段二：交退差异与合同计价

### 8.1 交付基线

以实际签署并归档的交付清单、Field Handover 事实和交付证据为基线。基线必须保存来源文档修订、证据清单哈希和合同引用，不读取可被后续覆盖的当前页面表单。

### 8.2 差异记录

建立版本化 `VehicleConditionDelta`，每项包含：

- 交付检查项及状态
- 退车检查项及状态
- 交付证据引用
- 退车证据引用
- 差异类型与数量
- 正常损耗判断
- 责任方和认定依据
- 认定人、时间和修订

更正差异通过新修订完成，不覆盖已经用于报价或账单的旧修订。

### 8.3 合同计费条款快照

合同生成时固化机器可执行的退车计费条款快照。条款至少包含：

- `clauseCode` 和客户可见条款标题
- 合同及合同版本
- 适用费用类型
- 计费单位、单价、阶梯、封顶和免赔规则
- 正常损耗和免责条件
- 必需证据类型
- 舍入规则和币种
- 条款原文定位或摘要

支持的阶段 1 费用包括超里程、损伤、缺件、钥匙/文件缺失、清洁、维修和提前结束等合同明确约定的项目。

### 8.4 费用明细

每个 `ClosureChargeLine` 或等价不可变明细必须关联：

- Closure Case 和结算修订
- 差异修订
- 合同及条款快照
- 数量、单价、计算步骤和结果
- 责任认定
- 证据引用
- 对应应收账单
- 价格例外审批（如有）

系统先生成费用预览，授权人员确认责任和计价事实后生成正式结算修订与账单。

### 8.5 无条款或证据不足

无法匹配合同条款、证据不足或需要人工覆盖价格时：

- 创建价格例外待办。
- 要求说明、补充证据和审批。
- 未批准前不得形成客户应付正式账单。
- 不阻断车辆检查、整备、库存释放和运营闭环。

## 9. 客户确认与争议

### 9.1 修订级客户反馈

每个正式结算修订对应一个客户反馈记录：

- `PENDING`
- `ACCEPTED`
- `PARTIALLY_DISPUTED`
- `DISPUTED`
- `NO_RESPONSE`

客户提交时绑定精确结算修订和每个争议费用明细。新结算修订发布后，旧反馈只保留历史，不自动套用。

### 9.2 Portal 能力

客户可以查看：

- 交付/退车差异
- 合同条款依据
- 证据缩略图或受权文件
- 计算过程和金额
- 押金抵扣及应付/应退金额

客户可以同意全部费用，或对具体明细提交异议、说明和补充文件。

### 9.3 异议与未响应

异议创建独立争议记录和时间线。Admin 可以补充证据、维持、调整或撤销收费；任何金额变化都通过新结算修订和必要审批完成。

超过通知期限未响应时记录 `NO_RESPONSE`、通知尝试和送达事实，可进入催收或司法评估，但不得记为客户同意。

客户同意、异议或未响应均不阻断车辆物理与运营流程。

## 10. 阶段三：结算与处置

### 10.1 客户主动支付

客户同意或决定先支付无争议部分时，从 Portal 创建主动支付单。支付回调经过签名、幂等和金额校验后：

1. 写入支付事实。
2. 核销对应应收明细。
3. 更新结算投影。
4. 保留部分支付和剩余债权。

### 10.2 人工介入

支持：

- 银行转账、现金或其他线下实收登记
- 付款凭证上传和复核
- 押金抵扣
- 押金退款
- 和解或减免审批
- 坏账核销审批

人工“确认收款”必须引用真实付款凭证；减免、和解和坏账分别使用明确的账务动作，不能共用“已支付”状态。

### 10.3 司法追偿

将全部或部分债权转入 `LEGAL_COLLECTION` 时记录：

- 转入原因、金额和应收明细
- 争议与通知记录
- 证据包版本和哈希
- 法务负责人、外部案件编号（如有）
- 判决、和解、执行到账或终止追偿的后续事实

`LEGAL_COLLECTION` 不等于付款、减免或坏账。只有实际到账、批准和解减免或批准坏账核销才减少/消灭债权。

## 11. 运营状态与财务状态双轴

### 11.1 运营轴

继续由 Closure Case 和订单状态表达：

```text
PREPARING_RETURN
  -> VEHICLE_SECURED
  -> RETURN_INSPECTION
  -> RECONDITIONING / PENDING_SETTLEMENT
  -> COMPLETED 或 TERMINATED
```

运营完成门槛：

- 车辆已取得物理控制。
- 退车证据清单已固化。
- 合同已按正常到期或提前结束终止履行。
- 车辆已进入明确库存/整备状态。
- 所有未结费用已进入明确财务处置状态。

最后一项允许为待收款、争议或司法追偿，但不能是无归属待办。

### 11.2 财务轴

增加独立财务投影：

- `DRAFT`
- `AWAITING_CUSTOMER`
- `PARTIALLY_PAID`
- `DISPUTED`
- `COLLECTION_PENDING`
- `LEGAL_COLLECTION`
- `SETTLED`
- `WRITTEN_OFF`

现有 `SubscriptionClosureSettlementRevision.stage=SETTLED` 只用于没有未结债权的真实结清。运营闭环时若存在司法追偿，结算修订保持 `FINALIZED`，财务投影为 `LEGAL_COLLECTION`。

### 11.3 应收处置

为每个应收明细保存独立处置：

- `OPEN`
- `PAID`
- `MANUAL_PAYMENT_CONFIRMED`
- `WAIVED`
- `WRITTEN_OFF`
- `LEGAL_COLLECTION`

处置通过追加事件或修订记录，不覆盖支付和账单历史。

## 12. Admin 与 Portal 页面

### 12.1 Admin 三阶段工作区

1. **车辆取回**：检查清单、文件上传、损伤、签署和物理控制确认。
2. **费用确认**：交退差异、责任、合同条款、计算预览、例外审批和账单发布。
3. **结算处置**：客户反馈、支付、押金、人工收款、减免/坏账、催收和司法追偿。

按钮由后端 `allowedActions` 返回，前端不自行猜测 Closure 状态机。Closure 当前只读面板升级为可操作工作区。

### 12.2 Portal

- 展示退车预约、清单和签署文件。
- 展示客户可见证据、合同依据和费用计算。
- 支持同意、逐项异议和主动支付。
- 显示争议处理和剩余应付，不暴露内部法务备注或审批材料。

## 13. 权限、安全与证据导出

按车辆接收、检查、责任认定、计价、账单发布、收款确认、减免审批、坏账审批和司法转交拆分权限。

文件下载采用鉴权或短期签名地址。证据包导出包含：

- 合同和计费条款版本
- 交付与退车签署文件
- 原始证据及 SHA-256
- 差异、责任和费用修订
- 客户意见、通知和支付/处置事实
- 审计时间线和证据包自身哈希

导出不改变任何业务状态。

## 14. 数据迁移与兼容

1. 新建检查项证据关联、差异修订、收费明细、客户反馈、争议和财务处置结构。
2. 保留 `VehicleReturnDamage.photoUrls` 读取；新 API 写入禁止外部 URL。
3. 历史 URL 可以转换为来源类型 `LEGACY_EXTERNAL_REFERENCE` 的只读记录，但不得伪造 SHA-256 或上传时间。
4. 为现有 Closure Case 根据当前状态生成初始财务投影，不改写历史 Settlement Revision。
5. 迁移采用扩展—回填—切换读取—停止旧写入的顺序。

## 15. 错误与恢复

- 文件上传失败保留表单草稿并显示失败项，不生成不完整签署清单。
- 客户拒签或不在场走单方取证分支，不进入技术异常。
- 条款缺失走价格例外，不进入默认计价。
- 支付未知结果进入主动查询/人工核对，禁止重复核销。
- 库存释放失败可重试，但不撤销已经成立的车辆物理控制事实。
- 所有命令带幂等键、期望版本和不可变命令收据。

## 16. 测试与验收

### 16.1 阶段一

- 钥匙、行驶证、附件和车况的必填矩阵。
- 文件上传、哈希、预览、失败恢复和证据替代。
- Return Manifest 内容、版本、哈希、正常签署和单方取证。
- 确认物理控制后车辆状态不受客户费用意见影响。

### 16.2 阶段二

- 交付/退车差异生成和修订。
- 合同条款匹配、计算、封顶和舍入。
- 无条款、证据不足和人工价格覆盖审批。
- 每个账单明细的合同、差异和证据追溯。

### 16.3 阶段三

- 客户同意、部分异议、全部异议和未响应。
- 主动支付、部分支付、重复回调和未知支付结果。
- 线下收款、押金抵扣/退款、和解减免和坏账审批。
- 司法追偿保持债权，不错误标记为已支付。

### 16.4 双轴闭环

- 财务未结或司法追偿时车辆仍可释放库存。
- 订单可运营完结，同时应收继续存在且可追踪。
- 真正结清后 Settlement Revision 才进入 `SETTLED`。
- 所有历史修订和证据可导出且哈希可复算。

## 17. 最终验收门槛

1. 退车损伤可直接上传并预览照片/视频，不再输入 URL。
2. 车况、钥匙、行驶证和随车附件进入签署退车清单。
3. 每项异常费用能追溯到交退差异、合同版本、条款、证据和计算。
4. 客户同意、拒绝或未响应均有明确分支且不阻断车辆处置。
5. 主动支付、人工介入和司法追偿保持不同会计与业务语义。
6. 车辆库存释放和订单运营完结不等待诉讼结束，未结债权不丢失。
