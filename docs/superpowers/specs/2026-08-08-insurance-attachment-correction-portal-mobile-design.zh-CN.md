# 保单与附件纠错、中文文件名治理及 Portal 移动端记录优化设计

日期：2026-08-08

状态：已完成逐节评审，待实施计划

## 1. 背景

本轮调整来自 Staging 人工验收后的七类问题：

1. 保单列表缺少删除入口，错误保单无法纠正；
2. 保单附件的中文文件名显示为乱码，且上传错误后无法删除；
3. 保单详情要求选择与保单无关的通用材料类型，操作冗余且容易误选；
4. 客户个人材料、商品照片、配置单、检测报告、车辆权证等多个上传入口存在相同的中文文件名或纠错能力风险；
5. Admin 左侧菜单虽已独立滚动，但不需要显示单独的滚动条；
6. Portal 权益表格在手机窄屏中被压缩为逐字换行；
7. Portal 账单中的支付单和核销记录表格存在相同的窄屏问题。

根因审计确认，当前上传端点普遍直接使用 Multer `AnyFilesInterceptor()` 的默认参数。Multer 2.1.1 将 multipart 参数字符集默认按 `latin1` 解释，UTF-8 中文文件名因而可能被保存成类似 `è½¦è¾...` 的乱码；各服务随后又将 `file.originalname` 原样写入数据库。附件删除能力则分散在各业务域中：部分服务已有软删除 API 但页面未暴露，部分证据材料按业务规则本来就不允许直接删除。

Portal 问题不是数据错误，而是桌面 Ant Design `Table` 在手机宽度下继续保留多列造成的布局挤压。

本设计采用已确认的方案 A：统一上传入口的字符集与文件名边界，同时在各业务域内实现受约束的纠错操作；不建设新的通用附件中心，也不重写现有业务流程。

## 2. 目标

### 2.1 业务目标

- 错录保单可以受审计地软删除，并从日常列表和有效保险计算中排除；
- 保单详情上传自动继承保单上下文，不再要求用户选择材料类型；
- 可纠错附件具有一致的预览、删除或替换能力；
- 商品引用和不可变业务证据继续受到强制保护；
- 新上传的中文文件名在所有入口正常保存和显示；
- 可可靠识别的历史乱码文件名得到幂等修复；
- Admin 左侧菜单保留滚动能力但不显示滚动条；
- Portal 权益、支付单和核销记录在手机端形成稳定、易读的信息卡片。

### 2.2 工程目标

- 将 multipart UTF-8 配置、文件名规范化和测试样例收敛到共享边界；
- 复用现有 `VehicleDocument`、`VehicleDocumentBatch`、商品原件绑定和各业务附件模型；
- 删除与作废规则由服务端强制校验，前端按钮可见性不作为安全边界；
- 数据迁移可预览、可重复执行、可审计、可精确回滚；
- Portal 响应式调整不改变现有 API 合同和业务数据模型。

## 3. 非目标

本轮不包含：

- 新建全局附件中心、统一附件表或跨业务文件生命周期平台；
- 将申请、付款、核销、交付、合同等证据材料改成任意删除；
- 物理删除对象存储中的历史文件；
- 重命名或移动对象存储的 bucket/object key；
- 改造理赔、订单、账单、权益或支付流程；
- 重构整个 Admin 导航框架或改变菜单层级；
- 将 Portal 桌面表格全部改为卡片；
- 修复无法可靠判断编码来源的历史文件名。

## 4. 总体架构

本轮分为四个相互隔离的改造单元：

```text
上传与文件名基础能力
  ├─ 统一 multipart UTF-8 配置
  ├─ 文件名安全规范化
  └─ 历史乱码扫描、修复与审计清单

保单与附件纠错
  ├─ 保单错误记录软删除
  ├─ 保单专用附件上传语义
  ├─ 可纠错附件的删除/替换
  └─ 商品引用与不可变证据保护

Admin 导航微调
  └─ 隐藏菜单滚动条，保留全部滚动方式

Portal 响应式展示
  ├─ 桌面继续使用表格
  └─ 手机使用方案 A 信息卡片
```

各单元共享错误表达和测试规范，但不互相侵入业务模型。除保单软删除唯一性、删除审计及必要的迁移辅助结构外，不增加新的持久化抽象。

## 5. 中文文件名治理

### 5.1 新上传文件的解析边界

所有使用 multipart 的文件上传入口必须引用同一组受测试的 Multer/Busboy 配置，显式设置：

```text
defParamCharset = utf8
```

覆盖范围至少包括：

- 客户及客户个人材料；
- 外勤和交付证据；
- 里程复核材料；
- Portal 申请、个人资料、服务工单和复核材料；
- 车辆商品图片；
- 保单、车辆权证、配置单和检测报告；
- BaaS 及其他现有 multipart 入口。

不允许各 Controller 继续分别依赖默认字符集。已有文件大小、数量和 MIME 限制继续保留，并与共享字符集配置组合，而不是被新配置覆盖。

### 5.2 文件名规范化

文件进入存储服务和数据库前，统一执行以下处理：

1. 取 basename，去除客户端路径；
2. 去除 NUL、控制字符、路径分隔符和不可见双向控制字符；
3. 进行 Unicode NFC 规范化；
4. 保留合法扩展名，限制基础名与整体长度；
5. 空名称使用安全回退名称，不使用对象 key 作为展示名称；
6. `fileName`、`originalName` 和对象元数据使用同一个规范化结果；
7. 预览响应使用 UTF-8 `filename*`，前端不再自行进行 Latin-1/UTF-8 转码。

对象存储 key 继续由服务端生成，不能直接采用客户端文件名，避免路径穿越、覆盖和隐私泄露。

### 5.3 历史乱码识别与修复

迁移工具只修复满足下列条件的记录：

- 当前文本符合“UTF-8 字节被按 Latin-1/Windows-1252 解码”的特征；
- 将候选文本按 Latin-1 还原为字节后可严格解码为 UTF-8；
- 修复结果不包含替换字符或非法控制字符；
- 往返编码校验成立；
- 修复结果与原值不同且更符合可读文件名特征。

修复只更新数据库中的展示/原始文件名字段，不修改文件内容、bucket 或 object key。无法可靠判断的记录保持原样，进入人工复核清单。

迁移按“预览”和“应用”两种模式运行，逐条保存：

- 数据表或业务来源；
- 记录 ID；
- 修复前文件名；
- 修复后文件名；
- 命中的检测规则；
- 执行时间和批次标识。

同一记录重复执行不得再次转码。回滚使用审计清单按记录 ID 恢复原值，不依赖重新推导乱码。

### 5.4 迁移结果报告

每次预览或应用输出：

- 扫描数量；
- 自动修复数量；
- 已正常、无需处理数量；
- 跳过及待人工确认数量；
- 失败数量和原因；
- 各业务来源的分项统计。

## 6. 保单记录纠错

### 6.1 删除语义

保单“删除”专门表示纠正错误录入，不替代正常的到期、取消或归档流程。操作入口放在列表行尾“更多”菜单中，文案为“删除错误记录”。

删除操作要求：

1. 操作者具有现有保单管理权限；
2. 二次确认并填写非空删除原因；
3. 服务端再次加载保单及其关联关系；
4. 已有关联理赔记录时返回 409，禁止删除；
5. 任一关联附件被商品原件绑定时返回 409，提示先解除引用；
6. 校验通过后在同一事务中软删除保单和未绑定的关联保单附件；
7. 保单保障范围等历史明细保留在软删除的父记录下，不物理删除；
8. 写入操作人、时间、原因、保单 ID 和删除前摘要的审计记录。

删除后的保单：

- 不出现在默认保单列表和车辆详情的有效保单区域；
- 不参与保险有效性、到期提醒和交付校验；
- 仍可通过审计记录追踪；
- 不通过普通 UI 恢复，若需恢复必须使用受控运维流程。

已结束但真实存在的保单应使用 `CANCELLED`、`EXPIRED` 或 `ARCHIVED`，不能使用错误记录删除。

### 6.2 唯一性

当前 `VehicleInsurancePolicy` 使用 `@@unique([vehicleId, policyNo])`，这会阻止错误记录软删除后重新录入同一保单号。

实施时应将其替换为数据库级活动记录部分唯一索引：

```sql
UNIQUE (vehicle_id, policy_no) WHERE deleted_at IS NULL
```

Prisma schema 对无法直接表达的部分索引保留说明和对应契约测试，避免后续迁移重新创建无条件唯一约束。

### 6.3 API 合同

建议新增：

```text
DELETE /vehicle-insurance-policies/:id
body: { reason: string }
```

成功响应返回被软删除记录的最小摘要或标准成功结果。主要错误：

- `404`：保单不存在或已删除；
- `409 POLICY_HAS_CLAIMS`：已关联理赔；
- `409 POLICY_DOCUMENT_BOUND`：关联附件仍被商品引用；
- `422 DELETE_REASON_REQUIRED`：缺少有效原因。

现有归档接口继续保留，二者语义不得混用。

## 7. 保单附件专用上传

### 7.1 操作界面

保单详情上传区只保留：

- 选择一个或多个文件；
- 可选备注；
- 上传按钮。

不再显示材料类型、保单号、车辆、有效期和客户可见性。详情上下文已经确定这些值，重复填写只会增加误操作。

### 7.2 服务端派生规则

由保单 ID 加载保单后生成附件字段：

| 保单类型             | `VehicleDocumentType`         |
| -------------------- | ----------------------------- |
| `COMPULSORY_TRAFFIC` | `COMPULSORY_INSURANCE_POLICY` |
| `COMMERCIAL`         | `COMMERCIAL_INSURANCE_POLICY` |
| `OTHER`              | `OTHER`                       |

同时派生：

- `vehicleId = policy.vehicleId`；
- `policyId = policy.id`；
- `effectiveFrom/effectiveTo = policy.effectiveFrom/effectiveTo`；
- `customerVisible = true`；
- `description = 用户填写的可选备注`。

前端不得提交可覆盖上述派生字段的隐藏参数。服务端也不得信任客户端提供的车辆或材料类型。

建议新增保单上下文接口：

```text
POST /vehicle-insurance-policies/:id/documents
multipart: files[] + optional description
```

通用 `POST /vehicles/:id/documents` 继续服务其他车辆材料，以保持兼容。

### 7.3 保单附件列表

每个文件显示：

- 正常化后的文件名；
- 上传时间；
- 可选备注；
- 预览；
- 删除错误文件。

删除复用 `DELETE /vehicle-documents/:id` 的软删除语义，并补齐操作人及原因审计。被商品引用时按钮置灰并显示具体绑定原因，服务端仍返回 409 保护。

## 8. 附件生命周期矩阵

附件不采用“一律可删”策略，而按业务证据属性分组：

| 业务位置         | 允许的纠错方式               | 删除约束                                 |
| ---------------- | ---------------------------- | ---------------------------------------- |
| 客户个人材料     | 删除错误文件、重新上传或替换 | 已进入不可逆流程的快照仍按流程保护       |
| 保单附件         | 删除错误文件、重新上传       | 商品引用时阻止；保单删除时受关联规则约束 |
| 车辆商品照片     | 删除、隐藏、重传             | 封面及发布状态沿用现有约束               |
| 车辆配置单       | 删除版本、上传新版本         | 商品原件绑定时必须先解除引用             |
| 车辆检测报告文件 | 删除版本、上传新版本         | 商品原件绑定时必须先解除引用             |
| 车辆权证材料     | 删除单个错误文件、上传新批次 | 被商品引用时阻止                         |
| 申请提交材料     | 补传更正版本或按原因作废     | 不允许直接删除证据                       |
| 付款及核销凭证   | 补传更正版本或按原因作废     | 不允许直接删除财务证据                   |
| 交付证据         | 补传更正版本或按原因作废     | 不允许直接删除交付证据                   |
| 已签合同         | 版本更正或作废流程           | 不允许直接删除签署证据                   |
| 流程审计材料     | 追加更正说明                 | 不允许删除审计证据                       |

### 8.1 权证批次内单文件纠错

现有权证页面保留批次和版本概念，并在批次文件列表增加单文件删除操作：

1. 删除前校验文件未被商品引用；
2. 仅软删除目标 `VehicleDocument`，不影响同批次其他文件；
3. 删除后若该批次无任何有效文件，则批次按现有“有效文件为零/已归档”语义处理；
4. 权证完整度立即根据当前有效文件重新计算；
5. 历史批次和版本号不复用、不重排。

若实施时需要显式区分“空批次”和“已归档批次”，可以为批次增加最小归档时间字段；不得借此扩展成新的附件状态机。

### 8.2 商品原件绑定

配置单和检测报告被 `VehicleListingSourceBinding` 引用时，以下操作均返回 409：

- 删除文件；
- 归档文件或批次；
- 把文件改为不兼容类型；
- 删除其关联保单。

前端展示“已用于商品配置单”或“已用于商品车况报告”，并提供前往解除引用的上下文提示。上传新版本不会自动改绑。

## 9. Admin 界面设计

### 9.1 保单管理

- 主要操作继续保留“查看/编辑”；
- “删除错误记录”放入低频“更多”菜单；
- 删除确认框包含简短风险说明和原因输入；
- 成功后刷新列表、有效保险摘要和车辆详情局部数据；
- 409 错误直接显示业务原因，不把记录提前从页面移除。

### 9.2 附件操作表达

统一使用三类表现：

- **可纠错附件**：显示“预览、删除/替换”；
- **已绑定附件**：显示绑定标签，删除置灰并说明先解除引用；
- **不可变业务证据**：显示“已提交，不可直接删除”，提供补传更正或作废入口。

不增加独立附件管理页，操作仍在原业务详情中完成。

### 9.3 左侧菜单滚动条

`menuViewport` 继续保持 `overflow-y: auto`，但通过标准和 WebKit 样式隐藏滚动条：

```text
scrollbar-width: none
::-webkit-scrollbar { display: none }
```

不得改成 `overflow: hidden`。鼠标滚轮、触控板、触屏、PageUp/PageDown、Home/End 和现有滚动位置恢复能力必须继续可用；右侧内容滚动仍不影响左侧菜单位置。

## 10. Portal 响应式记录展示

### 10.1 断点与总体规则

沿用 `768px` 移动端断点：

| 视口       | 权益、支付单、核销记录      |
| ---------- | --------------------------- |
| `> 768px`  | 保留现有桌面表格和列密度    |
| `<= 768px` | 使用已确认的方案 A 信息卡片 |

桌面和手机使用同一份请求结果，不重复发起 API 请求，不把视口信息提交给服务端。

### 10.2 权益卡片

卡片从上到下展示：

1. 权益名称及状态标签；
2. 突出的剩余额度、次数或文本权益；
3. 已使用额度；
4. 权益类型；
5. 来源；
6. 有效期。

不同单位沿用现有格式化规则。文本型权益不得伪造成数值。有效期可以分为起止两行，但中文标签不得逐字断行。

权益使用记录如需在同页展示，使用相同卡片骨架并突出使用量和使用时间。

### 10.3 支付单和核销卡片

支付单卡片展示：

- 支付单号和状态；
- 突出的已付金额；
- 支付渠道；
- 支付时间。

核销卡片展示：

- 收款或支付单号；
- 核销状态；
- 突出的核销金额；
- 收款方式；
- 核销时间。

长单号使用整词/字符级安全换行或复制友好的截断方案，金额与单位不拆开，中文标签设置最小宽度。无数据继续复用现有空状态。

### 10.4 可访问性

- 卡片保持可读的标题层级和状态文本，不只依赖颜色；
- 交互入口具有键盘焦点样式和足够触控面积；
- 金额、日期和单号的视觉顺序与 DOM 阅读顺序一致；
- 页面不得因卡片内容产生水平滚动。

## 11. 数据与 API 影响

### 11.1 数据库

必要改动包括：

- 将保单号唯一性调整为未删除记录的部分唯一索引；
- 为保单删除原因和操作人提供现有审计日志或最小审计字段；
- 增加迁移专用文件名修复审计清单或等价的可回滚记录；
- 若现有批次投影无法明确表达归档，可增加最小 `archivedAt`，但优先沿用有效文件数语义。

不改变订单、账单、支付、权益、理赔主模型。

### 11.2 API

新增或收敛：

```text
DELETE /vehicle-insurance-policies/:id
POST   /vehicle-insurance-policies/:id/documents
```

复用并强化：

```text
DELETE /vehicle-documents/:id
POST   /vehicle-document-batches/:batchId/archive
```

所有删除/归档接口必须在服务端执行商品绑定和证据可变性校验。Portal 权益和账单 API 不变。

## 12. 异常处理

| 场景                       | 行为                                                 |
| -------------------------- | ---------------------------------------------------- |
| 保单已关联理赔             | 返回 409，提示只能取消或归档                         |
| 保单/附件被商品引用        | 返回 409，列明绑定板块并提示先解除引用               |
| 不可变证据请求删除         | 返回 409/422，提示补传更正版本或作废                 |
| 删除原因缺失               | 返回 422，不改变任何记录                             |
| 文件类型、大小或名称不合法 | 返回 400/413，指出具体文件                           |
| 批量上传部分存储失败       | 清理本次已上传对象或保持事务一致性，不创建半批记录   |
| 文件名修复无法可靠判断     | 保持原值，进入人工复核清单                           |
| 文件名修复单条失败         | 记录失败，按迁移事务边界决定整批回滚或安全续跑       |
| Portal 字段缺失            | 使用统一回退文案，不显示 `undefined`，不破坏卡片布局 |

批量上传若沿用“整批为一个版本”的语义，则保持全成功或全失败；独立保单文件允许服务端返回逐文件结果时，前端必须明确列出成功和失败文件，不能笼统显示“全部成功”。

## 14. 数据迁移与部署

推荐顺序：

1. 备份目标数据库，并验证回滚权限；
2. 部署兼容旧 Web 的 API 及数据库结构迁移；
3. 运行文件名修复预览，审核统计和歧义清单；
4. 执行文件名修复应用并保存审计清单；
5. 部署新 Web；
6. 执行健康检查、API 回归和浏览器响应式检查；
7. 通知进入 Staging 人工验收。

回滚策略：

- API/Web 回滚到上一镜像；
- 文件名依据审计清单恢复原值；
- 软删除记录不物理清除，可通过受控运维恢复；
- 部分唯一索引迁移在回滚前先检查是否已有重复活动记录；
- 不回滚或移动对象存储 key，因为本轮从未修改它们。

## 15. 人工验收清单

1. 在客户个人材料、保单、商品照片、配置单、检测报告和权证入口分别上传中文文件名，列表和预览均正常；
2. 核对历史截图中的乱码记录已修复，歧义记录出现在人工清单；
3. 保单上传区只显示文件、备注和上传，不显示材料类型；
4. 交强险、商业险和其他保单附件自动落入正确类型；
5. 删除无理赔、无商品绑定的错误保单后，列表和保险有效性立即更新；
6. 使用同一保单号重新录入成功；
7. 删除有关联理赔或商品绑定的保单时收到明确阻止提示；
8. 删除错误的保单附件、客户材料、商品照片或权证文件成功；
9. 删除商品已引用的配置单/检测报告失败，解除引用后成功；
10. 删除权证批次中的一个文件不影响其他文件，最后一个文件删除后批次显示归档/无有效文件；
11. 申请、付款、核销、交付、合同和审计证据不能直接删除；
12. Admin 左侧菜单无可见滚动条，滚轮、触控板和键盘滚动正常；
13. 右侧内容滚动不影响左侧菜单位置；
14. Portal 权益在手机端为信息卡片，不出现逐字换行；
15. Portal 支付单和核销记录在手机端为信息卡片，金额、单号和时间可读；
16. Portal 桌面端继续显示现有表格；
17. 主要页面无新增水平滚动、权限泄露或业务流程回归。

## 16. 已确认决策

- 采用方案 A：统一上传边界与业务域纠错，不做通用附件中心重写；
- 错误保单采用软删除，理赔关联阻止删除；
- 商品绑定文件先解绑再删除；
- 保单附件上传由保单上下文自动派生类型和有效期；
- 可纠错材料允许删除/替换，不可变业务证据只允许更正版本或作废；
- 历史乱码只做保守、可逆、幂等修复，不修改对象存储 key；
- Admin 菜单隐藏滚动条但保留滚动；
- Portal 手机端采用方案 A 信息卡片，桌面端保留表格。

本设计批准后，下一步使用 `writing-plans` 形成逐任务、可测试、可回滚的实施计划；实施计划获准前不修改业务代码。
