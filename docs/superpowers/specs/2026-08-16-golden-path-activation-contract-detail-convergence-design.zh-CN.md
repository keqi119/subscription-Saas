# Golden Path 激活与合同详情收敛修复设计

## 1. 背景与已确认事实

当前 Staging 验收订单 `ORD20260814085019DMGZ` 已完成 Stage 2 交接签署、平台盖章、签署文件归档和人工“通过证据”，但 Journey 停留在 `AUTHORITATIVE_ACTIVATION`。

服务端只读核查确认：

- `VehicleDeliveryHandover` 已是 `ARCHIVED / ARCHIVED`，签署文件、对象键与 SHA-256 均存在；
- 对应 Stage 2 `Contract` 仍为 `SIGNED`，且 `fileId` 仍指向待签原件，而不是已签署归档文件；
- 工单保存的证据摘要为 `sha256:<hex>`，交接记录保存为 `<hex>`，现有激活判断按原字符串比较，误判为证据未批准；
- 因此激活引擎同时报告 `HANDOVER_ARCHIVED_ARTIFACT_MISSING` 与 `HANDOVER_EVIDENCE_NOT_APPROVED`。

另一个验收现象是主合同 `CON20260814085019DZ64` 已显示归档，但合同详情页看不到电子签流程结果和签署完成 PDF。数据库事实为：

- 主合同状态为 `ARCHIVED`，`signedAt`、`archivedAt`、已签文件 `fileId` 均存在；
- Stage 1 法大大任务为 `COMPLETED`，`signedDocumentObjectKey` 已写入；
- 已签 PDF 文件对象存在且文件名、对象键完整；
- 前端合同详情页会单独请求 `/contracts/:id/esign-tasks`，但把所有请求错误静默转换成空数组；
- 合同基础详情的访问范围判断接受大写角色（如 `ADMIN`），电子签服务却仅判断小写 `admin`。认证层实际输出的是大写 `RoleCode`，导致同一管理员能打开合同，却可能无法读取电子签任务；错误随后又被前端伪装成“暂无电子签任务”。

## 2. 目标

1. Stage 2 已签文件归档成功时，交接记录、关联合同和文件指针在同一事务中收敛为一致事实。
2. 激活引擎兼容带或不带 `sha256:` 前缀、大小写不同但摘要相同的 SHA-256 表达。
3. 以幂等迁移修复发布前已经归档、但关联合同仍未收敛的 Stage 2 存量记录。
4. 具有合同查看范围的管理员在合同详情页能够看到真实电子签任务、签署人结果、归档状态和已签 PDF 入口。
5. 电子签任务加载失败时明确提示错误，禁止再把接口异常显示成“暂无电子签任务”。
6. 修复后重新驱动当前 Journey，让现有人工审批结果继续进入权威激活，而不是重做签署或人工审核。

## 3. 非目标

- 不重新发起或替换已完成的 Stage 1/Stage 2 法大大签署任务。
- 不修改已归档 PDF 的内容、哈希或签署结果。
- 不绕过 `DELIVERY_EVIDENCE_DECISION` 人工审批。
- 不放宽普通销售人员的数据范围；其合同访问仍受所属销售约束。
- 不修改还车、支付、委托代扣或权益生成的业务规则。
- 不把接口异常降级成来自合同表的伪造电子签结果。

## 4. 方案比较

### 方案 A：事实收敛、摘要规范化、统一访问范围（采用）

- 在 Stage 2 最终归档事务中同时更新交接记录和关联合同；
- 激活比较前统一规范化 SHA-256；
- 用迁移修复同形态存量数据；
- 电子签服务的合同范围判断与订单/合同服务保持同一大写角色语义，并继续支持 `order:view:all`；
- 前端区分“接口成功但无任务”和“接口失败”。

优点：修复数据根因与展示根因，正常路径和存量路径均可恢复，权限边界不扩大。

### 方案 B：只放宽激活引擎

让激活仅信任 `VehicleDeliveryHandover`，忽略合同状态和文件指针。

缺点：合同详情、下载、审计与后续业务仍会读取到不一致合同，问题被隐藏而未修复。

### 方案 C：仅手工修当前 Staging 数据

缺点：无法防止后续订单复发，也无法修复合同详情权限错配和错误吞没。

## 5. 详细设计

### 5.1 Stage 2 归档事务收敛

`FadadaSignedArtifactService.finalizeStage2Archive` 在创建或复用已签 `FileObject` 后，于同一数据库事务中：

1. 更新 `ContractESignTask.signedDocumentObjectKey`；
2. 更新 `VehicleDeliveryHandover` 为权威归档状态并写入 `signedDocumentFileId`；
3. 更新 `VehicleDeliveryHandover.handoverContractId` 指向的合同：
   - `status = ARCHIVED`；
   - `signedAt` 保留既有值；为空时使用已确认的签署完成时间/归档时间；
   - `archivedAt = archivedAt`；
   - `fileId = signedDocumentFileId`；
   - `updatedBy` 使用本次系统执行主体；
4. 校验更新目标确为该 handover 的关联合同，禁止按订单范围批量更新。

重复执行时，如果三个实体已经指向同一已签文件，返回已有结果，不创建重复文件或覆盖为待签原件。

### 5.2 摘要规范化

新增单一内部规范化函数：

- 去除首尾空白；
- 大小写不敏感地移除一个可选的 `sha256:` 前缀；
- 将 64 位十六进制统一为小写；
- 非法格式返回不可比较结果，不做宽松相等。

`LeaseActivationEngine.sameManifest` 只比较规范化后的合法摘要。这样兼容历史存储格式，但不会让空值或非法字符串通过。

### 5.3 存量数据迁移

新增幂等迁移，仅处理满足全部条件的记录：

- handover 为完整权威归档；
- `signedDocumentFileId` 非空且对应文件对象存在；
- `handoverContractId` 非空且合同未删除；
- 合同尚未同时满足 `ARCHIVED`、正确 `fileId` 和非空 `archivedAt`。

迁移将合同收敛到 handover 的已签文件，并使用 handover 的归档时间。迁移不创建文件、不修改 PDF、不改变 Journey 或人工任务状态。

### 5.4 合同详情电子签可见性

后端保留现有 `/contracts/:id/esign-tasks` 接口及所有权校验，但修正全量查看判断：

- 按系统真实 `RoleCode` 使用大写角色集合；
- 与订单合同详情现有可见角色一致；
- 继续认可 `order:view:all`；
- 非全量角色仍只能读取自己负责申请下的合同。

同时修正同域已签 PDF 预览的访问范围判断，避免列表能看、文件又被拒绝的第二处不一致。

前端将合同基础信息、电子签任务和当前用户信息分开处理：

- 基础合同成功时仍展示合同；
- 电子签任务成功且为空时才显示“暂无电子签任务”；
- 电子签任务失败时显示可重试的错误提示，不再写入空数组掩盖故障；
- 当任务包含已签文件时，继续使用任务级预览接口展示“查看已签署 PDF”。

## 6. 错误处理与安全边界

- Stage 2 合同收敛失败时，整个最终归档事务回滚，不产生 handover 已归档但合同未归档的新裂缝。
- 存量迁移只向更完整的归档事实收敛，不回退状态，不触碰取消/删除记录。
- SHA-256 非法格式仍判定为条件不满足，并保留现有可观察错误码。
- 前端错误提示不暴露服务端堆栈、对象键或敏感身份数据。
- 权限修复只纠正大小写/角色集合不一致，不新增任何角色或权限。

## 7. 测试策略

### 7.1 API 单元/集成测试

1. Stage 2 最终归档会在同一事务内把合同更新为 `ARCHIVED`，并指向已签文件。
2. 重复归档保持幂等，不重复创建文件，不改变已收敛指针。
3. 事务任一步失败时，handover 与 contract 均不出现半完成状态。
4. 激活引擎接受 `<hex>` 与 `sha256:<HEX>` 表示的同一摘要。
5. 激活引擎拒绝不同摘要、空值和非法摘要。
6. `ADMIN` 等全量角色可读取合同电子签任务与已签 PDF；受限销售仍遵循订单归属。
7. 存量迁移只修复满足严格条件的 Stage 2 合同，重复执行无额外变化。

### 7.2 Web 测试

1. 电子签接口成功返回空数组时显示“暂无电子签任务”。
2. 接口失败时显示明确错误与重试入口，不显示伪空状态。
3. 已完成且有签署文件的任务显示流程结果、签署人状态、归档状态和“查看已签署 PDF”。

### 7.3 Staging 人工验收

1. 打开 `CON20260814085019DZ64`，确认可见 Stage 1 法大大任务结果及已签合同入口，PDF 可正常打开。
2. 重试当前 Golden Path 失败步骤，确认不再出现两个激活缺失条件。
3. 确认 Journey 完成，订单、交付、车辆、Lease、账期与权益进入既定激活状态。
4. 确认 `DELIVERY_EVIDENCE_DECISION` 仍保留本次人工通过记录，没有重复任务或重复激活。

## 8. 发布与回滚

- 发布前执行迁移状态检查、Prisma 校验、聚焦测试、API 全量测试、Web 测试、lint、typecheck 与 build。
- 先执行幂等迁移，再启动新 API；Web 可同时发布。
- 发布后先核对合同详情，再重试 Journey，避免在可观察性仍缺失时继续推进。
- 如应用回滚，已收敛的合同归档数据保持有效；它与已存在的权威 handover 事实一致，无需逆向迁移。
