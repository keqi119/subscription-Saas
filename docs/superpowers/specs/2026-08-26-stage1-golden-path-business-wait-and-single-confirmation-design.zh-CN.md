# 阶段 1 Golden Path 业务等待与最终方案单次确认设计

## 2. 背景与已确认根因

本轮人工验收暴露出 Golden Path 把正常业务等待与技术异常混在同一条错误路径中：

1. Portal 提交申请后，系统立即执行进件校验。材料审核、信用审核或押金尚未完成人工确认时，校验器抛出默认不可重试的 `SubscriptionJourneyError`。
2. Worker 将上述业务未就绪错误直接送入 `DEAD_LETTER`，Journey 和当前步骤被投影为 `EXCEPTION`。
3. 后续材料、风控或产品审核产生的 `APPLICATION_FACTS_CHANGED` 信号，在消费时按照 Journey 的当前步骤重新分派，而不是按照该信号的目标步骤和事实版本进行协调，可能产生错步骤任务或 `JOURNEY_INVALID_TRANSITION`。
4. 最终车辆分配发生在客户首次确认之后；车辆软锁确认又重新计算最终方案。当前商业差异判断直接对选定字段执行 `JSON.stringify`，嵌套 JSONB 对象的键顺序变化会被误判为商业内容变化，从而创建新修订并再次要求客户确认。

这些行为都不是外部系统偶发失败，而是状态与错误分类不完整造成的确定性缺陷。

## 3. 目标

1. Portal 正常提交后，人工材料、风控和押金审批应显示为可解释的业务等待，不进入异常或死信。
2. 业务事实变化能够幂等、乱序安全地重新协调进件校验。
3. 管理员一次完成押金方案、订阅方案和最终车辆软锁，再向客户发布唯一最终方案版本。
4. 正常流程中客户只确认一次最终方案。
5. 只有真正的技术故障或数据不变量破坏才进入异常；所有业务分支均有明确出口。
6. 对现有误入异常的 Journey 提供安全恢复路径。

## 4. 非目标

1. 不在本设计中重写完整 Subscription Journey 引擎。
2. 不改变电子签、初始账单、主动支付、交付和起租的既有业务顺序。
3. 不禁止管理员在客户确认后主动修改真实商业内容；发生真实修改时仍必须生成新修订并重新确认。
4. 不通过后台直接改库清理历史异常。

## 5. 核心原则

### 5.1 业务等待不是异常

进件校验返回结构化结果，而不是用异常表达正常业务状态：

| 结果 | 含义 | Journey 表现 | 后续出口 |
| --- | --- | --- | --- |
| `READY` | 所有进件事实满足 | 完成当前步骤 | 进入最终方案处理 |
| `WAITING_MANUAL` | 等待材料、信用、押金或产品人工处理 | `WAITING_MANUAL` | 事实变化后自动协调 |
| `WAITING_CUSTOMER` | 等待客户补件或更正资料 | `WAITING_CUSTOMER` | 客户重新提交后自动协调 |
| `REJECTED` | 申请被明确拒绝 | Journey 取消/拒绝终态 | 释放车辆占用并保留原因 |
| `SYSTEM_EXCEPTION` | 程序、数据不变量或基础设施故障 | `EXCEPTION` | 自动重试或人工接管 |

`JOURNEY_APPLICATION_MATERIALS_INCOMPLETE` 和 `JOURNEY_APPLICATION_CREDIT_NOT_APPROVED` 不再作为不可重试异常。它们被拆为业务等待原因码，仅用于界面解释和自动协调。

### 5.2 信号只协调声明的目标

所有进件事实信号必须包含：

- `targetStepCode`
- `factType`
- `factVersion`
- `applicationId`
- `sourceActionId`

消费规则：

1. 仅当目标是 `APPLICATION_VALIDATION` 且 Journey 仍处于该步骤时执行重新校验。
2. Journey 已越过该步骤时，信号按幂等成功处理，不对当前步骤产生副作用。
3. 低于已处理事实版本的迟到信号直接忽略。
4. 同一 `applicationId + factType + factVersion` 只产生一次协调效果。
5. 不再根据消费时的当前步骤将任意领域事实映射为当前步骤任务。

### 5.3 客户确认发生在最终车辆软锁之后

正常顺序调整为：

```text
APPLICATION_VALIDATION
  -> FINAL_PLAN_DECISION
  -> FINAL_VEHICLE_ALLOCATION
  -> CUSTOMER_PLAN_CONFIRMATION
  -> ORDER_AND_CONTRACT_CREATION
```

Admin 的“提交最终方案”是一个编排命令，在同一业务事务内完成：

1. 锁定申请及 Journey。
2. 校验材料、风控、客户等级和押金方案。
3. 校验订阅月份、套餐、价格和目标车辆。
4. 对目标车辆建立或确认软锁。
5. 生成规范化的最终方案快照与唯一修订号。
6. 完成 `FINAL_PLAN_DECISION`。
7. 自动完成 `FINAL_VEHICLE_ALLOCATION`，不再产生第二个人工确认任务。
8. 打开 `CUSTOMER_PLAN_CONFIRMATION`，向客户发布该修订。

事务中任一环节失败时，不得发布客户确认，也不得留下无主车辆软锁。

## 6. 商业方案修订语义

### 6.1 规范化比较

建立共享的 canonical JSON 工具，对对象键递归排序、保留数组顺序、统一 `undefined`/缺失字段规则，再进行稳定哈希或深比较。Repository 当前私有的 canonical JSON 能力应提取为共享实现，避免 Journey 与幂等层使用不同算法。

商业比较只选择下列语义字段：

- 套餐及套餐版本
- 订阅周期
- 月租、押金和其他客户应付价格
- 里程、补能等权益限制
- 最终车辆标识及客户可见车辆快照
- 生效日期和合同关键条款版本

时间戳、数据库键顺序、审计字段、内部锁记录和展示字段不参与商业修订判断。

### 6.2 修订规则

1. Admin 首次提交最终方案时创建修订 `N`，并记录 `commercialSnapshotHash`。
2. 车辆软锁只是该提交命令的一部分，不得在之后无条件创建修订 `N+1`。
3. 客户确认必须提交精确修订号和哈希。
4. 只有管理员主动改变上述商业字段时才创建新修订、失效旧确认并要求重新确认。
5. 同一修订的重复提交、软锁确认或信号重放均按幂等成功处理。

## 7. 状态恢复与历史兼容

### 7.1 已误入异常的 Journey

提供受控的 `reconcile application validation` 恢复命令：

1. 锁定 Journey、步骤和现有异常。
2. 仅允许恢复错误码属于原业务等待集合、当前步骤仍是 `APPLICATION_VALIDATION` 的记录。
3. 根据最新申请事实计算 `READY`、`WAITING_MANUAL`、`WAITING_CUSTOMER` 或 `REJECTED`。
4. 将旧异常标记为 `RESOLVED`，写入恢复事件和操作者。
5. 不复用“重试技术故障”语义伪装业务恢复。

发布时提供一次可重复执行的 reconciliation 作业，扫描符合条件的开放异常；不对其他错误码自动操作。

### 7.2 已处于后续步骤的 Journey

已越过进件校验或已完成最终方案确认的 Journey 不回退。旧事实事件重放必须是无副作用的幂等成功。

### 7.3 拒绝与车辆释放

申请被明确拒绝时：

- Journey 进入业务终态而非死信。
- 关闭开放人工任务。
- 释放属于该申请且尚未升级为签约锁定的车辆占用。
- 保留拒绝原因、审批动作和库存释放审计。

## 8. Admin 与 Portal 投影

### 8.1 Admin

- 业务等待显示“进件校验 · 等待人工”或“等待客户补件”。
- 展示具体等待原因和最后事实更新时间。
- 业务等待不展示“重试失败步骤”。
- 真正异常才展示重试、暂停、取消和人工接管。
- “提交最终方案”表单一次采集订阅月份、套餐和最终车辆，并明确说明提交后将软锁车辆并开放客户确认。

### 8.2 Portal

- 人工审核期间展示“资料审核中”，不展示“流程需要协助”。
- 补件状态展示缺失项和重新提交入口。
- 最终方案只对一个已发布修订开放确认。
- 同一修订确认成功后按钮保持不可重复操作状态。

## 9. 错误与并发处理

1. 业务状态冲突返回稳定业务码，不进入 Worker 死信。
2. 乐观锁冲突允许短暂自动重试；重读后若目标步骤已完成则按幂等成功。
3. 车辆软锁失败保持在 Admin 决策步骤，显示库存原因，不向客户发布不完整方案。
4. 重复 Admin 提交必须携带幂等键；相同负载返回相同结果，不同负载返回幂等冲突。
5. 共享 canonical JSON 工具必须拒绝循环对象、非 JSON 值和敏感字段。

## 10. 数据与迁移

预期数据变化包括：

- 为进件事实增加单调版本或等价的已处理版本记录。
- 为最终方案保存规范化商业哈希。
- 如现有步骤序列存储为固定顺序，迁移未完成 Journey 的 `FINAL_VEHICLE_ALLOCATION` 与 `CUSTOMER_PLAN_CONFIRMATION` 顺序；终态 Journey 不改写。
- 为业务等待原因建立可查询投影，避免从异常表推断。

所有迁移必须先兼容旧代码读取，再切换写入，最后清理不再使用的路径。

## 11. 安全与审计

- 最终方案提交、车辆软锁、方案重新发布和异常恢复均要求现有相应权限。
- 审计记录保存操作者、来源请求、前后状态、商业哈希和车辆锁结果，不保存支付凭据或敏感身份证明原文。
- 客户只能读取并确认属于自己的申请及精确修订。

## 12. 测试与验收

### 12.1 单元测试

- 五类校验结果映射。
- canonical JSON 对键顺序不敏感、对真实商业变化敏感。
- 迟到、重复和跨步骤事实信号无副作用。
- 客户确认精确修订校验。

### 12.2 集成测试

- Portal 提交后进入 `WAITING_MANUAL`，Job/Outbox 均不死信。
- 三类人工审核以任意顺序完成后仅推进一次。
- Admin 最终方案提交与车辆软锁原子完成。
- 并发选择同一车辆时只有一个申请成功软锁。
- 历史误分类异常可安全恢复，其他异常不被误恢复。

### 12.3 端到端验收

1. Portal 选车并提交。
2. Admin Golden Path 显示“进件校验 · 等待人工”。
3. 完成材料、风控和押金确认后自动出现最终方案操作。
4. Admin 一次提交订阅月份、套餐和车辆。
5. 客户只确认一次最终方案。
6. 系统直接进入合同制作、电子签和归档，不再出现第二次车辆确认或客户确认。

## 13. 发布与回滚

1. 先发布兼容性数据库迁移。
2. 发布 API，并保持旧投影字段可读。
3. 执行历史业务等待异常 reconciliation 试运行并核对数量。
4. 发布 Web，启用新文案和一次性最终方案操作。
5. 完成 Staging 全链路回归后再放量。

回滚时不得删除新事件或修订；关闭新协调入口并恢复旧代码读取，但保留已写入事实供后续重放。
