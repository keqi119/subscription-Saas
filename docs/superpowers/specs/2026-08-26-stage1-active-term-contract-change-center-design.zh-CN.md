## 2. 背景与能力边界

当前订单页的“申请变更方案”只支持交付前退回重做；`ACTIVE` 在租订单被明确排除。V2 变更域已经具备协议延长的变更单、报价、客户确认、补充协议、电子签、合同分段和到期激活能力，但 Admin 没有创建入口，Staging 功能开关未启用。提前结束已存在较完整的闭环后端，Web 没有写操作。换车只有枚举、工单类型和部分资产底座，没有业务编排。

阶段 1 必须让正常到期、续期、换车和提前结束都具有可发现入口和明确终态，同时避免把交付前重做、在租合同变更和退车动作混为同一个操作。

## 3. 目标

1. 在 `ACTIVE` 订单工作台提供统一“发起合同变更”入口。
2. 支持续期、换车、提前结束和受控的其他合同变更。
3. 复用现有 V2 变更域，而不是继续扩展旧的交付前订单变更。
4. 同一订单避免并发合同变更造成合同、车辆、账单或权益分叉。
5. 所有变更具有幂等命令、版本、客户确认、电子签、执行、失败恢复和审计。
6. 换车保持在原订单内，串联旧车回收、新车交付和合同事实。
7. 提前结束与 Subscription Closure 连续衔接。

## 4. 非目标

1. 不提供可任意修改数据库字段的通用合同编辑器。
2. 不把交付前“退回重做方案”迁入在租期变更中心。
3. 不在阶段 1 自动化所有罕见合同变更；未结构化类型走受控人工变更单。
4. 不通过换车创建第二个独立订阅订单。

## 5. 统一入口与业务互斥

### 5.1 页面入口

`ACTIVE` 在租订单的更多操作增加“发起合同变更”，打开类型选择：

- 续期
- 换车
- 提前结束
- 其他合同变更

旧入口改名为“交付前退回重做方案”，仅在原有交付前状态和权限下显示。

### 5.2 单活约束

阶段 1 对同一订单实施“一个活动合同变更”约束。以下状态视为活动状态：

- `DRAFT`
- `QUOTED`
- `CUSTOMER_CONFIRMED`
- `SIGNING_OR_PAYMENT`
- `SCHEDULED`
- `EXECUTING`
- `MANUAL_TAKEOVER`

通过数据库部分唯一索引和事务内锁共同保证。`COMPLETED`、`CANCELLED`、`FAILED` 不占用单活槽位。

## 6. 统一聚合设计

### 6.1 根变更单

扩展 `SubscriptionChangeType`：

- `EXTENSION`
- `VEHICLE_SWAP`
- `EARLY_TERMINATION`
- `MANAGED_OTHER`

`SubscriptionChangeOrder` 继续承担公共事实：

- 变更编号、订单、类型和统一状态
- 当前/已确认报价引用
- 客户确认发布时间
- 关联合同或补充协议
- 生效窗口和完成时限
- 失败、取消和人工接管事实
- 版本、创建人、更新人和审计时间

### 6.2 类型化明细

当前根表中的 `extensionMonths`、`pricingMode`、目标日期等续期专属必填字段迁入 `SubscriptionExtensionChangeDetail`。新增：

- `SubscriptionVehicleSwapChangeDetail`
  - 原车辆、目标车辆、目标套餐版本
  - 双向工单引用
  - 计划/实际换车时间
  - 价格与押金差异快照
- `SubscriptionEarlyTerminationChangeDetail`
  - 生效日、原因、试算修订
  - 提前结束协议和 Closure Case 引用
- `SubscriptionManagedOtherChangeDetail`
  - 原因、生效日、处理说明
  - 操作前后快照
  - 证据和可选补充协议引用

现有续期数据原位迁移到类型化明细，不改变变更编号、客户确认、合同、报价或合同区段。

### 6.3 统一状态机

```text
DRAFT
  -> QUOTED
  -> CUSTOMER_CONFIRMED
  -> SIGNING_OR_PAYMENT
  -> SCHEDULED
  -> EXECUTING
  -> COMPLETED
```

终止和异常出口：

- `CANCELLED`：业务取消，必须补偿已建立的临时占用。
- `FAILED`：不可继续且已安全收敛的失败。
- `MANUAL_TAKEOVER`：自动执行不能安全决定，但仍有明确人工操作入口。

业务等待不使用 `FAILED`。每次状态迁移都写入不可变事件和幂等命令收据。

## 7. 续期流程

复用现有 `SubscriptionExtensionService`、合同服务、激活服务和 Renewal Consideration：

1. Admin 从订单发起续期，选择月份和定价模式。
2. 系统基于当前有效合同区段生成报价。
3. Admin 发布正式报价。
4. 客户确认或拒绝精确报价修订。
5. 确认后生成补充协议并进入电子签。
6. 签署归档后进入 `SCHEDULED`。
7. 到目标生效日创建/激活新的合同区段、账单和权益。
8. 完成后更新 Renewal Consideration。

Web 必须补齐创建、报价、发布、取消、人工接管和执行状态展示。发布配置必须显式设置并启动校验 `SUBSCRIPTION_EXTENSION_ENABLED=true`。

## 8. 换车流程

### 8.1 原订单原则

换车不创建新的订阅订单。原订单保留客户、合同履行、收款和审计主线；通过合同区段、车辆使用期间和变更事件表达车辆切换。

### 8.2 套餐与车辆选择

1. 车辆套餐版本扩展为版本化多车型成员。
2. 换车报价绑定目标套餐版本和具体目标车辆。
3. 发布客户确认前软锁目标车辆。
4. 计算月租、押金、权益及生效日差异；真实商业变化形成报价修订。
5. 并发占用失败保持在 Admin 处理状态，不发布客户报价。

### 8.3 客户确认与补充协议

客户确认精确报价修订后生成换车补充协议，内容至少包括：

- 原车和目标车辆
- 计划换车时间
- 价格、押金和权益变化
- 原车退回义务和新车交付条件
- 异状费用依据

签署归档后才可进入现场执行。

### 8.4 双向工单

创建：

- 原车 `SWAP_INBOUND`
- 新车 `SWAP_OUTBOUND`

两张工单分别记录车况、里程、钥匙、行驶证、附件、证据和签署文件。原车实际取回与新车实际交付可按现场顺序完成，但最终切换必须满足约束。

### 8.5 原子切换

当约定的物理条件、签署条件和首期价格差额条件满足后，在一个编排事务中：

1. 关闭原车辆有效使用期间。
2. 创建并激活目标车辆使用期间。
3. 更新订单当前车辆。
4. 激活新合同区段或变更段。
5. 迁移/重算未来权益，保留历史已用权益。
6. 将目标车辆改为 `LEASED`。
7. 将原车辆置为已取回后的检查/整备状态。
8. 完成变更单。

任何失败不得产生两个同时有效的车辆使用期间，也不得丢失原车控制权。旧车费用结算可以继续，但不反向撤销已合法完成的物理切换。

## 9. 提前结束流程

提前结束变更单负责合同决策，`SubscriptionClosureCase` 负责物理退车、检查、费用和结算：

1. Admin 输入原因和拟生效日。
2. 系统基于合同条款生成提前结束试算。
3. 发布客户确认；客户可同意、拒绝或提出异议。
4. 同意后生成提前结束协议并电子签署。
5. 签署归档且到达执行条件后停止生成生效日之后的未来租期账单。
6. 创建并关联 `EARLY_TERMINATION` Closure Case，进入退车流程。
7. 变更单在 Closure 运营闭环完成后收敛为 `COMPLETED`；财务追偿可按退车结算设计继续存在。

签署前取消或拒绝必须释放临时资源并恢复原合同履行，不得提前停账或释放车辆。签署后的撤销必须通过新的受控命令和审批，不得删除事实。

## 10. 其他合同变更

阶段 1 的 `MANAGED_OTHER` 是受控人工变更单：

1. 必填变更原因、生效日、证据和期望处理结果。
2. Admin 审核后记录允许执行的明确动作，而不是提供任意字段编辑。
3. 涉及客户权利义务时生成补充协议并电子签署。
4. 执行时保存操作前后快照、操作者和审批引用。
5. 租期、车辆和提前结束必须分别转用专用类型，不能借此绕过专用规则。

阶段 1 不为 `MANAGED_OTHER` 自动改写价格、历史账单、车辆或合同区段。

## 11. Admin 与 Portal

### 11.1 Admin

- 订单页统一入口、活动变更摘要和阻断原因。
- 变更中心展示类型、状态、报价修订、客户确认、合同、工单、执行结果和审计时间线。
- 页面按钮由后端 `allowedActions` 和权限共同驱动，不在前端复制完整状态机。
- `MANUAL_TAKEOVER` 必须展示明确的恢复或终止动作。

### 11.2 Portal

- 展示客户所属订单的待确认报价、关键变化和有效期。
- 提供确认、拒绝、电子签、预约及状态查询。
- 不暴露内部审批、人工接管原因或非客户可见证据。
- 已确认修订保持只读，只有新修订才重新开放确认。

## 12. 权限、幂等与审计

按类型和动作拆分创建、报价、发布、审批、执行、取消和人工接管权限。所有写接口必须带幂等键和期望版本。

审计至少记录：

- 变更类型和来源订单
- 报价、合同和目标车辆版本
- 客户确认修订
- 状态前后值
- 资源软锁/释放结果
- 工单和 Closure 关联
- 失败码、人工接管及最终处置

## 13. 数据迁移与发布

1. 扩展枚举和创建类型化明细表。
2. 将续期专属根字段改为兼容迁移期间可空，并回填续期明细。
3. 校验每条现有 `EXTENSION` 都有且仅有一条明细，再切换服务读取。
4. 创建订单活动变更部分唯一索引。
5. 发布 API 后补齐 Admin/Portal。
6. 在 Staging 初始化既有 Active 订单的 BASE 合同区段，试运行核对后开启续期功能。

迁移失败时不得删除现有续期根数据；服务必须能在切换窗口回读旧字段。

## 14. 测试与验收

### 14.1 公共能力

- 四种入口、状态和权限矩阵。
- 同订单并发创建只允许一个活动变更。
- 幂等重放、乐观锁、取消补偿和人工接管。
- 旧续期数据迁移一致性。

### 14.2 续期

- Admin 创建到客户确认、电子签、归档和到期激活。
- 新合同区段、账单、权益和 Renewal Consideration 一致。

### 14.3 换车

- 套餐多车型版本、目标车辆并发软锁。
- 双向工单、双方证据和补充协议。
- 原子车辆切换；故障注入时不存在双租或无车状态。
- 原车检查/费用不阻断新车合法交付后的订单继续履行。

### 14.4 提前结束

- 试算、客户确认、电子签、停未来账单和 Closure 创建。
- 客户拒绝、签署失败和执行失败均有出口。
- Closure 运营完结后变更单收敛，未结债权继续保留。

### 14.5 其他变更

- 证据、审批、可选补充协议和前后快照完整。
- 无法借通用入口绕过续期、换车或提前结束规则。

## 15. 最终验收门槛

1. `ACTIVE` 订单可明确发起四类在租合同变更。
2. 交付前重做与在租变更在名称、权限和接口上完全分离。
3. 续期完整链路可在 Staging 真实操作。
4. 换车在原订单中完成旧车回收、新车交付、合同和权益切换。
5. 提前结束先完成受控方案与协议，再进入退车闭环。
6. 所有路径均能完成、取消、失败收敛或人工接管，不进入无出口死信。
