## STG2-005 调查证据与原因

### 实际文件

本次“现场录像”成功上传的源文件参数如下：

- 容器/编码：QuickTime MOV / H.264
- 分辨率：`480 × 360`
- 帧率：约 `23.98 fps`
- 视频码率：约 `711.6 kbps`
- 时长：约 `22.14 秒`
- 文件大小：`2,337,932 bytes`（约 2.23 MiB）

该文件已经正常进入接口并完成证据处理，因此本次低清晰度现象不是上传失败或网络丢包造成的。

### 前端采集方式

“现场录像”当前使用原生文件输入：

```html
<input type="file" accept="video/*" capture="environment">
```

页面只传递 `accept` 和 `capture`，没有建立摄像头媒体流，也没有传入宽度、高度、帧率或码率约束。W3C HTML Media Capture 规范将 `capture` 定义为用户代理选择采集方式和摄像头朝向的提示，并不提供录像清晰度控制：<https://www.w3.org/TR/html-media-capture/>。

因此，在当前 iPhone 微信内置浏览器环境中，具体录像档位由微信 WebView/iOS 的采集实现选择；本次实际选择了 480×360 的低清晰度档位。

### 服务端处理方式

服务端保存的是上传源文件，视频处理阶段使用 FFprobe 识别格式和时长，并使用 FFmpeg抽取证据关键帧。服务端不会转码或压缩源视频，因此 480×360 是到达服务端前已经形成的源文件分辨率。

当前 FFprobe 元数据只记录编码、MIME 和时长，没有持久化分辨率、帧率、码率，也没有最低清晰度校验。这使低质量视频可以正常显示为“上传成功”。

### 根因分类

STG2-005 属于移动端采集方案的设计缺口和 iOS 微信 WebView 兼容性问题，不属于摄像头硬件、网络、网关或后台压缩问题。

### 根因一：电子签就绪校验使用了过期版本常量

当前源 PDF 生成逻辑统一使用 `STAGE2_HANDOVER_SOURCE_ARTIFACT_VERSION=2`，本单数据库和生成任务也正确记录为版本 2。但 `Stage2HandoverESignReadinessService.checkHandoverSource()` 仍硬编码要求 `artifactVersion === 1`。

因此，Field 详情接口的 `stage2Capabilities.canStartESign` 被判定为 `false`，前端“发起电子签”按钮必然置灰。对应 blocker 为 `SOURCE_ARTIFACT_VERSION_INVALID`。这与 PDF 是否可预览、通知是否发送成功无关；即使通知任务恢复，按钮仍不会解锁。

现有 readiness 单元测试夹具也固定使用版本 1，没有引用生产侧的源 PDF 版本常量，因此未能发现该版本漂移。

### 根因二：Staging 缺少 Stage 2 Field 业务短信配置

交接确认单生成任务 `GENERATE_SOURCE_PDF` 已完成，随后创建的 `NOTIFY_FIELD_ESIGN_READY` 任务连续失败 3 次，目前处于 `PENDING` 重试状态。任务计划下一次重试时间为 2026-08-01 13:26:27（Asia/Shanghai），最大尝试次数为 6。

Staging API 容器未注入以下运行时变量：

- `ALIYUN_SMS_FIELD_HANDOVER_ESIGN_READY_TEMPLATE_CODE`
- `FIELD_OPERATOR_SMS_ENABLED`
- `FIELD_OPERATOR_SMS_PROVIDER`

`SmsService.sendStage2FieldReady()` 在创建发送记录前会强制读取 Field 业务短信模板编号。模板配置缺失时直接抛错，因此本次没有产生 `sms_send_log`，也没有请求短信供应商。工作流只记录了泛化的 `WORKFLOW_ERROR / Workflow operation failed.`，随后按退避策略重试。

### 根因三：工作台没有提供重试中任务的可执行指引

订单工作台把 `NOTIFY_FIELD_ESIGN_READY` 映射为 Field 发起电子签步骤。任务处于 `PENDING` 或 `PROCESSING` 时，页面仅显示当前步骤“处理中”；只有任务进入 `DEAD_LETTER` 后才生成“重发经办人通知”恢复操作。

因此当前阶段既没有明确说明“等待短信配置/任务重试”，也没有提示 Field 页面因 `SOURCE_ARTIFACT_VERSION_INVALID` 无法发起签署，造成 Admin 与 Field 两端都没有可执行的下一步。

### 建议解阻顺序

1. 修正 readiness 校验，统一引用 `STAGE2_HANDOVER_SOURCE_ARTIFACT_VERSION`，并增加版本 2 的回归测试。
2. 部署修复后刷新本工单 readiness，确认 `SOURCE_ARTIFACT_VERSION_INVALID` 消失且按钮可以发起电子签；不得手工把数据库版本改回 1。
3. 经确认使用真实短信环境后，补齐 Field 短信 provider、enabled 和已审核模板编号，再通过受控的 workflow retry 恢复现有通知任务，避免直接改任务状态或重复发送。
4. 工作台对重试中任务显示安全错误分类、下次重试时间和下一步；对永久配置错误应尽早停止无效重试并提供管理员恢复入口。
5. 完成一次端到端回归：客户确认 → PDF v2 → Field 通知 → Field 发起电子签 → 客户签署 → 平台盖章 → 签署文件归档 → 车辆交付确认。

## STG2-007 调查证据与原因

### 本单原始数据没有丢失

Field 当前工单和客户确认快照均保存了以下数据：

```json
{
  "accessoryChecklist": {
    "item1": "车钥匙1把，行驶证1本"
  }
}
```

因此，“车钥匙1把，行驶证1本”已经由 Field 提交并被客户确认。最终 PDF 显示 `item1` 不是现场人员漏填，也不是客户确认快照丢失。

### 根因一：Field 序列化结构与 PDF 格式化规则不兼容

Field 页面目前只有一个“随车物品”自由文本框，提示操作人员逐行填写钥匙、充电线、随车工具等。提交时，前端按行生成内部对象：

```ts
Object.fromEntries(lines.map((line, index) => [`item${index + 1}`, line]))
```

PDF 的 `formatAccessoryChecklist()` 在遇到对象时只保留 truthy 项的属性名：

```ts
Object.entries(value)
  .filter(([, entry]) => Boolean(entry))
  .map(([key]) => key)
```

所以 `{"item1":"车钥匙1把，行驶证1本"}` 被渲染为 `item1`，真实值被忽略。

Field 页面自身回显使用 `Object.values()`，可以显示真实文本；Portal 复核页同时显示键和值；PDF 只显示键。三端对同一字段采用了不同格式化规则，造成跨端内容不一致。

### 根因二：“随车证件”和“随车工具”错误复用同一字段

PDF 渲染器把同一个 `fieldFacts.accessoryChecklistText` 同时写入：

- 车辆基本信息 → 随车证件
- 车况确认 → 随车工具

当前数据模型没有区分证件、钥匙、工具和其他附件，因此即使修正 `item1` 的显示，两个栏位仍会输出完全相同的混合文本，无法表达“行驶证1本”和“车钥匙1把”分别属于什么验收类别。

### 根因三：PDF 车况栏位没有对应 Field 验收字段

PDF 的以下五个项目目前直接写死为 `-`：

- 仪表盘故障灯
- 空调/暖风
- 灯光系统
- 轮胎/备胎
- 内饰清洁度

Field 页面和 API 现有结构只采集里程、能源/油量、交接地点、随车物品自由文本、损伤声明和现场备注，没有上述五项的通过/异常/不适用状态，也没有对应异常说明。当前只有“损伤状态”能与 Field 的损伤声明正确关联，“备注”能关联现场备注。

### 测试覆盖缺口

- PDF 测试使用字符串数组形式的 `accessoryChecklist`，没有覆盖 Field 实际生成的 `{item1: value}` 结构。
- Field ViewModel 测试没有覆盖自由文本 → API payload → PDF render model 的完整链路。
- API DTO 只要求 `accessoryChecklist` 是任意对象，没有固定项目代码、显示名称、数量、状态或 schema version。

### 后续改进方向

1. **优先完善 Field 验收事项。** 将单一自由文本框拆为结构化验收表，至少区分随车证件、钥匙、工具和其他附件，并支持项目名称、数量、状态及备注。
2. **让 Field 车况项目与 PDF 一一对应。** 对仪表盘故障灯、空调/暖风、灯光系统、轮胎/备胎、内饰清洁度设置“正常/异常/不适用”，异常时要求说明；损伤声明继续使用现有专项流程和证据要求。
3. **统一权威数据结构。** 使用稳定业务代码和中文显示标签，例如 `{code, label, status, quantity, unit, note}`，保存 schema version；内部代码不得直接出现在客户页面或 PDF。
4. **按类别渲染 PDF。** “随车证件”只渲染证件，“随车工具”只渲染工具；钥匙和其他附件应有明确归属或独立栏位，不再复用同一混合文本。
5. **保持客户确认一致性。** PDF 必须从客户已确认的 Field facts snapshot 构建，并显示与 Portal 确认页相同的标签和值。
6. **兼容历史数据。** 对现有 `{itemN: value}`、数组和旧对象结构提供显式迁移/读取规则；本单真实文本仍在快照中，修复后可安全重新生成 PDF，不应手工改写为 `item1` 或丢弃原值。
7. **补充端到端测试。** 覆盖“车钥匙1把、行驶证1本”和全部车况状态从 Field 填写、API 保存、客户确认到 PDF 可见文本的完整链路，并断言 PDF 不包含 `item1` 等内部键。

### 建议验收口径

- Field 页面所有 PDF 核心车况项目都有明确输入项，必填状态可被提交门禁校验。
- Portal 客户确认页与最终 PDF 的项目名称、状态、数量、单位和备注一致。
- “车钥匙1把”与“行驶证1本”分别显示在正确类别，不重复、不混合、不显示内部键。
- 未检查项目不得静默显示 `-`；应明确显示“未检查”并阻止提交，或按业务规则显示“无此配置/不适用”。
- 客户确认后生成的 PDF 内容绑定该次确认快照，后续字段变化不能静默改变已确认内容。
