# Portal 权益页面重设计

日期：2026-08-09

状态：已完成逐项设计确认，待书面审阅

## 1. 背景

当前 Portal“我的权益”页面在手机端已经由横向表格改为卡片，但卡片之间缺少清晰的类型分组和期次层级，初始额度、已核销额度与当前可用额度也没有形成直观对照。随着同一订单逐月发放权益，用户难以快速判断：

1. 自己当前拥有哪一类权益；
2. 当前期次还有多少可用额度；
3. 同一类权益的近期期次和历史期次；
4. 当前类型对应的核销明细。

本次重设计只重新组织 Portal 权益页面现有数据，不改变权益发放、核销、状态流转或额度计算逻辑。

## 2. 范围说明

### 2.1 本轮范围

- Portal“我的权益”页面的信息架构与响应式 UI；
- 按权益类型组织余额卡片和核销明细；
- 期次分类和排序；
- 数值型、文本型权益卡片；
- 可用、已用尽、已过期、已取消的视觉状态；
- 自动补取现有分页接口的后续页；
- 加载、空状态、失败重试和登录失效处理；
- 360px、390px、768px 和桌面宽度验收。

### 2.2 明确不在本轮范围

- 数据库结构调整；
- 新增或修改权益业务 API；
- 权益发放、月度续发、核销和回退规则；
- 后台管理端权益页面；
- 附件上传、历史文件名修复或部署流程调整。

在当前 staging 镜像 `Staging-20260809-9d12f7e` 下，中文附件名上传已重新验收通过。该结论仅作为范围排除依据，不在本设计中追加附件相关改造。

## 3. 设计目标

1. 用户进入页面后，能够先按类型找到权益，再按期次查看卡片。
2. 每张数值型卡片突出“当前可用额度”，同时清楚展示初始额度与已核销额度。
3. 当前期始终优先，未来期和历史期按距离当前日期由近到远排列。
4. 已过期、已取消的权益在视觉上弱化，但仍可查阅。
5. 当前类型的核销明细紧邻该类型余额，切换 Tab 时同步切换。
6. 手机端不出现横向页面溢出、逐字换行或额度与单位分离。
7. 不修改现有业务数据含义，不在前端重新推导账面余额。

## 4. 已确认方案

采用视觉方案 B“可用额度突出”：

- 当前可用额度是卡片的主视觉数字；
- 使用进度位于主数字下方；
- 初始额度和已核销额度作为进度对照；
- 卡片头部显示权益名称、期次、有效期和状态；
- 卡片底部显示发放来源等辅助信息。

相较三额度等权并列，方案 B 更符合用户首先确认“现在还能用多少”的任务。相较期次时间线，方案 B 对不同单位和文本型权益的兼容性更好。

## 5. 页面信息架构

页面从上到下分为四层：

1. 页面导航：返回 Portal；
2. 页面标题：“我的权益”和简短说明；
3. 权益类型区：固定三类 Tab 及各类记录数；
4. 当前 Tab 内容：
   - 权益卡片列表；
   - 当前类型的核销明细。

固定 Tab 顺序为：

1. 服务权益；
2. 补能权益；
3. 里程权益。

即使某类没有数据，也保留对应 Tab，并显示“暂无该类型权益”。Tab 数量统计该类型下全部状态的权益卡片。稳定的 Tab 位置比按数据动态隐藏更容易形成使用记忆。

## 6. Tab 默认定位

首次进入页面时：

1. 按固定 Tab 顺序查找包含“当前可用权益”的第一个类型；
2. 若不存在当前可用权益，则查找第一个包含任意权益记录的类型；
3. 若所有类型均无记录，则定位到“服务权益”。

“当前可用权益”同时满足：

- 期次属于当前期；
- 状态为 `ACTIVE`。

本轮不增加跨会话记忆，不在浏览器存储用户上次选择，以保持行为可预测并避免引入额外状态。

## 7. 期次分类与排序

### 7.1 业务日期

以北京时间当天的自然日判断期次，不使用浏览器所在地时区。

### 7.2 期次分类

对每条权益：

- 当前期：开始日不晚于今天，且结束日为空或不早于今天；
- 未来期：开始日晚于今天；
- 历史期：结束日早于今天。

分类只描述日期位置，卡片是否置灰仍由权益状态决定。

### 7.3 排序规则

同一类型内按以下分组依次排列：

1. 当前期；
2. 未来期；
3. 历史期。

组内排序：

- 当前期：开始日倒序；
- 未来期：开始日正序；
- 历史期：结束日倒序；
- 日期相同时，以权益编号升序作为稳定排序键。

因此页面顺序稳定表达“当前 → 最近未来 → 最近历史 → 更早历史”。

## 8. 权益卡片

### 8.1 卡片头部

显示：

- 权益名称；
- 期次标签；
- 有效期；
- 状态标签。

期次标签以当前 Tab 内排序后的日期为依据，优先显示“当前期”；其他卡片显示有效期，不新增数据库期次编号。

### 8.2 数值型权益

适用于 `KM`、`KWH`、`TIMES` 和 `ITEM`：

- 主数字：`remainingAmount`，标签“当前可用”；
- 初始额度：`totalAmount`；
- 已核销额度：`usedAmount`；
- 单位沿用现有单位映射。

展示值直接使用接口字段，不通过“初始减已核销”重新计算当前可用，避免小数和业务修正造成差异。

进度仅用于视觉表达：

- 初始额度大于 0 时，进度为“已核销 ÷ 初始额度”；
- 将视觉进度限制在 0% 至 100%；
- 状态为 `EXHAUSTED` 时，视觉进度固定为 100%；
- 初始额度为空或不大于 0 时不显示进度条；
- 进度不参与任何业务判断或接口提交。

### 8.3 文本型权益

`TEXT` 权益无法表达数值额度，保持相同卡片层级但不显示进度条：

- 初始额度：已发放；
- 已核销：不适用；
- 当前可用：状态为 `ACTIVE` 时显示“可使用”，其他状态显示“不可用”。

### 8.4 辅助信息

卡片底部显示：

- 发放来源；
- 必要时显示权益编号，作为异常排查和客服沟通依据。

长编号可以换行；额度数字与单位作为一个视觉整体，不允许逐字拆分。

## 9. 状态视觉

状态规则：

| 状态        | 标签   | 卡片视觉                                       |
| ----------- | ------ | ---------------------------------------------- |
| `ACTIVE`    | 可用   | 正常卡片，主数字和进度使用强调色               |
| `EXHAUSTED` | 已用尽 | 不整体置灰，进度显示 100%，当前可用显示 0      |
| `EXPIRED`   | 已过期 | 整张卡片使用灰色背景、灰色文字和中性状态标签   |
| `CANCELLED` | 已取消 | 与已过期相同的失效视觉，并保留“已取消”状态语义 |

日期分类和状态可能暂时不一致，例如当前日期范围内的卡片已取消。此时卡片仍位于当前期分组，但按“已取消”置灰，忠实展示后端状态。

## 10. 核销明细

核销明细位于当前 Tab 的卡片列表下方，标题包含当前类型名称，例如“补能权益核销明细”。

规则：

- 仅显示与当前 Tab 相同的 `entitlementType`；
- 按发生时间倒序；
- 手机端使用紧凑记录卡；
- 桌面端保留表格；
- 显示权益名称、核销额度、状态、来源、发生时间和使用编号；
- 长使用编号允许在安全位置换行；
- 当前类型没有核销记录时显示独立空状态。

本轮不增加“点击某张权益卡片后只筛选该卡片核销记录”的二级交互。类型级过滤足以满足已确认的追溯需求，也避免让卡片产生隐藏选择状态。

## 11. 数据加载与分页

沿用现有接口：

- `GET /portal/entitlements`；
- `GET /portal/entitlements/usages`。

现有接口默认每页 20 条，单次读取会导致 Tab 计数、历史卡片或核销记录不完整。本轮在前端增加通用的 Portal 分页补取逻辑：

1. 首次请求使用 `pageSize=100`；
2. 读取响应中的 `total` 和 `pageSize`；
3. 总数超过已取条数时继续请求后续页；
4. 合并后再进行类型分组和排序；
5. 保留 URL 中现有的 `orderId` 过滤条件。

不在 API 中新增 `entitlementType` 参数，避免为纯展示重组扩大后端契约。

权益余额与核销记录并行加载。只有两类数据都成功后才进入完整展示态，避免余额与核销明细来自不同读取状态。

## 12. 加载、错误与空状态

页面状态：

- 加载中：保留标题和 Tab 骨架，内容区显示加载状态；
- 成功：计算默认 Tab 并展示完整内容；
- 空数据：保留三个 Tab，每个 Tab 显示对应空状态；
- 普通失败：内容区显示错误信息和“重新加载”按钮；
- `401`：沿用现有逻辑跳转 Portal 登录页，并携带返回地址。

重试重新读取余额和核销明细，不复用失败前的半套数据。

## 13. 响应式布局

### 13.1 手机端

在 `<= 768px`：

- Tab 可在容器内均分宽度，标签和计数保持可读；
- 每行一张权益卡片；
- 核销明细使用记录卡；
- 页面不产生横向滚动；
- 名称可自然换行，编号使用 `overflow-wrap`；
- 数字和单位保持为一个展示组。

### 13.2 桌面端

在 `> 768px`：

- 权益卡片使用两列网格；
- 排列顺序从左到右、从上到下；
- 核销明细使用现有桌面表格；
- 页面主体继续限制在现有最大宽度内。

## 14. 组件边界

建议拆分为以下职责：

### 14.1 页面数据容器

负责：

- 读取 `orderId`；
- 并行加载全部权益和核销记录；
- 维护加载、失败和重试状态；
- 处理 `401` 跳转；
- 将完整数据交给展示组件。

### 14.2 纯数据投影

提供可独立测试的纯函数：

- 按类型分组；
- 判断当前、未来、历史期；
- 按已确认规则稳定排序；
- 选择默认 Tab；
- 计算受限的视觉进度。

### 14.3 权益类型视图

负责：

- Tab 与数量；
- 当前 Tab 状态；
- 卡片网格；
- 当前类型的核销明细；
- 空状态。

### 14.4 权益卡片

只消费一条 `PortalEntitlementGrant` 和已计算的展示模型，不发起网络请求，不修改业务数据。

现有 `PortalEntitlementUsageRecords` 可继续复用其桌面表格与手机卡片能力，但由当前 Tab 传入已过滤的记录。

## 15. 可访问性

- Tab 使用具备键盘交互和选中语义的标准组件；
- 状态不能只依赖颜色，必须保留文字标签；
- 置灰卡片仍保持足够对比度；
- 进度条提供可读的百分比语义；
- 加载和错误状态具有明确文本；
- 交互控件保留可见焦点样式。

## 16. 测试策略

### 16.1 纯函数测试

- 北京时间期次边界；
- 当前、未来、历史分组；
- 三组排序和同日期稳定排序；
- 默认 Tab 定位；
- 进度小于 0、大于 100、初始额度为空或为 0；
- 文本型权益展示模型。

### 16.2 组件测试

- 固定三类 Tab 和记录数；
- 切换 Tab 后卡片与核销明细同步过滤；
- 方案 B 的当前可用、初始额度、已核销额度；
- 四种状态的类名和文字；
- 文本型权益不显示进度条；
- 空状态、加载状态和错误重试；
- 长名称、长编号所需 CSS 契约。

### 16.3 分页测试

- 总数不超过 100 时只请求一页；
- 总数超过 100 时补取后续页；
- 保留 `orderId`；
- 任一后续页失败时进入完整失败态，不展示不完整分组。

### 16.4 回归门禁

- Web 相关 Vitest；
- Web TypeScript 类型检查；
- Web lint；
- 生产构建；
- 现有 Portal 权益与账单记录测试保持通过。

## 17. 人工验收

在 staging 使用具有多种权益和多个期次的订单，验证：

1. 三个固定 Tab、数量和默认定位正确；
2. 当前期、未来期、历史期顺序正确；
3. 方案 B 主数字、进度、初始额度和已核销额度直观；
4. 已过期、已取消置灰，已用尽不整体置灰；
5. 文本型权益显示“已发放／不适用／可使用或不可用”；
6. 切换 Tab 后核销明细同步变化；
7. 360px、390px、768px 和桌面宽度无页面横向溢出；
8. 长权益名称、额度单位和长使用编号可读；
9. 刷新和失败重试行为正确；
10. 账面额度、权益状态和核销记录内容与改造前接口数据一致。

## 18. 完成标准

满足以下条件即视为本轮完成：

1. 页面采用已确认的方案 B；
2. 类型、期次、状态、额度和核销明细遵循本设计；
3. 不修改数据库和现有权益 API 契约；
4. 自动补取分页数据，Tab 计数与内容完整；
5. 自动化测试、类型检查、lint 和构建通过；
6. 四种验收宽度通过人工检查；
7. staging 人工验收确认布局清晰且业务数据未改变。
