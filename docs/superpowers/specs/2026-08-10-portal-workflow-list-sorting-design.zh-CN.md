# Portal 流程列表默认排序优化设计

日期：2026-08-10

状态：已审核通过，允许进入实施计划

## 1. 背景

当前 Portal 多数流程列表沿用“创建时间倒序”或单一业务日期排序。该方式能够表达历史时间线，但不能稳定突出客户当前需要处理的事项。

已确认的直接问题是“我的账单”中已支付账单可能排在待支付账单之前。审计同时发现，申请、订单、合同、支付单、服务工单、车辆交付复核和续租列表也缺少统一的待办优先规则。

本次调整只优化默认排列，不改变业务流程、操作入口、状态流转或数据含义。

当前 Golden Path 验收因微信模板处于审核期而挂起。该事项与本设计相互独立，不纳入本轮实施和验收范围。

## 2. 设计目标

1. 客户进入流程列表后，首先看到当前需要自己操作的记录。
2. 平台处理中记录位于客户待办之后，已完成、已取消等历史记录统一沉底。
3. “我的账单”严格遵循已确认的业务优先级。
4. 排序在整个查询结果中成立，不能只重排当前分页。
5. 保持现有筛选、分页、鉴权、响应字段和页面操作方式不变。
6. 不引入数据库迁移，不增加用户操作复杂度。

## 3. 已确认方案

采用服务端“优先级状态桶 + 全局分页”方案。

- 服务端基于实际业务事实对记录分组并排序；
- 有分页的接口按优先级桶计算全局分页；
- 无分页的接口在服务层使用统一分类器和稳定比较器排序；
- Portal 前端按接口返回顺序展示，不做当前页二次排序；
- 不使用数据库特定的原生 SQL；
- 不新增展示优先级字段或其他冗余数据。

未采用以下方案：

- 前端当前页排序：无法保证跨页全局顺序；
- 数据库增加展示优先级：需要迁移且产生长期维护成本，本轮没有必要。

## 4. 范围

### 4.1 本轮调整

- Portal 申请列表；
- Portal 订单列表；
- Portal 合同列表；
- Portal 我的账单；
- Portal 支付单列表；
- Portal 服务工单列表；
- Portal 车辆交付复核列表；
- Portal 续租列表。

### 4.2 保持现状

以下列表本身属于时间线、配置顺序或已有独立业务排序，不套用通用待办优先规则：

- 消息通知：继续严格按时间倒序，未读只通过角标和样式突出；
- 押金流水、支付流水、账单核销记录、自动扣款尝试及其他历史记录：继续按发生时间倒序；
- 商品目录：继续使用商品配置和业务相关性排序；
- 材料清单：继续使用材料类型和要求顺序；
- 权益列表：保留当前期、未来期、历史期及类型 Tab 的专用排序；
- 里程复核：保留逾期优先和计划时间排序。

### 4.3 明确不在本轮范围

- 新增历史记录 Tab、筛选项、按钮或操作入口；
- 修改状态机、支付、签署、交付、续租或账务逻辑；
- 修改公开 API 响应结构；
- 数据库结构及迁移；
- Admin 后台列表排序；
- 微信模板和 Golden Path 验收。

## 5. 通用排序模型

流程记录分为三级：

1. 客户待操作；
2. 平台处理中；
3. 已完成或历史记录。

同一分组内：

1. 存在明确业务期限时，按期限升序；
2. 没有期限时，按 `updatedAt` 倒序；
3. 前述值相同时，按 `createdAt` 倒序；
4. 仍相同时，按记录 `id` 升序，保证稳定顺序。

终态记录不再使用过期的业务期限参与排序，统一按最近更新时间倒序。

分类优先读取现有 `nextAction`、可支付余额、可签任务、可提交复核等真实业务事实。失败或异常记录如果没有客户可执行入口，不得错误进入客户待操作组。

## 6. 账单排序

“我的账单”固定顺序为：

1. `OVERDUE`：已逾期；
2. `PARTIALLY_PAID`：部分支付；
3. `PENDING`：待支付；
4. `PAID`：已支付；
5. `CANCELLED`：已取消。

同一状态内：

- 按 `dueDate` 升序；
- 因此逾期账单中逾期最久者优先，未到期账单中最近到期者优先；
- 到期日相同后按 `updatedAt` 倒序、`createdAt` 倒序和 `id` 升序。

当请求带 `billStatus` 或其他现有筛选条件时，只在筛选结果内部应用组内排序，不改变筛选语义。

## 7. 各流程模块分类

### 7.1 申请

客户待操作：

- 补充材料；
- 确认最终方案；
- 进入合同签署；
- 进入支付；
- 提交里程复核。

平台处理中：

- 审核中；
- 等待订单创建；
- 等待交付；
- 其他非终态且当前没有客户操作入口的状态。

历史记录：

- 已拒绝；
- 已取消；
- 关联订单已经完成、终止、取消或拒绝的申请。

分类应复用现有 Portal 下一步动作推导，避免再维护一套仅依赖 `ApplicationStatus` 的不完整规则。

### 7.2 订单

客户待操作：

- `PENDING_CUSTOMER_CONFIRMATION`；
- `PENDING_SIGN` 或存在可签但尚未完成的合同；
- `PENDING_PAYMENT` 或存在待付余额；
- 存在待提交或被退回的里程复核。

平台处理中：

- `PENDING_REVIEW`、`PENDING_CONTRACT`、`PENDING_VEHICLE`、`PENDING_DELIVERY`；
- `ACTIVE`、`SUSPENDED`、`PENDING_RETURN` 中没有客户操作入口的记录；
- 其他非终态记录。

历史记录：

- `TERMINATED`、`COMPLETED`、`CANCELLED`、`REJECTED`。

### 7.3 合同

客户待操作：

- 当前电子签任务为 `CREATED`、`WAITING_CUSTOMER` 或 `SIGNING`，且 Portal 可以继续签署。

平台处理中：

- 合同草稿、生成中、平台盖章或归档中；
- 当前没有客户可执行入口、需要平台处理的失败或异常任务。

历史记录：

- 已签署、已归档、已终止、已取消。

### 7.4 支付单

客户待操作：

- `CREATED`；
- `PENDING` 且仍可继续支付。

历史记录：

- `PAID`、`FAILED`、`CLOSED`、`CANCELLED`、`EXPIRED`。

支付单当前没有独立的平台处理中分组。自动扣款尝试继续作为历史时间线处理，不混入本规则。

### 7.5 服务工单

客户待操作：

- `WAITING_CUSTOMER`。

平台处理中：

- `SUBMITTED`、`ACCEPTED`、`IN_PROGRESS`。

历史记录：

- `RESOLVED`、`CLOSED`、`CANCELLED`。

### 7.6 车辆交付复核

客户待操作：

- 工单为 `EVIDENCE_SUBMITTED` 或 `CUSTOMER_REVIEWING`；
- 关联交接电子签为 `PENDING_CUSTOMER_SIGNATURE`。

平台处理中：

- 客户确认或提出异议后等待后台处理；
- 客户已签后等待平台盖章；
- 运营复核中的其他可见状态。

历史记录：

- `FIELD_COMPLETED`、`OPS_REVIEWED`；
- 关联交接文件已经 `SIGNED` 或 `ARCHIVED`。

### 7.7 续租

客户待操作：

- 选择续租或到期；
- 确认续租报价；
- 签署协议或支付；
- 已确认到期并需要准备还车。

平台处理中：

- 等待报价；
- 等待协议；
- 等待续租生效；
- 需要平台处理的异常状态。

历史记录：

- 续租已完成；
- 已到期；
- 已取消。

续租分类应以现有 `considerationNextAction` 和关联变更单状态为主要依据。

## 8. 期限来源

客户待办存在多个候选期限时，取最早的有效期限作为排序期限：

- 账单：`dueDate`；
- 订单：待付账单到期日、签署链接有效期、里程提交截止时间中的最早值；
- 合同：电子签链接有效期；
- 支付单：支付单过期时间；
- 车辆交付复核：交付预约时间；
- 续租：续租办理完成期限；
- 申请、服务工单：当前没有明确期限时使用 `updatedAt`。

已经过期但仍可操作的待办仍留在客户待操作组，并按期限升序排在更晚期限之前。

## 9. 全局分页算法

账单、订单、支付单和服务工单是分页接口，必须保证跨页全局顺序。

每次请求按以下步骤执行：

1. 在原有客户归属、软删除和请求筛选条件上，构造各优先级桶的查询条件；
2. 统计各桶记录数；
3. 根据全局 `skip` 与 `take` 计算当前页与各桶的交集；
4. 只查询与当前页相交的桶，并应用该桶内部排序；
5. 按桶优先级拼接结果；
6. 返回现有 `items/page/pageSize/total` 结构。

统计与本页记录查询应在同一只读事务中完成，减少一次请求内状态变化导致的重复或漏项。

实现一个可独立测试的分页规划工具，输入各桶数量、`skip`、`take`，输出需要查询的桶及各桶内偏移和数量。工具不感知具体 Prisma 模型或业务状态。

当请求已经按单一主状态筛选时，仍需保留可支付余额、可签任务、里程待办等动态事实分类。只有能够证明筛选结果全部属于同一优先级桶时，才可直接执行组内排序；返回契约始终保持一致。

### 9.1 订单非终态工作集例外

Prisma 7.8 对一对多关联排序只支持关系计数，不能直接按待付账单、里程复核和签署任务中的最早期限进行关联聚合排序。订单列表因此采用已经确认的窄范围例外：

1. 只读取当前客户符合请求筛选条件的全部非终态订单及排序所需关联数据；
2. 在服务层提取真实下一步动作和最早期限，完成客户待操作与平台处理中两组排序；
3. 根据全局 `skip/take` 截取非终态结果；
4. 若本页还需要历史记录，再按剩余偏移和数量查询终态订单；
5. 已完成、已终止、已取消和已拒绝等历史订单始终由数据库分页，不加载完整历史。

该例外不使用原生 SQL，不修改数据库，也不改变接口契约。它加载的是客户当前仍在履行或处理的工作集，而不是完整订单历史。

为防止未来单客户非终态订单数量异常增长，当一次请求读取的非终态订单超过 100 条时，记录代码为 `PORTAL_ORDER_ACTIVE_SET_LARGE` 的结构化告警；告警只包含数量和分页参数，不记录客户姓名、手机号、证件号等个人信息。该阈值不阻断查询，也不改变返回结果。

## 10. 无分页列表

申请、合同、车辆交付复核和续租接口当前返回客户范围内的完整列表。本轮保持查询范围不变：

1. 读取现有记录及分类所需关联数据；
2. 提取优先级、期限、更新时间、创建时间和 ID；
3. 使用纯函数稳定排序；
4. 映射并返回原有 DTO。

不得为了排序新增客户端全量补页逻辑。

## 11. API 与数据兼容

- 保持现有路由、查询参数、默认页大小和最大页大小；
- 保持现有响应字段、字段类型和总数语义；
- 保持客户归属、软删除和其他鉴权条件；
- 保持现有状态筛选的准确性；
- 不新增数据库字段、索引或迁移；
- 不写审计日志，因为本轮只是只读展示顺序变化，不修改业务数据。

## 12. 前端边界

Portal 页面继续消费现有接口并按返回顺序渲染：

- 不增加 Tab 或额外筛选；
- 不增加客户需要理解的新概念；
- 不在前端对当前页重新排序；
- 不改变卡片、按钮和详情入口；
- 不改变空状态、加载状态或错误处理。

因此实际操作界面不会变复杂，变化仅体现在更符合任务优先级的默认排列。

## 13. 测试策略

### 13.1 纯函数测试

- 每个模块的客户待办、平台处理中和历史边界；
- 真实业务事实优先于单一主状态；
- 有期限和无期限记录的组内排序；
- 相同期限、更新时间和创建时间下的稳定 ID 兜底；
- 异常但无客户操作入口的记录不进入客户待办组。

### 13.2 账单测试

- `OVERDUE -> PARTIALLY_PAID -> PENDING -> PAID -> CANCELLED`；
- 同状态按 `dueDate` 升序；
- 逾期最久和最近到期边界；
- 状态筛选后只应用组内排序。

### 13.3 分页测试

- 一页完全落在一个桶内；
- 一页跨越两个或多个桶；
- 前一个桶数量恰好等于页边界；
- 空桶和空列表；
- 最后一页不足 `pageSize`；
- 不重复、不漏项；
- `total/page/pageSize` 与现有契约一致。

### 13.4 接口回归

- 客户数据隔离；
- 现有状态和业务类型筛选；
- 消息、流水、核销、自动扣款、商品、材料、权益、里程复核顺序不变；
- 相关 API 和 Web 类型检查、lint、测试；
- Prisma validate 和迁移状态检查，预期无迁移。

## 14. 人工验收

在 staging 使用同时具备进行中和历史数据的客户账号验证：

1. “我的账单”依次展示已逾期、部分支付、待支付、已支付和已取消；
2. 待支付类账单在历史账单之前；
3. 同状态账单的到期日顺序正确；
4. 申请、订单、合同、支付单、服务工单、交付复核和续租均先展示客户待办；
5. 平台处理中记录位于待办之后；
6. 已完成、已取消等记录仍可查看但统一沉底；
7. 状态筛选结果准确；
8. 跨页浏览无重复或漏项；
9. 页面按钮、详情入口和操作路径未变化；
10. 消息和各类历史时间线仍保持原有时间顺序。

## 15. 风险与回滚

不同分页请求之间若业务状态实时变化，记录允许根据最新状态移动位置。这属于实时任务优先级的预期行为。单次请求内部通过稳定排序和只读事务保证一致性。

本轮不改数据库和业务数据。若需要回滚，只需回退排序分类、分页规划和对应服务调用，不需要数据库回滚或数据修复。

## 16. 完成标准

1. 所有范围内 Portal 流程列表符合本设计的优先级；
2. 分页排序在完整结果集上成立；
3. 现有筛选、鉴权、响应契约和 UI 操作保持不变；
4. 没有数据库迁移；
5. 自动化测试和质量门禁通过；
6. staging 人工验收通过。
