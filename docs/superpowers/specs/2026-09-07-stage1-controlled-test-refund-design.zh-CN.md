# Stage 1 专用测试支付原路退款窄范围方案

状态：**待复审。仅获准编写并独立提交方案与计划；未批准代码、商户操作、付款、退款或账务写入。** 核查基线为 `f798f5bdacfa56b074a30d7357f30616fb8ebec7`，不是已冻结 RC。本文不修改已经批准的 [混合环境 Runbook](../../runbooks/stage1-golden-path-production-acceptance.zh-CN.md)。

## 1. 决策与范围

**推荐先验证并有条件采用 A：既有微信商户平台人工原路退款 + Staging 只读核对 + 既有受控财务凭证及日终对账。** 本次只提交 A 的实施计划，不新增退款子系统，也不把“代码缺退款接口”推导成必须接入 API。条件尚未实测，所以不声称 A 已可执行。

目标仅是本轮专用测试支付的资金退回、结果确认与账务对账；结果可记为“人工渠道退款及人工核对通过”，**不能记为平台自动退款、平台退款状态同步或完整保证金退款产品通过**。

固定范围：Staging 应用/API/数据库/队列/对象存储 + 生产微信直连商户 + 已批准专用测试付款人。每个原支付单只允许一次全额、CNY、无优惠券/分账/多付款人/历史退款的原路退款；每笔和整轮金额均受独立批准上限约束。A 进一步只接受按正常风控/押金规则已合法批准免押、原付款只含专用测试租金的样本，不处理保证金余额。需要部分退款、差额退款、异常退款、其他收款账户或服务商模式时停止，不现场扩大。

不包含通用售后、争议退款、法务处置、完整保证金产品、新财务总账、生产业务数据库、普通客户及运营车辆。签署、付款、退款、通知分别批准。候选证明、最终镜像双链、线上隔离、通知门槛、B4–B6 仍独立；B3 由原线程据 Task 3S 证据判定，不重复 fresh；Task 30、旧 Task 6/29R/I 及 stash 继续冻结。已批准的本地 B/R 工作不因本文暂停。

### 2.2 官方依据（2026-09-07 查阅公开文档，未登录商户）

微信官方 [订单退款产品介绍](https://pay.wechatpay.cn/doc/v3/merchant/4013071001)列有商户平台手工退款与 API 两种入口，因此人工路径具有产品依据；特定商户是否有权限、是否允许该订单退款仍需实测。

[申请退款](https://pay.wechatpay.cn/doc/v3/merchant/4013071036)区分申请受理与最终结果，并规定原交易、金额及商户退款单号。[开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)要求通过结果通知或查询确定终态。本文采用人工查询，不据此承诺当前平台有查询接口。

[退款常见问题](https://pay.wechatpay.cn/doc/v3/merchant/4013071200)说明商户后台配置的退款通知可能是 v2 XML，且商户资金先扣出并不等于用户退款成功。因此不能复用现有支付 callback，不能用资金支出行、申请成功页或到账提示单独判定退款成功。

上述文档不证明实际 UI 支持填写自定义退款单号、不证明特定租户隔离、不替代权限读回或批准。真实窗口前须重新核对官方规则与实际页面，差异导致本计划不适用时停止。

## 3. A 的付款前可行性门槛

以下条件必须在**真实付款之前**由只读观察和无资金桌面演练证明。不能先支付，再以“钱已付”要求临时扩权。观察需要外部只读许可，本文不授予该许可。

1. 已有商户与本轮支付商户完全相同，操作者有精确单笔退款权限，独立复核人可查询原订单、退款列表、退款结果及所需回单；没有批量退款授权。实际页面可显示/导出第 4 节所需字段，完整权限与商户观察进入受控档案。
2. 该商户后台的退款通知行为已经只读核实。A **不新增退款接收器、不修改全局 callback、不把 XML 发到支付 JSON callback**。仅在本次退款实际不向应用推送通知，并经独立批准采用商户查询作为结果来源时，申请“退款 notify 不适用”的窄口径；这是对旧 Runbook 无条件 notify 描述的待批准修订，不是直接豁免。如果存在全局通知、未知通知目标或生产应用会收到该测试退款，A 不合格，保持原配置并停止。
3. 既有财务负责人明确接受本轮测试退款通过既有受控财务系统/档案处理；在付款前指定该次实际记账凭证类型、责任人、复核人、档案位置、权限及处理时限。不是只写一个“差异说明”；如果需要冲减应收、改变租金义务、释放押金负债或平台净额自动更新，必须已有合适、另获批准的业务处置路径，否则 A 不合格。
4. 一次操作只有一位执行人，其他有退款权的人员/自动任务已对**精确测试原交易**确认不并发操作；交接须查询最新原单与全部退款记录。现有人工变更记录具备独占责任与版本历史；若不能排除第二执行者或证据覆盖，停止，不临时造分布式锁工具。
5. 已明确单次付款上限、单次退款上限、整轮累计上限、无优惠/分账的限制、可退款期限、资金可用性、测试付款来源及失败联系路径。将来每笔付款金额必须同时不超过付款/退款单次上限及两者剩余额度，保证按本方案全额收尾。
6. 已有私有受控财务保管位置及独立读回流程可用，覆盖批准、商户读回、平台观察、财务凭证及日终复核；原件不进 public Git/Actions，不读取普通客户明细。若商户只能提供整商户账单，必须由已有授权财务人在其原有受控边界提取该测试交易行并证明来源；本计划不授权 agent 下载整商户账单或接触普通客户记录。
7. 候选身份与全部独立运行门槛按已批准主线满足；特别是总预检要求通知开启，未独立批准通知时仍 `STOP`。退款路径可用不代表可付款。

此外，样本必须已有正常审批的免押事实，实际付款分摊中没有押金；不得为走 A 调低押金、改风险等级或伪造零押。含押金的本轮付款不能以“只退租金”冒充全部资金收尾，A 对该样本不适用。专用 Staging 样本不得进入生产经营财务报表、实际营运或真实权益消费；实际现金流仍须在既有真实财务体系依法记账。退款后继续保留的 ACTIVE 租约/权益/月租计划必须纳入现有精确样本暂停/后续正常处置批准，不能让它成为新的自动对外收款或重复退款来源。没有合格样本不触发另造免押夹具或数据写入。

缺权限、证据字段、通知隔离、财务处置或保管等任一项时登记具体失败条件；不将方案 B 作为自动 fallback。尚未实测的条件保持未通过，不能以当前没有原支付单为由伪造探测退款。

## 5. 金额、重复与 UNKNOWN

- 金额统一整数分；商户页面/账单若以元显示，以十进制精确换算并由两人复核，禁止浮点舍入。原实付为 `P`，既有成功退款为 `S`，已受理/处理中占用为 `U`，本次为 `R`：至少满足 `0 < R <= P-S-U` 与全部批准上限；无法确定 U 则停止。付款分摊含押金即拒绝 A，不把退款数值正确等同于押金负债已正确处理。
- A 更严格限定 `S=0、U=0、R=P`，原单无任何未决退款或其他操作者申请；只支持一次全额退回。出现历史退款、优惠分摊或混币种时不现场计算新方案。
- 点击退款前先将操作记录置为人工“已占用、待单次提交”，由复核人确认；提交一次后禁止刷新重提、重复点击或换执行人再申请。浏览器断线/超时/会话丢失即 UNKNOWN，只查询原交易退款列表，不生成新申请。无法证明零副作用时，空列表也不能直接放行重提。
- 取得退款单号后只查询该单，必要时按原交易列表辅助定位；重复观察/重复回单按真实退款号归为同一事实，不重复计账。状态矛盾、同号不同金额/原单、第二笔退款均停止并升级；不覆盖旧证据。
- `PROCESSING` 是渠道未完成；`UNKNOWN` 是观察不充分，两者不是失败即重试。达到批准窗口/查询时限即停止新写并安排独立只读跟进批准；不存在后台自动重试。
- `CLOSED/ABNORMAL` 不算成功，本方案不启用异常退款、改收款账户或新退款单重做。渠道成功但财务未核对时，资金事实保留、对账门禁仍未通过。
- A 不安装/消费退款回调。对本应无通知的退款若观察到通知，立即停止并保留来源，由已有获准事故流程处理；不能 ack 为成功、送现有付款 callback、用重复通知触发账务。B 若另行设计，必须测试验签/解密、重复和乱序通知，但本文不授予其入口。

## 6. 成功后的账务处理与证据界限

原 `PaymentRecord.CONFIRMED` 表示曾到账、`PaymentWriteOff` 表示当时的核销；退款发生不允许抹掉这段历史。A 对平台业务数据全程只读，不调用 `refund-deposit`、不写负收款、不改 bill/Payment/Closure/Journey 状态，也不声称已经将平台余额冲回。

财务负责人必须按第 3 节**预先批准的现有记账方法**为真实退款出具实际凭证并经第二人复核；渠道 `SUCCESS` 后才计入已成功退款额，不能在“受理”时把清算过渡扣款认作已退给用户。本文不指定新的会计科目或虚构收入冲销/费用补贴；不存在该方法或不能依法依规处理该具体付款性质时，A 失败并停止后续付款。

逐原交易同时呈现三组数：平台历史收款/原核销，渠道成功退款，财务入账与日终资金变动。客户现金净额为 `P-S`（其中 S 仅含渠道确认成功的退款）；全额退后为零，但不等同于平台应收/押金负债为零。手续费、返还手续费、结算日期差异按实际账单单列，不能用简单商户净支出代替退款额。

所有差异须分类为“时间差待后续账单”“已凭证解释”“未解决”；前两者也只有证据齐全且所需财务凭证已生效才可按批准标准关闭。账单尚未生成或无法取得原路成功证据时保持待对账，不把当天窗口结束当通过。受控档案至少保留核查原件、来源/观察时间、内容摘要、原单关联、操作者及复核引用；180 日为最低保留要求，已有财务规定更长时从其规定，位置/权限/保留策略须实际读回，不虚构存储 receipt。

若退回测试款后订单仍在租、押金负债或其他履约责任未结束，应如实列为独立未完成事项，按已批准 B/R/A 正常流程处理；不能凭现金退回把 B6/合同履行闭环签掉，也不能让该样本继续发生未获批准的自动扣款/退款。精确样本的停止/恢复按 Runbook 已预批准边界执行，不能为了本方案停普通客户。

## 8. 可判定的验收门槛

1. 静态：精确文件范围、Markdown 格式、链接、staged diff；RF0 登记改动另过现有 Schema/contract/discovery 离线门禁，不运行产品/DB 测试冒充退款验证。
2. 无资金桌面演练：正确原单/全额/最终成功链可闭合；错误商户、错误原单、超额、有未决退款、重复提交、丢响应、冲突结果、账单未出、财务凭证缺失、全局通知、通知未批等均拒绝。此类演练只验证人工作业规则，不是供应商接口测试。
3. 实际执行：付款前路线可用，精确候选及外部动作独立批准；原支付完成后再次原单核验并独立批准退款；只一次商户申请，同单结果确认、实际财务凭证、日终对账与独立保管读回全部满足。每个原支付单单独判定，任何 UNKNOWN/缺件不通过。
4. 最终报告明确“商户人工退款及人工核对通过/未通过”，并列出平台自动退款、业务净额同步未覆盖；`stage1.refund` 仍是必须外部验证，不改成 N/A。

## 9. A 失败时的唯一出口

记录失败条件、证据与所需能力，由用户决定是否提出 B 的窄范围变更；不能用本方案自动进入 B。缺商户权限、资金、候选证明或普通客户隔离时，接 API 也不是绕过手段。

若证据证明障碍仅为受控单笔申请、稳定退款身份或同单查询，则 B 的候选接口集仅考虑原交易查询、单笔退款申请和同单退款查询；现有商户回单/财务对账可继续复用。只有独立批准的通知策略要求消费回调时才考虑独立退款通知入口；不复用支付 callback，不新增通用售后。

B 不是本次实施计划的分支任务。提出 B 时必须先提交完整的精确产品文件、持久化事实/迁移、权限、幂等/并发/UNKNOWN/通知测试影响及审批申请；不得先向 `PaymentProvider` 增方法、把状态塞入 remark/通用 JSON，或在本计划授权下创建模型。**本稿不申请 B 的任何代码/模型/迁移/权限额度。**
