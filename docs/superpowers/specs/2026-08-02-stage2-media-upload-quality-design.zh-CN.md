# Stage 2 车辆环绕视频上传与清晰度保障设计

日期：2026-08-02
状态：已获业务设计批准，待实施计划确认
范围：Wave 2（STG2-004、STG2-005）

## 1. 背景与问题

Stage 2 现场交接验收暴露出两个独立但相互关联的问题：

1. 从相册选择约 191.6 MiB 的 `IMG_0203.mov` 后，页面提示“上传失败，请检查网络后重试”。应用层已经允许单个视频最大 300 MiB，但实际 Staging API Nginx 虚拟主机仍使用 20 MiB 请求体限制，导致请求在到达 API 前被 413 拒绝。
2. 移动端“现场录像”使用原生 `<input type="file" accept="video/*" capture="environment">`。微信/iOS WebView 决定实际录像参数，页面无法约束分辨率，验收样本仅为 480×360，不能形成有效车辆交接证据。

既有应用已经具备上传进度、取消、重试、300 MiB 前端限制、服务端媒体探测和关键帧生成能力。本轮不重写上传链路，而是在入口配置、交互入口和服务端证据质量三个边界上补齐约束。

## 2. 已确认业务决策

采用方案 B：

- 移动端取消网页内“现场录像”入口。
- 验车人员先使用手机系统相机，以 720p 或更高画质完成录像，再通过 Field 页面“从相册选择”上传。
- 服务端对车辆环绕视频执行最低 720p 清晰度门槛，以视频短边像素数不低于 720 为准。
- 低于门槛的视频不得作为新的车辆环绕视频证据入库。
- 照片“现场拍摄”入口保持不变。

选择该方案的原因是目标微信/iOS WebView 无法可靠控制原生文件输入的录像分辨率。继续保留该入口会制造“操作成功但证据不可用”的假成功。

## 3. 目标与非目标

### 3.1 目标

- 允许符合应用限制的接近 300 MiB 视频可靠通过 Staging 入口。
- 对 413 返回明确、可操作的错误说明，不再误报为网络故障。
- 杜绝通过网页内不可控入口生成新的低清车辆环绕视频。
- 服务端记录视频分辨率、帧率和码率，并对车辆环绕视频强制执行 720p 门槛。
- Field 和 Admin 可查看服务端探测到的实际视频分辨率。
- 保持历史证据和已归档交接单可读，不对已完成订单做追溯性阻断。

### 3.2 非目标

- 不实现 `getUserMedia`/`MediaRecorder` 网页内受控录像。
- 不修改照片清晰度规则。
- 不增加数据库表或 Prisma 迁移。
- 不修改 Wave 1 编排、短信、电子签或归档逻辑。
- 不处理 STG2-007 的 Field 验收字段和 PDF 内容映射；该问题属于 Wave 3。
- 本轮先发布 Staging，不修改 Production。

## 4. 端到端设计

### 4.1 Staging API 入口

仅调整 `staging-api.subauto.keybox.cloud` API 虚拟主机：

```nginx
client_max_body_size 320m;
client_body_timeout 1200s;
proxy_request_buffering off;
proxy_read_timeout 1200s;
proxy_send_timeout 1200s;
```

320 MiB 为 multipart 请求头和表单边界预留空间；业务层单文件上限继续保持 300 MiB。Admin/Web 虚拟主机继续维持 20 MiB，不扩大无关入口。

变更前保存带时间戳的 Nginx 配置备份；执行 `nginx -t` 成功后才 reload。发布后用 `nginx -T` 验证生效值。

### 4.2 Field 移动端入口

上传输入契约调整如下：

- PHOTO：继续提供“现场拍摄”和“从相册选择”。
- VIDEO：只提供“从相册选择”，不再生成 `capture="environment"` 的 `video-capture` 输入。
- PHOTO + VIDEO：保留一个相册/文件选择入口，允许选择符合当前证据项媒体类型的文件。

当证据项允许视频时，在选择入口附近展示固定提示：

> 请先使用手机系统相机以 720p 或更高画质录制完整车辆环绕视频，再从相册选择上传。单个视频不超过 300MB。

该提示不依赖 User-Agent 文案推断，桌面端也可显示简化版上限说明。

### 4.3 413 错误映射

XHR 收到 HTTP 413 时，不解析 Nginx HTML 错误页，也不回退为网络错误。统一展示：

> 文件过大，单个视频不得超过 300MB。若文件未超过限制，请联系管理员检查上传网关配置。

其他非 JSON 错误保持安全通用提示；网络断开、超时和用户取消继续使用现有独立文案。

### 4.4 服务端媒体探测

视频 `ffprobe` 增加读取：

- `width`
- `height`
- `avg_frame_rate`，无有效值时回退 `r_frame_rate`
- 流级 `bit_rate`，缺失时回退容器级 `bit_rate`

新上传视频的 JSON metadata 在现有 `artifactVersion: 1` 基础上增加：

```ts
videoWidthPx: number | null;
videoHeightPx: number | null;
videoFrameRate: number | null;
videoBitRateBps: number | null;
videoQualityStatus: "PASSED" | null;
```

不提升 `artifactVersion`，避免让历史 metadata 失效。帧率和码率仅作为诊断信息，不在本轮设置最低门槛；部分合法 MOV/MP4 不提供可靠码率时允许为 `null`。

### 4.5 清晰度门槛

仅对 `WALKAROUND_VIDEO` 类型执行：

```text
min(videoWidthPx, videoHeightPx) >= 720
```

如果宽高缺失、非正整数或短边低于 720，媒体准备阶段立即失败，不创建源文件、衍生关键帧或证据关联记录。API 返回可识别的业务错误和中文提示：

> 车辆环绕视频清晰度不足，检测到 {width}×{height}，请使用系统相机以 720p 或更高画质重新录制后上传。

无法读取分辨率时显示“无法识别视频分辨率”，同样要求重新录制。其他视频证据类型记录探测值但暂不执行该门槛，避免无依据扩大业务规则。

### 4.6 历史兼容

- 已存在的 `artifactVersion: 1` metadata 即使没有新增字段，仍可读取并通过原有完整性校验。
- 新上传的车辆环绕视频必须经过新门槛并写入 `videoQualityStatus: "PASSED"`。
- Field/Admin 对历史记录显示“历史资料未记录分辨率”，不伪造分辨率。
- 已签署、已归档订单不重新探测、不重新生成 PDF，也不改变状态。

### 4.7 Field/Admin 展示

证据文件视图读取 metadata：

- 有合法宽高：显示“视频清晰度：{width}×{height}”。
- 新上传且通过门槛：可同时显示“符合环绕视频最低要求”。
- 历史视频无宽高：显示“视频清晰度：历史资料未记录”。
- 照片不显示视频清晰度行。

展示值只来自服务端 metadata，不以浏览器本地推断作为事实来源。

## 5. 数据与兼容性

本轮只扩展 `VehicleDeliveryEvidenceFile.metadata` JSON 内容，不修改 Prisma schema。现有证据包 manifest、源文件 SHA-256、衍生关键帧和电子签就绪判断继续使用原流程。

新字段不得改变历史 evidence manifest 的序列化结果。质量门槛发生在新文件落库前，因此不需要后台批量回填，也不触发历史 PDF 失效。

## 6. 测试策略

### 6.1 Web 单元测试

- 移动端视频契约不再包含 `video-capture`。
- 移动端照片契约仍包含 `photo-capture`。
- 视频相册入口及 720p/300MB 提示存在。
- 413 映射为文件过大/网关配置提示。
- 网络错误、超时、取消及普通业务错误文案保持不变。
- 视频 metadata 的有值、历史缺失两种展示正确。

### 6.2 API 单元测试

- `ffprobe` 宽高、分数帧率和码率解析正确。
- 1280×720、720×1280 和更高分辨率车辆环绕视频通过。
- 480×360、宽高缺失和非法宽高车辆环绕视频被拒绝。
- 非环绕视频记录分辨率但不被本轮门槛拒绝。
- 新 metadata 可通过证据就绪校验。
- 缺少新增字段的历史 `artifactVersion: 1` metadata 继续兼容。
- 低清拒绝不会留下源文件、衍生文件或证据关联记录。

### 6.3 配置与人工验收

- `nginx -t` 成功，reload 后 API vhost 显示 320m/1200s/关闭缓冲。
- 原验收文件 `IMG_0203.mov`（约 191.6 MiB）可完成上传和关键帧处理。
- 低于 720p 的测试视频得到明确重录提示。
- 720p 或 1080p 系统相机视频上传成功，Field/Admin 显示实际分辨率。
- 超过 300 MiB 的文件在前端被明确拦截。
- 人工复核移动端不再出现“现场录像”按钮，照片现场拍摄仍可用。

## 7. 发布与回滚

发布顺序：

1. 合并 Web/API 代码和测试。
2. 构建不可变 Staging 镜像。
3. 备份并调整 Staging API Nginx，执行 `nginx -t` 和 reload。
4. 部署 Staging API/Web 镜像并检查健康状态。
5. 依次执行小文件、720p 视频、原 191.6 MiB MOV、低清视频和超限文件验收。
6. 更新 Stage 2 验收报告，记录 STG2-004/005 的验证证据。

回滚方式：

- Web/API 镜像回滚到发布前 digest。
- Nginx 恢复时间戳备份，执行 `nginx -t` 后 reload。
- 因无数据库迁移和数据回填，不需要数据库回滚。

## 8. 后续工作

Wave 2 验收通过后，另开 Wave 3 分支处理 STG2-007：将 Field 随车证件、钥匙、工具、其他附件及五项车况检查结构化，并让 Portal 与交接确认单 PDF 使用客户确认快照的一致字段。

### 8.1 GPS 现场证据扩展点

取消网页内视频直拍不影响后续加入 GPS 地图定位。定位证明与媒体拍摄应解耦，并通过服务端现场证据会话绑定：

1. Field 人员到场后主动执行“到场定位打卡”。
2. 页面通过浏览器或微信定位能力取得经纬度、定位精度、采集时间和原始坐标系。
3. 服务端保存不可变 `locationProof`，并签发短时有效的 `evidenceSessionId`。
4. 人员使用手机系统相机录像，返回 Field 后从相册上传，上传记录绑定 `locationProofId` 和 `evidenceSessionId`。
5. 上传前可再次请求定位，形成“拍摄前打卡 + 上传时复核”的位置连续性证据。
6. Admin 后续可展示地图、逆地理地址、定位精度及与预约交接地点的距离。

后续数据设计需要保留原始坐标系，并明确中国地图展示使用的坐标转换结果。位置会话建议默认有效 10–15 分钟，距离和定位精度门槛应可配置。

从相册上传无法绝对证明视频是在定位点拍摄。媒体创建时间和 EXIF 只能作为辅助信息，不得作为权威位置来源；可信事实来自服务端定位记录、上传时间、文件哈希、操作者身份和审计日志。若未来业务要求“定位与拍摄不可分离”的强证据，应迁移到微信小程序或原生 App 的受控采集能力。

本扩展点不纳入当前 Wave 2，不新增本轮数据库模型、接口或页面实现。
