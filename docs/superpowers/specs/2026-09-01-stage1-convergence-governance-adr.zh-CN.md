# Stage 1 收敛治理主 ADR

日期：2026-09-01

状态：待评审

基线提交：`2b96822dddcf4221142caa0c3993449ba6b98978`

## 决策摘要

Stage 1 后续工作采用以下依赖顺序：

`S0 范围与权威治理 → S1 可信发布底座及测试隔离 → S2 最小主路径语义收敛 → S3 单一候选版本提升及验收 → S4 结构拆分 → S5 独立能力启用、补齐与验收`

本 ADR 只决定范围、波次依赖、不可变原则和审批边界。它不是 S0—S5 的总实施计划，也不批准 S1、S2 或后续波次施工。

首批正式规格仅包括：

- 本 ADR；
- [S0 原子事实权威与临时资产治理规格](./2026-09-01-stage1-s0-authority-and-temporary-asset-governance-design.zh-CN.md)。

S1、S2 必须分别完成规格评审后，才能分别生成实施计划。S3 Runbook 可以先有骨架，但必须等 S1 的 Runner 命令、证明格式和数据库隔离契约稳定后才能定稿。S4、S5 必须等 Stage 1 签字后再设计。

## 背景

PR260—302 在约三周内显著扩大了业务域、数据库、权限、状态机和运行时代码。PR303—312 主要继续增加验收、发布、数据库治理和数据修复能力。两段投入解决了大量真实安全与业务问题，但也形成了四项结构性风险：

1. Journey 与 Application、Order、Contract、ESign、Handover、Payment、Lease、Vehicle、Closure 之间缺少清晰的事实所有权，导致流程状态被误用为业务事实或需要多处同步；
2. Closure、Handover、订单工作台和大型集成测试已超过可靠局部审查的合理边界；
3. API runtime 同时承担业务服务和验收/维护工具箱职责；
4. 测试数量很大，但数据库身份、隔离、并发确定性及最终发布物代表性不足。

当前不能通过继续增加新模型、新状态、新功能开关或专用修复脚本解决这些问题，也不能在恢复 Stage 1 验收前发动全面重构。

同一基线在 GitHub main CI 中通过，但全新本地 worktree 的基线运行进一步暴露了 S1 的必要性：

- 首次执行命令为 `pnpm -r test`，根级并行测试因 Web 先于 Shared 构建而失败；
- 确定性重跑命令为 `pnpm --filter @subscription-saas/shared build; pnpm -r test`，Web 96 个文件、846 项测试通过；API 数据库测试出现“未提供 `DATABASE_URL`”、旧 Schema 缺列和数据库凭证不匹配等失败，并存在跳过；
- 该次运行没有预先注入和冻结受控数据库身份，故“目标数据库身份”为未知，不可作为环境证明；
- 当次控制台输出未固化为可复核的脱敏日志，精确跳过数量也未留存。因此脱敏日志位置和精确跳过数量均为“无”，这些数字只属于设计阶段观察，不能成为 Release 或 S0 通过证据。

该结果不是本 ADR 对产品代码的失败判决，而是“数据库身份、隔离、可留存脱敏日志和零跳过必须进入 S1”的现状证据。S1 以后任何测试证据必须记录完整命令、构建证明、数据库不可逆身份、通过/失败/跳过数量及证据输出 digest。

## Stage 1 冻结范围

本轮 Stage 1 人工验收只覆盖：

`进件 → 审核 → 最终方案 → 客户单次确认 → 正式签约 → 主动支付 → 交付 → 激活 → 周期账单与自动催收 → 无争议正常退车及合同结束`

其中：

- 微信委托代扣不属于当前基线；收款采用主动支付、自动提醒、逾期标记和人工催收；
- “正常结束”只覆盖事实完整、无损伤争议、无复杂费用争议且可以按现有支付/核销事实关闭的路径；
- 验收必须同时使用一张从新进件开始的黄金订单和一张具有完整来源证明的受控成熟订单夹具；
- 不得通过直接修改黄金订单日期、伪造 Journey 状态或覆盖领域事实把同一订单“催熟”。

以下能力不作为本轮 Stage 1 恢复验收的共同前置条件：

- 协议延长、在租换车、提前结束和受控其他变更；
- 损伤争议、复杂合同计价、客户拒绝或未响应处置；
- 司法/法务追偿；
- Stage 1C 车辆资产、成本、资本和收益权的完整验收。

这些能力的现有代码和不可变历史事实不得删除。除 P0 安全、数据完整性或现有主路径阻断外，Stage 1 签字前不继续扩展或启用。

## 波次决策

### S0：范围与权威治理

目标是批准原子事实权威、不变量、派生投影边界和临时资产生命周期。

S0 不修改业务代码，不创建数据库迁移，不启用功能。其退出条件是：

- 原子事实权威矩阵获得批准；
- 激活前置事实、原子写入、同步投影和后置编排投影已分层；
- 激活重放完整不变量已定义；
- Closure 与 Billing/Payment 的职责边界已定义；
- 当前实现到目标权威的偏差已登记并路由，但未形成 S1/S2 施工授权；
- 临时资产分类、实际基线清单、owner、退出规则和审批责任已定义。

### S1：可信发布底座及测试隔离

S1 包括三个独立工作流，不预设为三个 PR：

1. 数据库测试隔离、逐套迁移和零跳过门禁；
2. 最终 API/Web/Runner 镜像及真实 Compose 验证；
3. Runner 构建/执行证明、逻辑 Manifest 和通用受控修复执行边界。

S1 实施计划至少按以下可独立评审单元拆分：

- 独立数据库基础设施；
- 逐套数据库测试迁移；
- Release CI 零跳过门禁；
- 最终镜像 Compose 验证；
- Runner 身份与证明；
- Manifest 和通用修复执行器。

默认使用独立数据库。只有一套测试被证明完全 Schema-safe，才允许使用唯一 Schema 隔离。禁止整个测试体系依赖单 worker，但明确验证串行语义的单个场景可以声明并使用串行执行。

### S2：最小主路径语义收敛

S2 只按主路径转换收敛语义，不全面拆分巨型文件。允许处理：

1. 进件事实与业务等待；
2. 最终方案、车辆预约和客户单次确认；
3. Contract 与 ESign 状态边界；
4. Handover 事实触发权威激活；
5. Billing/Payment 事实触发流程推进；
6. 无争议正常到期和订单结束。

Journey 只拥有调度、等待、重试和技术异常。它可以命令领域服务执行动作，但 Journey 自身状态不得证明领域动作已经完成。

默认保持 API、错误码、审计事件、锁顺序和事务边界兼容。确因消除重复权威需要调整时，必须单独说明一致性模型，并证明：

- 锁顺序无新增死锁路径；
- 并发 barrier 下只有一个权威结果；
- 事务失败无部分领域事实；
- Outbox 事件丢失可恢复；
- 重放幂等且不会重复副作用。

经批准可以增加向后兼容的审计字段或事件版本，但不得静默改变既有语义。

### S3：单一候选版本提升及验收

“单一候选版本”是指每次验收尝试只提升一个冻结 RC，不是禁止 CI 和临时环境反复构建验证。

- RC1 失败后立即作废；
- 修复必须返回 CI/临时环境；
- 重新冻结完整的 RC2；
- 禁止在 Staging 原地打补丁、替换单个镜像或混用不同 source SHA 的组件。

每个 RC 必须绑定一个明确 source SHA。不能使用“包含某 PR 的最新 main”作为可执行身份。当前本地 `main` 的同步和未提交内容保护属于独立工作区操作，不进入收敛提交。

S3 使用两条证据链：

- 新建黄金订单验证从进件到激活的前门主路径；
- 受控成熟订单夹具验证维护执行、周期账单、正常到期、无争议退车和结束。

成熟订单夹具必须通过 Runner/夹具工厂建立完整领域事实，记录 source SHA、Runner digest、数据库身份、夹具规格版本、生成输入指纹和结果 digest。夹具不得直接覆盖 Journey 状态，也不得通过手工 SQL 修改单一日期来伪造时间经过。

连续两次受控维护执行分别证明：

1. 第一次正确识别并入队；
2. 第二次重放不重复、不漏单且 `blockedCount=0`。

它们证明维护执行和幂等性，不代表两个真实月度账单周期。

### S4：结构拆分与资产退役

Stage 1 签字后，S4 再分别设计：

- Closure、Handover 和订单工作台拆分；
- 大型集成测试拆分；
- 一次性脚本、阶段开关和兼容分支退役；
- `BillingMaintenanceCycleFact` 停写、保留或泛化决策；
- Journey 重复外键的前向迁移评估。

S4 不默认删除已有不可变业务、审计、支付或法律事实。

### S5：独立能力启用、补齐与验收

协议延长、换车、提前结束、争议和司法处置分别判断：

- 保留并独立启用验收；
- 补齐缺失能力；
- 继续暂停；
- 或通过前向兼容方式退役。

不得默认重新建设，也不得重新成为最小 Stage 1 的共同前置条件。

## 发布证明分层

正式发布证明采用两层模型。

### 构建证明

构建证明只包含构建时可确定、不可变的身份：

- API image digest；
- Web image digest；
- Runner image digest；
- source SHA；
- migration catalog hash；
- repository contract digest。

### 执行证明

Runner 验证所需能力范围内的构建证明后，生成并冻结本次环境 Manifest，再形成执行证明：

- build-proof digest；
- environment-manifest digest；
- 目标数据库不可逆身份；
- 执行类型和能力范围；
- 批准记录引用；
- 输入计划 digest；
- 输出证据 digest；
- 执行开始、完成时间和终态。

完整验收要求验证 API/Web/Runner。单独 migration/schema 操作只要求与其能力范围相关的 API schema、Runner、迁移目录和仓库契约，不因 Web 尚未部署而失去执行能力。

Manifest 必须有显式 schema 版本，并使用一种由 S1 规格固定的规范化序列化算法。秘密、手机号、令牌和原始数据库连接不得进入证明；只保存受控引用或不可逆指纹。

## 数据修复原则

默认使用全新验收数据。历史数据只处理会破坏环境完整性、阻塞 Worker 或污染验收结果的部分。

任何数据写操作必须独立经过：

`dry-run → 目标身份验证 → 计划摘要 → 输入 evidence digest → 人工批准 → apply → replay → 后置条件`

不同修复不得打包成一次笼统授权。合同变更 bootstrap 默认不执行；只有被证明是当前有效订单或 Worker 健康的必要前置条件时，才单独申请。

## 全局硬门槛

- 新业务模型、枚举、权限和功能开关默认净零增长；新增业务语义必须有独立 ADR、owner、退出条件和批准；
- 不得通过通用 JSON 字段隐藏新增状态机或业务语义；
- 未解决目标数据库漂移时不得新增业务迁移；
- 已合并或已应用迁移不可改写，只能前向修正；
- Release 门禁不得存在被静默跳过的数据库测试；
- 行为保持型修改默认保持 API、事务、锁顺序、错误码、审计和幂等结果兼容；
- 每个波次必须预先定义回滚条件和停止条件；
- S2 单个 PR 超过约 1,500 行产品代码或25个生产文件时，必须拆分或单独批准；纯文件移动也必须保持可审查的单一责任边界。

## 已确认的非决策

本 ADR 不决定：

- S1 的具体 Runner 命令、Manifest Schema 或 CI 实现；
- S2 各转换的最终代码修改；
- S3 的服务器命令和具体测试数据；
- `BillingMaintenanceCycleFact` 的最终泛化模型；
- Journey 外键的删除方案；
- Closure、Handover 或订单页面的拆分文件结构。

这些事项必须在依赖规格中分别评审。

## 后果

正面结果：

- Stage 1 恢复验收不再依赖完整车辆运营和合同变更平台；
- 发布可信度在语义修改前建立；
- Journey 与领域事实的关系可以逐转换收敛；
- 巨型模块拆分不再阻塞最小闭环验收；
- RC 失败不会诱发 Staging 现场补丁。

代价：

- S1/S2 施工前增加规格审批时间；
- 部分现有高级能力继续保持关闭或未验收；
- 旧模型、迁移和巨型文件会在 Stage 1 签字前继续存在，但不再继续扩张。
