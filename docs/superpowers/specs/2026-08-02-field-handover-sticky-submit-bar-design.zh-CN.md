# Field 交接详情页与 Portal 交付闭环修复设计

## 背景与事实

人工验收在 iPhone 微信内置浏览器中下滑 Field 交接详情页时，已选中的“无可见损伤”单选按钮绘制到蓝色“提交现场资料”操作栏上方，形成控件重叠并遮挡操作栏内容。

当前页面将提交栏放在表单末尾并使用 `position: sticky; bottom: 0`，但提交栏没有显式堆叠层级，背景仍为半透明；页面也只按系统安全区设置底部留白。Ant Design 选中态单选按钮带有非零堆叠层级，因此滚动经过提交栏时会穿透显示。这是展示层叠和滚动空间问题，不涉及交接状态、表单数据或提交接口。

## 已批准方案

采用方案 A，保留底部粘性提交入口，并修正其层叠与滚动边界：

1. 提交栏使用不透明页面背景，设置高于表单控件的明确 `z-index`。
2. 提交栏增加上边界和轻量阴影，使操作区与滚动内容有稳定视觉分隔。
3. 页面滚动区域预留“提交栏高度 + iPhone 底部安全区”的空间，保证末尾表单内容能够滚动到操作栏上方。
4. 提交栏继续使用 `env(safe-area-inset-bottom)`，不改变现有按钮启用条件、上传拦截规则和提交行为。

## 修改范围

- 仅修改 `apps/web/src/app/field/handover/tasks/[id]/page.tsx` 的页面布局样式。
- 更新 `apps/web/test/field-handover-pages.spec.ts`，覆盖粘性栏层级、不透明背景、视觉分隔和底部预留。
- 不修改 API、数据库、交接业务状态或电子签流程。

## 验收标准

1. 在 iPhone 微信内置浏览器中上下滚动时，单选按钮、输入框、文本或卡片均不会绘制到提交栏之上。
2. 页面末尾内容可以完整滚动到提交栏上方，不被提交栏永久遮住。
3. 刘海屏/全面屏底部安全区仍有足够留白。
4. “提交现场资料”按钮的显示、禁用、上传中状态和点击行为保持不变。
5. Field 页面聚焦测试、Web lint、Web typecheck 和生产构建通过。

## 回滚

该修复仅涉及 Web 样式；如出现意外，可单独回退本提交并重新发布上一版 Web 镜像，无需数据库回滚。

## 补充验收问题事实

在原方案获批后，订单 `ORD20260802071556GFEY` 的后续验收又确认了四个相互关联的问题：

1. 车辆交接确认单已经完成双方签署并归档，但 Portal 仍显示“签署暂未开放，请稍后刷新”。后端终态投影仍把“不能再次发起签署”翻译成阻塞项，前端又原样展示该阻塞，形成互相矛盾的终态提示。
2. Portal 只暴露“已归档”的状态，没有客户权限范围内的已签署交接确认单 PDF 预览接口和页面入口。
3. “我的申请”后端虽然能判断 `GO_CONTRACT`、`GO_PAYMENT`、`WAIT_DELIVERY` 等阶段，但只返回动作代码；页面没有渲染这些阶段的操作入口，申请生成订单后便失去连续引导。
4. Portal 订单详情接口在没有已确认押金台账时返回内部 BigInt 零值，Express 在 JSON 序列化时抛出 `TypeError: Do not know how to serialize a BigInt`，导致订单详情 500。该问题与订单数据权限无关。

## 补充设计：交接签署终态与已签 PDF

### 终态语义

- 当 Stage 2 交接确认单具备完整归档字段时，Portal 电子签状态仍保留 `canStartSigning = false`，但不再返回“签署未开放”阻塞项。
- Web 展示模型对“已完成并归档”再做一层防御性收敛：终态不展示发起签署类阻塞，避免旧响应或瞬时刷新状态产生矛盾 helper。
- 未完成、失败、异议、签署条件不足等非终态继续保留现有阻塞提示和重试语义。

### 已签 PDF 预览

- 增加客户鉴权路由：`GET /api/portal/handover-reviews/:id/esign/signed-document/preview`。
- 接口先校验交接工单属于当前客户，再复用现有 Stage 2 归档文件读取能力；仅在完整归档时返回文件流，使用 `inline` 响应头供浏览器预览。
- Portal 电子签状态在文件可用时返回相对预览地址；交接详情页显示“查看已签署交接确认单”入口。
- 不向客户端返回存储桶、对象键、供应商任务号或签署能力链接，不放宽现有客户数据权限。

## 补充设计：“我的申请”持续引导

### 服务端动作投影

申请进度响应新增可空的 `nextActionTarget`：

```ts
interface PortalNextActionTarget {
  label: string;
  url: string;
}
```

目标由服务端根据申请、正式订单、主合同和当前可见交接工单统一计算，前端不再猜测业务关联：

| 当前阶段 | 引导目标 |
| --- | --- |
| 等待生成正式订单 | 仅展示等待信息，不提供无效跳转 |
| 订单审核中 | 当前正式订单详情 |
| 待签合同 | 当前订单的主合同详情；若关联尚未就绪则退化到合同列表 |
| 待支付 | 按当前订单过滤的“我的账单” |
| 交接任务尚未开放给客户 | 展示等待现场人员提交的信息，并提供订单详情作为进度入口 |
| 客户复核、交接签署或归档中 | 当前可见的交接任务详情 |
| 车辆已交付、订单在租 | 当前订单详情，并明确提示交付已完成 |

为定位精确目标，申请查询只补充必要的关联 ID、状态以及最新的交付出库工单，不返回后台人员、短信、存储或签署供应商数据。

### Portal 页面

- “我的申请”顶部增加统一的“下一步”引导卡片，显示当前阶段说明和服务端返回的按钮。
- 原有最终方案确认、补充资料等页内动作继续保留；合同、账单、车辆交接和交付完成阶段改为精确跳转。
- 申请进度步骤继续展示全链路状态，不改变现有申请审核、订单、签约、支付或交接状态机。

## 补充设计：Portal 订单详情 500

- 无押金台账时，先通过现有 `toPlainDepositAccount` 将内部 BigInt 金额转换为 Number，再返回默认押金账户。
- 有押金台账时的聚合逻辑、金额单位和状态推导保持不变。
- 增加无台账订单回归用例，明确要求整个订单详情响应可被 `JSON.stringify`，且默认金额均为数值 `0`。

## 补充修改范围

- API：Portal 订单押金摘要、申请进度动作投影、Stage 2 Portal 电子签终态、客户侧已签 PDF 预览路由。
- Web：Field 粘性提交栏、Portal 交接签署终态与 PDF 入口、“我的申请”下一步引导。
- 测试：API 单元/控制器测试、电子签生命周期投影测试、Portal 纯展示模型与页面契约测试。
- 不新增数据库字段或迁移，不修改订单、支付、车辆交接或电子签状态流转规则。

## 补充验收标准

1. 交接确认单完整归档后，不再显示“签署暂未开放”，并可在当前交接详情预览已签署 PDF。
2. 其他客户不能访问该交接单的电子签状态或已签 PDF；未完整归档时不能伪造可用入口。
3. 从“我的申请”可以连续进入当前合同、当前订单账单、当前交接任务，直至车辆交付完成；每个入口均指向当前申请生成的正式订单。
4. 无押金台账的订单详情返回 200，响应可安全 JSON 序列化；`ORD20260802071556GFEY` 不再触发 500。
5. 原 Field 页面遮挡修复的五项验收标准继续全部成立。
6. API 与 Web 聚焦测试、lint、typecheck 和生产构建通过。

## 补充回滚

本轮不含数据库迁移。API 与 Web 应作为同一发布单元回退，以避免旧 Web 看不到新增动作目标或新 Web 请求尚未存在的 PDF 路由；订单数据和已归档 PDF 不需要回滚。
