## ACC-20260826-04 代码边界审计摘要

### 已存在的底座

- V2 合同变更域已建立变更单、报价、合同分段、续订考虑期、自动化任务、幂等命令和审计数据模型。
- 协议延长后端已覆盖创建、报价、客户确认、补充协议、电子签、归档和到期激活等核心步骤。
- Portal 可在续订考虑期选择续订或到期结束，并可确认或拒绝续期报价。
- 订阅闭环域已建立正常结束、提前终止、退车/追回、检查、结算和库存释放的后端能力。

### 当前不可验收的部分

- 订单页现有“申请变更方案”是交付前订单重做入口，`ACTIVE` 在租订单被明确禁止使用。
- Admin 合同变更中心只能查看续订考虑期和已有协议延长单，没有调用 `POST /subscription-changes/extensions` 的人工发起入口。
- `SubscriptionChangeType` 当前只有 `EXTENSION`，尚无在租换车、通用条款调整等正式变更类型。
- 提前终止虽然已有后端发起、取消和执行接口，但 Web 端没有调用；订单页仅暴露“提前终止退车”这一物理退车选项，不能替代终止方案、协议签署、审批和执行闭环。
- 在租换车只存在枚举、车辆期间原因和出入库工单类型等底座，没有完整状态机、车辆切换、补充协议、账单和权益迁移编排。
- Staging 已部署相关数据库迁移，但未设置 `SUBSCRIPTION_EXTENSION_ENABLED=true`；截至记录时，合同变更、续订考虑期、合同分段和订阅闭环新表均无业务记录。

## ACC-20260826-05/06 退车验收目标

### 节点一：车辆取回与现场证据固化

- 现场逐项确认车辆外观、内饰、里程、电池/充电设备、钥匙、行驶证、随车附件和客户遗留物，并完成车辆物理取回。
- 每个车况或附件异常必须能直接拍摄或选择照片、视频等文件，展示上传进度、失败原因、预览和替换记录；不得要求人工填写外部 URL。
- 参考 Field Handover 的证据采集方式，将附件与具体检查项、损伤项一一绑定，并记录采集时间、提交人员、文件摘要、原始文件和替换关系。
- 固化交车和退车两端的签署文档、检查快照与原始附件，确保后续争议或司法环节能按车辆、订单、检查项和时间线完整导出举证材料。
- 客户可现场确认，也允许客户拒绝确认、无法到场或失联；上述情况必须留痕，但不得阻止平台先取得车辆控制权和固化证据。

### 节点二：状态对比、合同计价与异状账单

- 以车辆交付时的已确认快照为基线，与退回后的检查事实逐项对比，生成可追溯的异状清单。
- 每个收费项必须绑定实际签订订单合同的版本、具体条款、计价规则、数量/里程/损伤等级、证据和计算过程，避免脱离合同直接人工报价。
- 系统根据确认后的责任和计价事实生成账单；无法自动匹配合同条款时进入人工复核或审批，不得静默采用默认价格。
- 客户同意、客户拒绝、客户未响应三种结果都必须有独立状态和后续路径。拒绝或未响应可以把账单标记为争议/待追偿，但不得阻断车辆整备、库存处置和订单闭环编排。

### 节点三：账单结算与订单完结

- 客户同意：支持 Portal 自助付款并自动核销账单。
- 人工介入：支持线下收款登记、人工核销、减免/调整审批、保证金抵扣和退款处理。
- 司法处置：支持转入诉讼或其他法务追偿路径，以受控的司法/法务核销方式关闭运营待办，同时保留应收、追偿、判决/执行和坏账处置事实，不能伪装为客户已经付款。
- 三条结算路径都必须形成账单、支付/处置凭证、审批、会计事实和审计日志，最终将订单收敛到明确终态。
- 订单完结不得删除或覆盖交付、退回、损伤、合同条款、客户意见、账单版本和结算历史。

## 后续统一处理范围

1. 将交付前“退回重做”与租期内“合同变更”在命名、权限和页面入口上彻底分离。
2. 在在租订单工作台增加统一变更入口，至少支持协议延长、换车和提前结束，并为暂未实现的类型给出明确能力边界。
3. 接通 Admin 协议延长人工创建入口，完成 Staging 分段初始化、功能开关启用和端到端回归。
4. 将提前终止后端接入 Admin 操作页，形成方案、协议、签署、审批、执行、退车、结算和库存释放的连续流程。
5. 建设换车编排，覆盖原车退还、新车锁定、双向交接、车辆订阅期间、补充协议、账单与权益迁移。
6. 为所有变更建立一致的幂等、版本控制、失败恢复、人工接管、审计和最终状态收敛规则。
7. 将退车损伤照片从 URL 文本改为受控附件上传，并复用 Field Handover 已验证的采集、预览、替换和证据治理模式。
8. 把退车重构为车辆取回取证、交退状态对比及合同计价、账单结算完结三个可恢复的大节点。
9. 建立客户同意、拒绝和未响应的非阻断分支，以及自助付款、人工核销和司法/法务核销三种结算路径。

## 后续验收门槛

- `ACTIVE` 在租订单能从订单工作台明确进入“租期内变更”，不会再落入交付前退回重做流程。
- Admin 可主动发起协议延长，客户只需确认一次确定版本的变更方案；补充协议签署归档后，新合同分段按生效日执行。
- 提前结束必须先完成受控的终止方案和协议流程，再进入退车、结算与库存释放；任何失败均可重试或人工接管，不进入无出口死信。
- 换车必须以一个可审计的变更单串联原车、新车、双向交接、合同、账单和权益事实，失败时不得同时占用两台车辆或丢失原车控制权。
- 正常到期结束、续期、换车和提前结束四条路径均能收敛到明确终态，并通过 Admin、Portal、数据库事实和签署文档交叉核验。
- 退车损伤记录可以直接上传并预览照片/视频；每份证据能追溯到车辆、订单、检查项、提交人、采集时间、原始文件和文件摘要。
- 每个异状账单项能追溯到交付/退回差异、合同版本和具体条款，并展示可复核的计算过程。
- 客户拒绝或未确认账单时，车辆取回、证据固化、整备和库存处置可以继续；系统保留争议及追偿状态，不把争议账单静默核销。
- 自助付款、人工介入和司法/法务处置均能把运营流程收敛到明确终态，同时保持支付、应收和法务处置事实的语义区别。
