# 管理后台登录用户自助修改密码设计

## 1. 背景

管理后台当前支持用户名/密码登录，也允许拥有 `user:manage` 权限的管理员在用户管理中代改其他用户密码，但登录用户没有验证本人当前密码后自助改密的入口。Staging 的 `admin` 密码失效后只能通过受控数据库操作恢复，说明后台需要一个不依赖用户管理权限的本人凭据维护能力。

本设计只覆盖管理后台 `User` 账号，不改变客户 Portal 短信登录或现场人员 OTP 登录。

## 2. 目标与非目标

### 2.1 目标

- 所有已登录且状态有效的管理后台用户均可修改自己的密码。
- 修改前必须验证当前密码。
- 新密码继续沿用现有最少 8 位规则，并显式限制为最多 72 个 UTF-8 字节，避免 bcrypt 静默截断；当前密码仍允许验证历史上可能超过该边界的凭据。
- 新密码不得与当前密码相同。
- 密码更新和审计日志必须原子提交；审计中不得出现明文密码或密码哈希。
- 修改成功后清除当前浏览器的 `access_token` Cookie，并跳转登录页重新认证。
- 不引入新的 RBAC 权限、菜单、数据库字段或迁移。

### 2.2 非目标

- 不实现忘记密码、邮件找回、短信找回或管理员审批流程。
- 不使其他浏览器中的既有 JWT 立即失效；它们仍按现有过期时间失效。
- 不改变管理员在用户管理中代改密码的现有能力。
- 不修改客户 Portal 与现场人员认证。

## 3. 方案选择

采用“顶部登录用户入口 + 改密弹窗”。它不依赖菜单和业务权限，所有登录用户都能到达，且不会把“本人验证后改密”混入“管理员代改其他用户”的系统管理语义。

不采用独立个人中心页面：本期只有改密一个动作，新增路由和页面没有足够收益。不复用用户管理页面：普通用户未必拥有 `user:view`/`user:manage`，并且两类改密的身份校验和审计语义不同。

## 4. 后端设计

### 4.1 接口

新增受 `AuthGuard` 保护的接口：

```http
POST /api/auth/change-password
Content-Type: application/json

{
  "currentPassword": "string",
  "newPassword": "string"
}
```

成功响应：

```json
{
  "success": true
}
```

控制器成功后清除 `access_token` Cookie。接口只使用 `request.user.id` 确定目标用户，不接受用户 ID 或用户名，避免水平越权。

### 4.2 DTO 校验

新增 `ChangePasswordDto`：

- `currentPassword`：字符串，至少 8 个字符；不新增 72 字节限制，以兼容历史上已由 bcrypt 截断并保存的凭据。
- `newPassword`：字符串，至少 8 个字符，最多 72 个 UTF-8 字节。
- 确认密码只在前端表单中存在，不发送给 API；服务端只信任 `newPassword`。

字符数校验继续使用 `class-validator`，UTF-8 字节上限由服务方法显式检查，因为 bcrypt 的输入边界按字节而不是 JavaScript 字符数计算。

### 4.3 服务流程

`AuthService.changePassword(userId, dto, context)` 按以下顺序执行：

1. 读取指定 `userId` 的账号；不存在、已删除或非 `ACTIVE` 时返回未授权。
2. 使用 `bcrypt.compare` 验证 `currentPassword`；错误时返回 `CURRENT_PASSWORD_INCORRECT`。
3. 使用 `bcrypt.compare` 检查 `newPassword` 是否与现密码等价；相同则返回 `PASSWORD_REUSE_NOT_ALLOWED`。
4. 使用 cost 12 生成新 bcrypt 哈希。
5. 在一个 Prisma 事务中使用 `updateMany` 条件更新：条件同时包含用户 ID、旧 `passwordHash`、`ACTIVE` 和未删除。更新数不是 1 表示并发改密或账号状态变化，整个事务以 `PASSWORD_CHANGE_CONFLICT` 回滚。
6. 同一事务写 `AuditAction.UPDATE`：模块为 `system`，实体为当前用户，操作者为当前用户；快照只记录 `credential: "password"` 和 `selfService: true`，不记录任何密码、哈希或长度。

条件更新避免两个并发请求都基于同一旧密码覆盖彼此；审计与密码更新同成同败。

### 4.4 错误合同

| HTTP | code | 场景 |
| --- | --- | --- |
| 400 | `CURRENT_PASSWORD_INCORRECT` | 当前密码验证失败 |
| 400 | `PASSWORD_REUSE_NOT_ALLOWED` | 新密码与当前密码相同 |
| 400 | `PASSWORD_TOO_LONG` | 新密码超过 72 个 UTF-8 字节 |
| 401 | 现有认证错误 | Cookie 无效或账号不再有效 |
| 409 | `PASSWORD_CHANGE_CONFLICT` | 并发改密或验证后账号状态变化 |

响应不得回显提交的密码。当前密码错误只说明本次凭据不正确，不返回用户或哈希细节。

## 5. 前端设计

### 5.1 入口

在 `ProtectedShell` 顶部右侧显示当前用户姓名/用户名，并提供“修改密码”操作；退出登录继续保留。入口不检查业务权限。

### 5.2 弹窗

抽取独立 `ChangePasswordModal`，包含：

- 当前密码；
- 新密码；
- 确认新密码；
- 密码输入框的显示/隐藏能力；
- 提交与取消操作。

前端校验最少 8 位、两次新密码一致、新旧密码文本不得相同。字节上限以 API 为最终边界，前端同步给出提示以减少无效请求。

提交期间按钮进入 loading 并阻止重复提交。API 错误显示在当前页面，不关闭弹窗、不清空当前密码以外的无关页面状态。成功时显示提示、关闭弹窗、跳转 `/login`；服务端已清 Cookie，因此返回受保护页面会重新要求登录。

## 6. 安全与审计

- API 目标身份只来自已验证 JWT，不允许客户端指定用户。
- 当前密码和新密码只通过 HTTPS 请求体传输，不写日志、审计或错误响应。
- bcrypt cost 固定为现有的 12，不改变已有密码兼容性。
- 密码更新采用旧哈希条件更新，防止并发覆盖。
- 成功后只终止当前 Cookie 会话；全会话撤销需要密码版本或 `passwordChangedAt`，本期明确不做。
- 不新增权限：本人改密属于认证能力，不属于用户管理授权。

## 7. 测试策略

### 7.1 API 单元与合同测试

- 当前密码错误时不生成哈希、不更新用户、不写审计。
- 新旧密码相同时拒绝更新。
- 新密码超过 72 个 UTF-8 字节时拒绝更新，包括多字节字符样例；当前密码不受该新增边界影响。
- 成功时生成可验证的新 cost 12 哈希，并在同一事务完成条件更新和脱敏审计。
- 条件更新数量为 0 时返回 409，且不提交审计。
- 控制器路由受 `AuthGuard` 保护，只使用 `request.user.id`，成功时清除 Cookie。

### 7.2 Web 测试

- 所有登录用户均可看到修改密码入口。
- 表单要求三个字段，拒绝不一致的新密码和文本相同的新旧密码。
- 提交调用 `/auth/change-password`，请求体不包含确认密码。
- API 失败时保留弹窗并显示错误。
- 成功时显示提示并跳转 `/login`。

## 8. 发布说明

该功能合并部署后即可使用，无需 seed 或数据库迁移。Staging 部署后用普通后台账号和 `admin` 各验证一次：错误当前密码被拒绝，正确改密后当前会话退出，新密码可重新登录，旧密码不可登录。验证账号必须使用专用测试凭据，结果不得记录明文密码。
