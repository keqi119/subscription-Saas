# 六个月订阅业务自动化设计

日期：2026-07-29

更新：2026-07-30

状态：已批准的设计基线

## 背景

当前系统已经能够在运营人员深度参与的情况下完成一笔订阅订单，并已具备客户申请、产品与车辆审核、订单、Stage 1 与 Stage 2 签约、账单、微信 JSAPI 支付、交付、月度权益、退车、服务工单及运营报表等能力。

未来六个月的产品目标不是平台多租户化，而是在单一运营主体下，让正常订单能够从 A/B 线申请开始，自动完成签约、付款、交付、流程通知、周期账单及合同结束。

会计入账、对外付款和真实退款执行继续由人工处理；客户收款和应收核销必须自动化。系统负责生成对外应付计划、汇总每日付款批次、登记实际付款结果并完成业务核销，但一期不导入完整银行流水、不接银企直连。系统还应为未来资产公司接入预留边界，但不能在本次六个月交付周期内把现有后台整体改造成多租户系统。

## 目标

1. 自动化 A/B 线正常订单的下单至交付流程，同时保留终审方案、车辆最终分配和交付证据验收三个明确的人工决策节点。
2. 自动完成账单生成、客户主动付款、授权代扣、支付回调处理和应收核销。
3. 提供持久化流程执行能力，支持幂等、重试、超时、人工接管和端到端审计。
4. 通过明确的变更单支持履约期内换车、车型包多车型、提前结束、协议延长和权益加购。
5. 增加客户账户级积分，以及可购买的里程、补能和换车权益。
6. 保持单运营主体架构，同时为未来资产公司 SaaS 入口建立清晰的资产归属边界。
7. 通过资产运营工单记录车辆从采购到处置的全过程，归集实际成本，并将相关事实纳入单车、车辆池和资产所有方运营财务指标。
8. 建立统一对外付款底座，覆盖融资偿付、租金收入分配、资产工单费用和人工确认的客户退款。
9. 将现有 ROE 明确为“单车直接经营试算 ROE”，采用权责发生制经营收益和期间加权权益资本，另行展示收付实现制现金流。

## 非目标

- 总账入账、会计凭证、税务核算或自动化财务关账。
- 自动批准或自动执行客户退款。
- 六个月范围内的完整多租户系统或资产公司用户门户。
- 允许资产公司控制平台产品、客户订单、车辆分配或履约流程。
- 通用 OA、动态 SOA 审批引擎、多级会签、审批代理或按金额动态路由。
- 全成本管理 ROE，以及营销获客、人力和公司管理费用向车辆的分摊。待营销成本、客资归因和转化率数据稳定进入系统后再单独设计。
- 银行流水全量导入、银行账户级完整对账、银企直连或系统自动付款。后期固定付款账户和流程稳定后，通过银行 API 接入同一付款事实模型。
- 基于单车实际成本的净利润分润。六个月范围内只支持以实际收到并核销的租金为基础的租金收入分配。
- 自动里程 OCR、车联网数据接入或补能合作商 API 接入。
- 微信支付以外的支付渠道。内部支付边界仍需保持渠道无关，以便未来扩展其他渠道。

## 架构决策

采用在现有应用和数据库内建设“轻量流程编排内核”的方案。

直接在现有服务之间追加链式调用，虽然初期更快，但会使跨领域重试、幂等和人工恢复更加困难。现在直接拆分为多租户微服务，则会带来超过六个月目标所能承受的交付风险。

流程编排内核只决定“下一步执行什么”，不直接拥有或修改领域事实。订单、合同、应收、支付、交付、车辆、Lease、权益和通知仍由各自领域服务负责。

编排内核包括：

- 每个业务旅程对应一个持久化流程实例；
- 具有等待、就绪、执行中、完成、失败和取消状态的流程步骤；
- 对应三个已批准人工决策节点的人工任务；
- 不可变业务事件；
- 使用稳定幂等键的持久化执行任务；
- 具有负责人、处理时限和恢复动作的异常记录；
- 事务事件表，确保所属领域事务提交后才发布后续任务。

## 下单至交付流程

A 线和 B 线申请在各自完成进件数据收集后，汇合到同一套订阅流程。

正常流程如下：

1. 接收 A/B 线申请并归集材料。
2. 执行确定性的完整性和业务规则校验。
3. 创建“终审方案审批”人工任务。
4. 通知客户并等待客户确认最终方案。
5. 创建“车辆最终分配”人工任务。
6. 自动创建报价、订单、合同和 Stage 1 签约任务。
7. 等待可信签约回调并完成已签文件归档。
8. 自动创建首期应收及付款、代扣授权流程。
9. 处理支付回调并核销应收。
10. 自动创建交付工单。
11. 创建“交付证据验收”人工任务。
12. 完成 Stage 2 签约及已签文件归档。
13. 通过一个权威激活动作同步激活订单、当前车辆和 Lease。
14. 启动周期账单、授权代扣、权益和通知计划。

客户确认、客户签约、客户付款和客户交车动作属于持久化等待状态，是外部业务动作，不属于运营人工审批节点。提醒和超时任务应围绕这些等待状态运行，不长期占用进程或请求。

流程可以在明确边界上取消或执行补偿。已经形成的法律、支付和审计事实不得删除或回滚。

## 激活与资金事实

应收账单、支付交易和支付核销是证明必需款项已经收到的唯一权威事实。

交付准备不得再使用运营人员勾选“保证金已收”或“首月租金已收”作为判断依据。激活动作必须校验真实账单和核销结果，然后同步完成：

- 订阅订单状态变为 `ACTIVE`；
- 已分配车辆状态变为 `LEASED`；
- Lease 状态变为 `ACTIVE`；
- 流程步骤变为已完成。

该动作必须在所属领域事务中完成全部可变激活事实，否则保留为可安全重试状态。订单、车辆和 Lease 状态不一致时，流程不得报告激活成功。

## 周期账单与授权代扣

现有应收账单、支付订单、收款记录和核销记录继续作为资金事实来源。在自动化层增加三个明确概念：

- `BillingSchedule`：决定下一期应收账单的生成时间；
- `PaymentMandate`：记录微信代扣授权、有效状态、撤销状态和所属客户；
- `DebitAttempt`：记录每一次代扣请求、渠道结果、幂等键及后续重试决定。

默认执行节奏如下：

| 时间 | 系统动作 |
| --- | --- |
| 到期前 3 天 | 生成或确认账单，发送账单及代扣预通知 |
| 到期日 | 发起第一次授权代扣 |
| 到期后第 1 天 | 对未支付账单重试代扣 |
| 到期后第 3 天 | 发起最后一次自动重试，并发送关键短信 |
| 到期后第 5 天 | 将账单标记为逾期并创建催收任务 |

客户第一次主动付款时完成后续月度代扣所需的微信授权。客户仍可主动支付未结账单；主动支付完成账单核销后，系统取消尚未执行的代扣任务。

每一笔渠道交易只能入账一次。重复、迟到或乱序回调均返回幂等结果。同一账单可以同时接收主动支付和代扣资金，但总核销金额不得超过应收金额。

代扣失败不得自动暂停订单、车辆或 Lease。超过宽限期后，由运营决定是否限制新增可选权益或启动终止流程。

自动化收款流程只覆盖客户收款和应收核销。会计入账仍由人工处理。退款金额计算、审批和真实退款执行仍为人工动作；人工确认金额后，系统创建退款应付账单并纳入统一付款批次，登记最终外部付款结果并回写客户应收、押金或合同结算记录。

## 通知策略

客户通知渠道为：

- 微信服务号消息作为主要通知渠道；
- Portal 站内消息作为持久化客户记录；
- 短信只用于签约即将失效、连续扣款失败、账单逾期和交付变更等高优先级、强时效事件。

运营人工任务和自动化异常统一进入后台任务与异常工作台。

每条通知都记录对应事件、模板版本、目标地址、渠道、尝试次数、发送结果和关联业务对象。通知失败不得回滚触发通知的领域事务。

## 订阅变更中心

所有履约期变更使用明确的 `SubscriptionChangeOrder`。不得直接覆盖原订单、原合同、价格快照或历史账单。

变更单记录：

- 类型和原因；
- 客户发起或运营发起；
- 生效日期；
- 产品、价格和规则快照；
- 报价及结算试算；
- 积分和现金分配；
- 客户确认；
- 所需补充协议及签约状态；
- 支付状态；
- 执行引用及最终结果。

统一生命周期为：

`DRAFT -> QUOTED -> CUSTOMER_CONFIRMED -> SIGNING_OR_PAYMENT -> SCHEDULED -> EXECUTING -> COMPLETED`

各变更类型可以跳过不适用步骤。取消、失败和人工接管必须是明确状态，不能通过修改已完成历史实现。

### 车型包模型

一个版本化车型包定义：

- 可供分配和切换的车型集合；
- 各车型预计分配用时权重；
- 加权基础订阅价格；
- 免费赠送的换车权益次数；
- 最低履约期；
- 提前结束违约金比例；
- 可购买权益和适用范围；
- 生效时间及稳定产品版本。

基础订阅价格采用加权平均：

`车型参考价格与预计分配用时权重乘积之和 / 权重之和`

签约后的车型包价格在原合同期内保持不变。车型包内正常换车不调整月订阅费，也不按实际使用车型做比例重算。

### 车辆更换

客户主动发起的包内换车流程：

1. 校验车型包适用性和可用换车权益；
2. 预占一次换车权益，但暂不正式扣减；
3. 创建替换车辆最终分配人工任务；
4. 记录旧车交回证据及新车交付证据；
5. 创建交付证据验收人工任务；
6. 新车交付成功后才切换订单当前车辆；
7. 最终完成时正式消耗预占权益。

换车取消或失败时释放预占权益。

因故障、维修、事故或召回产生的运营保障换车，使用相同的车辆及证据流程，但不消耗客户权益。此类换车需单独标记，用于车辆质量和运营成本统计。

客户提出包外车型需求时，系统生成差价报价。客户可以按规则使用积分抵扣，剩余部分形成应收，并在车辆分配前完成支付。

### 提前结束

产品版本保存最低履约期和提前结束违约金比例。

达到最低履约期后，提前结束不收取违约金，只结算已发生费用。未达到最低履约期时：

`违约金 = 剩余合同价值 × 违约金比例`

剩余合同价值只包含提前结束生效日至原合同结束日期间不可取消的固定订阅费。已发生费用单独结算，可取消的权益加购不计入剩余合同价值。

系统生成结算试算、获得客户确认、创建终止补充协议，并在生效时间停止未来账单和权益续发，然后启动退车流程。真实退款由财务人工处理。

### 协议延长

协议延长通过新增连续合同段实现，不修改原合同期限。

默认报价使用提出延期申请时生效的产品版本。授权运营人员可以审批沿用原价或提供续约优惠。客户确认并签署补充协议后，系统延长账单、授权代扣、权益、保险检查和通知计划。延期失败不得改变原合同结束日期。

## 权益与积分模型

首期权益目录如下：

| 权益 | 单位 | 参考价格 | 购买方式 |
| --- | ---: | ---: | --- |
| 里程包 | 1,000 公里 | 800 元 | 单次购买或按月订阅 |
| 补能包 | 100 kWh | 60 元 | 单次购买或按月订阅 |
| 换车权益 | 1 次 | 1,000 元 | 仅单次购买 |

价格属于版本化产品配置，不得作为代码常量写死。

月度套餐包含权益及月度购买权益按账期重置，不结转。单次购买的里程包和补能包有效至当前订阅合同结束。权益批次按照最早到期顺序消费。

单次权益在付款成功后生效。月度周期附加项需要客户确认，并加入后续月度账单。换车权益只在换车最终完成时消耗。

当确认用量超过所有套餐内及已购买权益余额时，超出部分采用线性计费，不向上取整购买新的整包：

- 里程超额价格为 0.8 元/公里；
- 补能超额价格为 0.6 元/kWh。

超额费用进入下一账期调整账单。客户可以使用符合规则的积分抵扣，剩余金额通过主动支付或授权代扣收取。

客户积分采用客户账户级、只追加的流水账。每批积分记录来源、生效时间、到期时间、适用产品、使用范围和可选抵扣上限。积分不是现金，不能提现，也不形成支付交易。业务取消或履约失败时，通过新增冲正流水返还已消费积分。

客户提出特殊需求时，系统计算差价、抵扣符合条件的积分，并为剩余现金金额创建应收。

## 用量凭证与人工录入

在六个月范围内，里程和补能用量均由运营人员人工录入。

里程数据处理：

- 客户上传里程表照片作为原始凭证；
- 运营查看照片后人工录入累计里程数；
- 系统根据上一条已确认累计里程计算当期使用量。

补能数据处理：

- 运营上传或关联合作商月度报表；
- 运营按客户、车辆和账期人工录入确认的 kWh 数。

每条记录保存账期、车辆、客户、操作人、原始凭证和确认时间。已经确认的记录不得覆盖修改；更正必须新增冲正及替代记录，并保存原因和审计轨迹。

缺失读数不得估算。系统发送提醒并创建异常任务。后续收到累计读数或合作商报表后形成确认调整；如果相关账单已经关账，调整进入下一账期，不能改写已经关闭的账期。

## 资产运营工单与成本归集

现有采购价、资本事件、折旧、BaaS 成本、保险理赔、退车损伤、车况报告及客户服务工单继续由原领域负责。这些事实目前分散在不同模块，尚未形成从采购到处置的统一执行和成本轨迹。

新增资产运营领域边界：

- `AssetWorkOrder`：负责执行过程、凭证、派工、验收及运营异常；
- 只追加的 `VehicleCostLedger`：负责归集运营财务成本事实；
- 车辆运营限制：解释车辆为何不能被分配或交付；
- 车辆状态影响 Helper：解释深层状态依赖，但不直接修改状态。

客户提交的事故、救援和客服事项继续保留为 `ServiceCase`。当资产运营需要处理车辆时，由客户工单创建或关联资产运营工单。Fleet Ops 继续作为只读和分析入口，所有新增写操作由资产运营工单领域负责。

### 工单记录与生命周期

资产运营工单记录：

- 工单编号、车辆和资产所有方快照；
- 生命周期阶段和工单类型；
- 来源类型及来源记录编号；
- 可选的订单和客户引用；
- 优先级、安全风险及是否需要限制车辆；
- 负责人、计划时间、实际开始、完成、验收和关闭时间；
- 问题描述、处理方案、供应商、原始文件和完工证据；
- 当前状态、关闭原因及只追加的操作历史。

固定状态机为：

`待处理 → 处理中 → 待验收 → 待成本确认 → 已关闭`

取消必须是明确状态。无成本工单可以在验收后直接关闭。工单关闭后，执行历史不可修改；后续付款、追回和成本更正使用关联台账记录，不重新打开执行历史。

工单来源包括：

- 资产运营人员主动创建；
- 客户 `ServiceCase`；
- 退车损伤、车况报告或保险理赔；
- 异常周期成本；
- Fleet Ops 检测到的运营、资料、可用性或成本异常；
- 采购入库或资产处置。

同一个来源事件最多创建一张起始工单。即使工单已经关闭，重复触发仍返回原工单。后续确有新的处理事项时，必须使用新的来源事件，并作为后续工单关联原工单。

### 全生命周期覆盖

| 阶段 | 主要工单 | 完成条件 | 运营财务结果 |
| --- | --- | --- | --- |
| 采购入库 | 采购交接、运输、入库检测、上牌、首次保险、首次整备 | 车辆资料、检测、资产归属及投入成本确认完成 | 采购价和经确认资本化费用进入资产投入基数 |
| 待租准备 | 清洁、美容、维修、调拨、仓储、资料补全、保险续保 | 所有安全和交付限制解除 | 实际费用进入期间运营成本 |
| 用车中 | 保养、维修、故障、事故、救援、保险理赔、违章、拖车、调拨、停运、保障换车 | 处理结果验收、车辆状态明确、成本及责任方确认 | 成本、追回责任和停运天数进入运营分析 |
| 退车整备 | 退车损伤、清洁、轮胎、电池检查、维修、重新检测、重新上架 | 损伤、责任、维修、车况报告及可用性确认完成 | 修复成本与客户或保险承担分别归集 |
| 资产处置 | 处置检测、估值、方案、下架、销售或拍卖、佣金、过户、物流 | GM 确认、所有权转移、车辆退出运营池、成本和收入证据完整 | 形成处置收入、处置成本和处置净收益 |

用车中车辆遵循以下规则：

- 客户事故、救援或故障工单可以派生资产运营工单，并保持双向引用；
- 安全或交付风险创建车辆运营限制，阻止新的车辆分配或交付；
- 车辆维修期间订阅订单可以保持生效，车辆停运和保障换车分别记录；
- 完成保障换车后，原车工单继续跟踪维修、成本及恢复可用，不得提前关闭；
- 保险理赔、客户损伤应收、供应商质保或其他追回均关联原资产工单；
- 技术验收、成本确认和现金收付是相互独立的业务事实。

车辆进入处置流程后立即从可分配池排除。资产运营提交估值和销售方案，由 GM 进行一次特别确认。处置成交款属于资产退出现金流，不属于订阅经营收入。完成所有权转移后，车辆才能进入最终退出状态。

### 哪些成本必须走工单

执行型和异常型成本必须走工单，包括采购办理、运输、整备、保养、维修、救援、调拨、退车整备、车辆异状和资产处置。

正常合同成本或周期成本，例如保险保费、BaaS 月租、融资利息和已确认折旧，继续由现有领域产生并直接进入成本台账。当发生逾期、金额不匹配、合同缺失或其他异常时，可以派生资产运营工单。

该边界既保证全生命周期成本归集，也避免创建没有实际执行或验收价值的形式工单。

### 成本运营分类

每条成本事实具有一种运营分类：

- **资产投入成本**：采购价及经确认计入资产投入基数的采购相关费用，不直接扣减当期经营收益；
- **期间运营成本**：保养、维修、救援、调拨、清洁、仓储等费用，进入发生账期；
- **处置成本**：检测、佣金、过户和物流等费用，参与计算处置净收益；
- **追回及补偿**：客户、保险公司、供应商、资产公司或其他第三方对原成本的承担金额。

最终会计资本化仍由财务人工决定。系统保存运营分类和后续财务确认分类，但不生成会计凭证。

### 成本台账与运营指标

预计金额只用于执行方案，不进入核心指标。完成单级成本确认后，生成不可变 `VehicleCostLedger` 流水，记录：

- 车辆、资产所有方快照、生命周期阶段及成本类别；
- 来源类型、来源记录及工单编号；
- 成本发生日期和归属账期；
- 已确认实际成本；
- 客户、保险公司、供应商、资产公司、平台或第三方承担金额；
- 已确认可追回金额及实际追回金额；
- 可选的订单、供应商、发票、付款和凭证引用；
- 确认人、确认时间及冲正关系。

核心计算：

- `经营净成本 = 已确认实际成本 - 已成立承担金额`
- `现金净流出 = 实际付款 - 实际追回款`

平台投入权益资本的车辆使用经营净成本计算单车直接经营试算 ROE；车辆池和资产所有方可以聚合展示收入、成本、现金流及经营贡献。平台未投入车辆权益资本的外部托管或代运营车辆不强行计算 ROE，改为展示平台留存收入、单车贡献收益和租金分配率。现金流分析使用现金净流出，已成立但尚未收回的承担金额单独展示为待追回敞口。

维修准备金和其他估算运营成本退出主要 ROE 口径，只能作为非主要计划参考展示。已确认折旧和按权责期间确认的融资利息进入经营收益；折旧不进入现金流，融资还本只进入现金流和资本余额。

客户损伤账单、保险赔付、供应商退款和周期成本均使用稳定来源键，避免同一经济事实重复归集。已经确认的台账流水只能通过冲正和替代记录更正。

当现有领域事实映射进入统一成本台账后，指标计算使用规范化台账记录替代原来源金额，不能在原金额基础上再次累加。采购成本、折旧、融资、BaaS、保险、客户损伤和追回来源键都必须进入勾稽校验。

报表按车辆、车辆池、资产所有方、工单类型、生命周期阶段、责任方、供应商和账期聚合。单车直接经营试算 ROE 中的每笔成本都能反查到工单或周期来源、发票、付款和追回凭证。

### 车辆运营限制与状态 Helper

车辆生命周期主状态和当前运营可用性分开表达：

- `Vehicle.status` 继续保存生命周期主状态；
- 一辆车可以同时存在多条 `VehicleOperationalRestriction`；
- 每条限制保存来源工单、原因、严重程度、阻断范围、解除条件和解除证据；
- 任何适用的阻断性限制仍然有效时，车辆不能被分配或交付；
- 验收一张工单只解除属于该工单且满足条件的限制，不能移除其他有效限制。

状态影响 Helper 展示：

- 生命周期主状态、实际可用性和限制原因树；
- 导致每项限制的工单或领域事实；
- 对订单、预占、交付、车型包、车辆池和 ROE 的影响；
- 当前操作完成后的预计结果，以及仍会保留的限制；
- 缺失凭证、所需权限、建议下一步及来源记录入口。

Helper 只负责解释，不产生副作用。后端业务命令必须执行相同阻断规则，前端提示不是安全或一致性边界。

### 轻量成本控制

六个月范围内不建设通用审批工作流或 SOA 引擎。

- 资产运营负责创建、派工、执行和提交工单；
- 具有 `asset_work_order:cost_confirm` 权限的人员对最终实际成本进行一次确认；
- 财务核验凭证并登记实际付款和追回款；
- 资产处置额外要求 GM 确认；
- 不提供按金额动态路由、多级会签、审批代理或可配置流程设计器；
- 已在线下 OA 完成的审批可以记录审批来源、编号和附件，但本期不实现 OA 集成。

创建人、执行人、验收人、成本确认人和付款登记人保留为独立的可审计参与者字段。通过现有权限分配职责，无需建设通用组织审批平台。

### 资产运营约束与验收

系统必须保证：

- 实际成本确认前不能进入经营 ROE；
- 真实付款或追回发生前，金额不能进入现金流；
- 实际维修成本和维修准备金不能同时扣减主要经营结果；
- 存在有效阻断性限制的车辆不能变为可分配或可交付；
- 对应工单验收前不能解除车辆限制；
- 有成本工单完成成本确认前不能关闭；
- 处置工单在 GM 确认和所有权转移前不能进入最终退出；
- 来源重复、责任金额不平或金额冲突时，禁止确认并展示修复指引。

必须覆盖的资产运营场景：

1. 采购、运输、入库检测、首次整备及释放到可用库存。
2. 在租车辆故障、停运、保障换车、维修验收及恢复使用。
3. 客户事故工单派生资产工单，并关联保险理赔及客户承担。
4. 退车损伤、维修、客户应收、实际收款及重新上架。
5. 正常周期成本直接进入台账，异常周期成本派生工单。
6. 已确认实际成本进入经营 ROE，真实付款进入现金流，且不重复归集。
7. 保险和供应商追回分别在对应事实发生时影响经营收益和现金流。
8. 多个车辆限制同时存在并分别解除。
9. 处置确认、下架、销售、过户、处置收入、处置成本及最终退出。
10. 重复事件、服务重启、冲正及迟到付款或追回的一致性。

最终验收结果应形成连续的车辆采购至处置时间线，工单、证据、成本、现金和追回之间可以双向追溯，单车直接经营试算 ROE 和现金流能与成本台账逐笔勾稽，车辆可用性可以解释到具体限制和来源工单。

## 单车直接经营试算 ROE

六个月范围内只保留一项 ROE：**单车直接经营试算 ROE**。不增加全成本管理 ROE，也不把营销获客、人力或公司管理费用分摊到车辆。现有后端字段可以暂时保留以避免无价值的数据迁移，但页面、导出和说明必须使用完整名称，防止将其误解为会计 ROE 或全成本回报。

当前代码仍以已收金额作为经营收入，并使用单一权益资本事件值或“采购价减融资分配本金”的静态估算作为分母。本节属于对现有公式的升级要求，而不只是名称调整；新口径上线前，页面必须继续披露现行实收和静态权益假设。

经营收益采用权责发生制：

- 已履约形成的租金及其他经营收入进入所属期间，不以客户付款日期决定收入期间；
- 已确认且由平台最终承担的车辆直接成本进入所属期间，不以实际付款日期决定成本期间；
- 逾期应收使用“账龄比例 + 单项认定”的坏账拨备修正 ROE；账龄比例采用带生效日期的版本化配置，核销冲减拨备，后续追回再转回；
- 坏账拨备修正已确认应收的可回收性，与不进入主 ROE 的维修准备金严格区分；
- 收入按不含增值税金额计算；可抵扣进项税不进入成本，不可抵扣进项税进入成本；
- 购置税进入车辆初始投入及折旧基础，车船税等车辆直接税费进入经营成本，企业所得税不分摊到单车。

资金安排、租金收入分配和现金流分析采用收付实现制。实际收款和实际付款只改变现金流及相应结算状态，不重复确认经营收入或成本。

单车 ROE 分母采用期间加权平均权益资本。每个资本事件按实际生效天数参与计算：

`单车权益资本 = 已资本化车辆投入 + 车辆专属受限资金 - 尚未偿还的车辆融资本金`

车辆取得阶段为达到可运营状态发生的购置税、上牌、运输整备和必要装配等一次性费用进入投入及折旧基础。能够明确归属车辆的融资保证金、履约保证金和其他受限资金只增加资本占用，不进入成本或折旧；退回时减少资本占用，被扣罚且确认无法收回时转为实际成本。客户押金是应退负债，不作为平台权益资本。

ROE 从平台实际形成车辆资本投入之日开始，包含待租、维修、事故停运、整备和调拨期间。报表同时展示出租天数、可运营天数和非运营原因。平台未投入权益资本的外部托管车辆不计算 ROE。

车辆处置回款全额进入现金流，但经营结果只确认：

`处置损益 = 实际处置净收入 - 处置时车辆账面净值`

处置净收入扣除评估、整备、渠道佣金、过户及税费等直接处置成本。所有权转移并解除资本占用后停止日常 ROE，生成包含购置投入、运营收支、融资成本和处置损益的单车全生命周期收益结算。

日常报表使用最新事实动态计算。月末由运营生成带时间戳的运营快照，保留当时的收入、成本、拨备、权益资本和 ROE。迟到成本、补录或冲正可以生成新版本及差异清单，但不覆盖原快照，也不引入会计期间锁定。

## 融资偿付计划

录入融资事件时同步录入本金、利率、期限、还款方式、还款日和必要费用。系统自动生成合同级偿付计划，并在内部拆分每期本金、利息和费用；运营日常只核验每期账单总额，不人工拆分本息。

一份融资合同覆盖多辆车时，融资事件保存各车辆的分配金额或比例并校验合计。合同仍生成一张总偿付账单，系统内部将本金、利息和资本变化分配到车辆。无法完成车辆分配时可以继续付款，但受影响车辆的 ROE 暂不出值并说明缺失原因。

提前还款、展期、利率调整、车辆分配变更或债务重组使用带生效日期的计划版本：

- 已核销账单和历史付款分配不可修改；
- 原计划版本保留，只重新生成生效日之后未支付的计划；
- 提前还款本金、违约金和手续费分别列示；
- 新计划启用前由运营进行一次人工核验，不增加复杂审批。

利息按权责期间进入单车直接经营成本。偿还本金不进入经营成本，只进入实际现金流和融资余额。本金余额减少以银行实际扣款日生效；运营 T+1 完成付款登记后，系统回溯更新对应日期的未偿本金和期间加权权益资本。

## 统一对外付款底座

融资偿付、租金收入分配、资产工单费用和人工确认的客户退款分别生成来源业务账单，共用以下付款链路：

`业务账单 → 每日付款批次 → 财务线下付款 → 运营登记付款结果 → 业务核销`

系统每天汇总所有符合轻量条件的项目供运营核验和提交，包括当日到期、以前到期但未付或部分支付、已解除挂起及运营明确加入的提前付款。第一期不把发票、完整合同附件、预算或多级审批作为硬性准入条件；缺失材料只做提示。最低校验为账单有效、剩余金额大于零、收款方及付款用途存在且提交金额合法。

职责边界为：

- 业务模块或运营生成应付账单；
- 运营核验账单并编制每日付款批次；
- 财务可以接收或退回批次并说明原因，但不能修改业务金额或收款方；
- 财务在线下完成真实付款；
- 运营 T+1 根据银行流水登记实际付款并完成账单关联；
- 不增加额外审批人，关键动作保存操作人、时间和状态历史。

一笔实际付款可以结清多张账单，但只有能够完整结清的账单才完成核销。单张账单不足额支付时，账单及已付金额进入挂起状态；后续付款累计达到整单金额后再确认。整单确认后，系统按照融资计划本息构成和合同清偿顺序，自动把各次挂起付款回溯分配到实际银行扣款日，运营不参与本息拆分。

付款金额大于所选完整账单时，剩余金额进入该收款方的待分配付款余额，不自动冲抵未来账单。后续由运营指定使用；误付、退回或长期无法分配的金额使用退款或冲正记录处理。已核销付款不能直接修改，只能撤销、冲正并重新分配。

一期不导入完整银行流水。运营直接在原付款批次中登记实际付款账户、收款方、扣款日、金额、流水参考号和关联账单；每日批次只需上传一份银行流水或付款回单作为依据，不要求逐账单上传。现金流报表明确标注只覆盖系统内已登记付款，不代表银行账户完整流水，也不能发现计划外支出。

后期流程稳定并固定付款账户后，通过银行 API 向同一个付款事实模型写入数据，自动完成防重、付款结果获取和候选账单匹配。银行 API 替换人工登记入口，不重建账单、挂起、核销、融资余额或 ROE 逻辑。

统一待办中心提示到期未提交、历史未付、财务退回、超过 T+1 未登记、挂起账单、待分配余额及融资逾期风险。一期只使用系统内待办、角标和每日汇总清单，不接外部通知渠道。

## 租金收入分配

第一期只支持基于租金实收的收入分配，不支持确认单车成本后的净利润分润。二者必须使用不同规则类型、结算单和报表名称，不能把租金收入分配描述为利润分润。

系统以已经实际收到并完成应收核销的租金为分配基础，排除押金、未收应收和非租金项目。每辆车先按适用规则计算分配明细，同一资产方、同一结算周期的车辆明细汇总为一张分配结算单。运营核验车辆级明细，付款时只提交资产方应付总额；整张结算单进入统一付款批次，付款核销后保留总额与车辆明细的勾稽关系。

退款、冲正或收款核销调整形成下一期调整项，不回改已经完成的历史付款。只有在单车成本台账达到足够及时性和准确性后，才单独设计扣除成本后的净利润分润。

## 资产所有方边界

未来六个月系统继续保持一个运营主体和一个后台权限域，不增加租户感知路由或通用租户隔离。

系统引入：

- `AssetOwner`：代表平台或外部资产公司；
- `VehicleOwnershipPeriod`：保存具有时间范围的车辆归属历史；
- 订单正式分配车辆时固化资产所有方快照；
- 可归属的资金及运营事实同步保存资产所有方快照；
- 按资产所有方归集购置、保险、维修、折旧、残值、融资、收入及结算分析。

资产归属快照用于避免车辆未来变更所有方后，历史合同经济数据被重新归属。

客户收款仍统一进入平台支付体系。系统生成资产公司租金收入分配试算和结算单，并纳入统一付款底座；会计核算、开票及真实付款仍由人工处理，系统登记付款结果并完成业务核销。

未来资产公司 SaaS 入口初期只提供：

- 其名下车辆清单及状态；
- 隐私最小化后的订单和合同摘要；
- 收入、成本、利用率及残值分析；
- 月度结算单查看、下载和确认；
- 保险、车辆证件及结算材料上传。

资产公司用户不能修改平台产品、客户、订单、车辆分配或履约流程。主体级数据隔离和资产公司用户体系在真正交付该门户时建设，不属于当前自动化项目范围。

## 失败处理与运营恢复

系统错误采用有上限的退避重试。业务拒绝、源数据缺失、规则冲突以及重试耗尽后，创建由运营负责的异常任务，不允许无限循环。

异常工作台展示：

- 被阻塞的流程及步骤；
- 客户、订单、账单、车辆和变更单引用；
- 历史尝试及完整错误信息；
- 建议处理动作及所需权限；
- 负责人、处理时限及升级状态；
- 具有审计记录的恢复、取消、补偿或人工完成动作。

跨领域流程使用明确补偿动作，例如释放车辆预占、取消尚未执行的支付订单或返还预占权益。合同、支付事实、核销、积分和权益流水等不可变记录，只能通过后继记录或冲正记录更正。

## 安全与审计

- 客户动作必须校验客户数据归属。
- 运营动作沿用现有权限模型。
- 所有人工审批、越权操作、流程恢复、用量人工录入、积分调整、人工收款及退款记录均进入审计日志。
- 资产公司摘要只暴露资产关系所必需的客户数据。
- 支付渠道凭证、代扣授权、回调和已签文件继续作为服务端受保护资源。

## 验收标准

运营目标为：

- 至少 95% 的正常订单，除终审方案、车辆最终分配和交付证据验收外，不需要其他运营人工介入；
- 计划账单按时生成；
- 自动化失败在 5 分钟内进入异常工作台；
- 重复请求和重复回调不得产生重复订单、账单、支付核销、积分或权益；
- 每笔订阅均可从申请追溯到订单、合同、支付、交付、通知、周期运营及退车；
- 每笔系统管理的对外付款均可从来源账单追溯到付款批次、人工登记的实际付款、挂起或待分配金额及最终核销；
- 单车直接经营试算 ROE 可以追溯到权责收入、坏账拨备、已确认实际成本、融资偿付事件和期间加权权益资本；
- 服务重启、重复回调、乱序回调和渠道超时后，流程能够恢复或进入责任明确的人工异常任务。

必须覆盖的系统级场景：

1. A 线和 B 线正常下单至激活流程。
2. 签约超时、拒签、重复回调及已签文件归档恢复。
3. 主动支付、授权代扣、失败重试、转逾期及后续主动补缴。
4. 客户包内换车、运营保障换车及包外积分与现金结算。
5. 最低履约期前和达到最低履约期后的提前结束。
6. 按当前价格延期，以及经审批沿用原价或优惠价延期。
7. 单次权益及周期权益加购。
8. 里程和补能人工录入、更正、数据缺失及迟到调整。
9. Stage 2 证据、签约、归档恢复、激活、退车、保证金结算及车辆重新入池。
10. Worker 或 API 重启后的流程恢复。
11. 融资合同自动生成本息计划、多车分配、计划版本变更、每日提交、整单核销和部分付款挂起。
12. 一笔实际付款结清多张账单、待分配付款余额、退款或冲正及 T+1 付款结果登记。
13. 车辆级租金收入分配、资产方级结算付款及后续期间调整。
14. 权责经营收益与收付现金流分离、坏账拨备、资本事件日加权和月度运营快照版本差异。

每次数据库发布必须同时验证全新数据库和存量数据库升级。已经提交或执行过的迁移文件不得修改；后续更正必须使用新的增量迁移。
