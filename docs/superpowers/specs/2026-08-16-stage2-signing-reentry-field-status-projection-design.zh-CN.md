# Stage 2 签署重进与 Field 状态投影设计

日期：2026-08-16
状态：已批准
适用范围：Stage 2 车辆交付交接单、客户 Portal、Field 交接任务列表

## 1. 背景

Golden Path 在 Staging 镜像 `Staging-20260816-7f9e823` 上已经验证：

- Stage 2 交接单 PDF 可以正常生成；
- Field 可以正常发起法大大签署；
- 客户可以从 Portal 首次进入法大大签署页面。

人工验收发现两个后续阻断：

1. 客户未签署时通过左滑等方式退出法大大页面，返回 Portal 后不能再次进入仍然有效的签署流程。
2. Field 交接任务列表把资料工单的“客户已确认”当作总流程状态，导致待发起签署、签署中以及已归档任务均显示为“客户已确认”；已归档任务也未进入已完成页签。

## 2. 线上调查证据

对本次验收记录进行只读核对：

- 订单：`ORD20260814085019DMGZ`；
- Field 工单：`034dbf32-b1e4-48fb-9e9e-bda4c9f658b0`；
- 工单状态：`CUSTOMER_CONFIRMED`；
- 交接单状态：`PENDING_CUSTOMER_SIGNATURE`；
- 电子签任务状态：`WAITING_CUSTOMER`；
- 客户签署人状态：`SIGNING`；
- 平台签署人状态：`PENDING`。

对同一客户签署事务进行法大大只读状态查询，脱敏后的响应事实为：

```text
result = 9999
result_desc = 待签署
message = success
```

当前适配器没有将该明确响应识别为“签署中”，而是返回 `UNKNOWN`。Portal 的重新签署入口要求供应商状态必须为 `SIGNING` 或签署记录尚不存在，因此第二次点击被关闭式阻断。

同时，Staging 已存在多条满足以下组合的历史记录：

```text
VehicleHandoverWorkOrder.status = CUSTOMER_CONFIRMED
VehicleDeliveryHandover.status = ARCHIVED
VehicleDeliveryHandover.archiveStatus = ARCHIVED
ContractESignTask.taskStatus = COMPLETED
客户与平台签署人状态 = SIGNED
```

Field 列表目前只使用 `VehicleHandoverWorkOrder.status` 生成卡片标签和页签分组，因此这些已完成记录仍显示为“客户已确认”。

## 3. 根因

### 3.1 Portal 签署入口

当前重新进入流程会先查询供应商状态。法大大查询接口以 `9999 / 待签署`表达已存在但尚未完成的签署事务；适配器只识别 `3000`、`3001`、`3002`、`3003`及 `sign_status` 字段，未覆盖该生产响应形态。

法大大签署页面地址本身由系统根据当前时间重新签名生成，不需要创建新的合同或新的签署事务。因此，未签署期间重新生成同一签署事务的有效页面地址是正确的恢复行为。

### 3.2 Field 状态标签

系统存在两个职责不同的状态机：

- `VehicleHandoverWorkOrder.status`：现场资料采集、客户资料复核和运营资料处理；
- `VehicleDeliveryHandover.status`、电子签任务及归档状态：Stage 2 法律文件的生成、签署、盖章和归档。

Field 列表直接将第一个状态机当作整个交接流程状态，导致电子签开始后仍停留在“客户已确认”。问题属于读取投影错误，而不是历史数据缺失。

## 4. 设计目标

1. 客户只要尚未完成签署且法大大任务仍有效，就可以反复重新进入签署页面。
2. Field 卡片主状态准确表达当前 Stage 2 总流程，而不是只表达资料确认阶段。
3. 完成交接单归档后立即进入 Field 已完成页签，不等待 Admin 最终交付确认。
4. 两次签署入口生成之间强制间隔 60 秒，避免网络延迟期间引导客户反复进入签署页面。
5. 保持现有资料工单、电子签和交付确认流程不变。
6. 不新增数据库字段，不回填历史状态，不泄露供应商或签署敏感信息。

## 5. 非目标

本轮不处理：

- 合同、支付、账单或 Journey 流程调整；
- Admin 最终交付确认口径；
- Stage 2 电子签任务重建或换单；
- 法大大实名认证流程；
- 数据库历史记录状态回填；
- Field 资料采集页面重构。

## 6. 状态权威与聚合边界

### 6.1 权威事实

`VehicleHandoverWorkOrder.status` 继续表示现场资料流程。不得为了修正列表显示而同步改写其历史值。

Stage 2 签署流程以以下事实为准：

- `VehicleDeliveryHandover.status`；
- `VehicleDeliveryHandover.archiveStatus`；
- 当前 `ContractESignTask.taskStatus`；
- 客户和平台两个签署人的状态；
- 交接单归档时间和归档结果。

### 6.2 服务端投影

Field 列表接口由服务端生成统一、安全的展示投影：

```ts
type FieldHandoverDisplayStatus =
  | "HANDOVER_PDF_GENERATING"
  | "ESIGN_INITIATION_PENDING"
  | "CUSTOMER_SIGNATURE_PENDING"
  | "PLATFORM_SEAL_PENDING"
  | "ARCHIVE_PENDING"
  | "ARCHIVE_FAILED"
  | "COMPLETED"
  | "CANCELLED"
  | "VOIDED"
  | "FAILED"
  | "INCONSISTENT"
  | "FIELD_WORK_PENDING"
  | "CUSTOMER_REVIEW_PENDING";

interface FieldHandoverWorkflowProjection {
  displayStatus: FieldHandoverDisplayStatus;
  displayStatusLabel: string;
  taskGroup: "ACTIVE" | "ENDED";
  completedAt: string | null;
}
```

Web 端只消费投影，不复制状态组合规则。原始供应商状态、供应商账号、签署地址和内部错误不得出现在 Field 列表响应中。

## 7. Portal 签署重进

### 7.1 入口展示

- 客户签署人本地状态为 `PENDING`：按钮显示“去签署”。
- 客户签署人本地状态为 `SIGNING`：按钮显示“继续签署”。
- 客户已经签署：关闭签署入口，显示“客户已签署”或“平台盖章处理中”。
- 任务取消、失败、过期或绑定失效：关闭入口，显示稳定的可恢复提示。
- 上一次签署入口生成后不足 60 秒：保留按钮但禁用，显示“请等待 XX 秒后重新进入”。

### 7.2 点击行为

每次点击由后端执行：

1. 校验当前客户拥有该交接单；
2. 校验工单、交接单、合同、电子签任务及签署人绑定；
3. 查询法大大当前签署状态；
4. 若为已签署，按现有对账逻辑推进客户已签状态；
5. 若为明确待签状态，重新生成同一事务的时效签署页面地址；
6. 返回经过域名白名单校验的跳转地址。

前端在请求期间禁用按钮，避免重复点击。签署地址不写入浏览器持久存储，也不在数据库长期保存；数据库仅保留有效期等非敏感元数据。

### 7.3 重新进入冷却时间

首次点击“去签署”不受冷却限制。每次后端成功生成签署入口后，以数据库时间记录本次入口生成时间，并开始 60 秒冷却。

冷却时间由服务端强制执行，Portal 同步显示倒计时：

- 状态接口返回安全的 `reentryAvailableAt` 和 `reentryRemainingSeconds`；
- Portal 根据服务端时间基准显示剩余秒数；
- 倒计时结束后按钮自动恢复，无须重新登录；
- 刷新页面、切换浏览器或重复请求不能绕过冷却；
- 服务端拒绝冷却期内的入口生成请求，并返回稳定错误码 `STAGE2_PORTAL_SIGNING_REENTRY_COOLDOWN`、剩余秒数和可重试时间。

冷却时间写入签署人现有的 `snapshot` JSON 内部元数据，不新增数据库字段。不得复用 `lastAttemptAt`：该字段已经记录法大大任务创建及后台恢复尝试，复用会把刚创建的任务误判为客户已经进入过签署页，并污染自动恢复语义。

内部元数据使用独立命名空间 `portalSigningEntry`，只保存 `claimToken`、`claimUntil` 和 `lastIssuedAt`。服务端先用数据库时间和乐观并发条件取得一次短期入口生成权；并发请求只能有一个进入供应商地址生成。生成成功后写入 `lastIssuedAt` 并清除生成权，生成失败则清除生成权且不写入冷却时间。所有比较以数据库时间为准，避免多实例服务器时钟偏差。

只有成功生成签署入口才启动冷却。生成入口前即失败的请求不启动冷却；如果服务端已经生成入口但客户端因网络中断未收到响应，冷却仍然生效，以防止重复生成。客户已签署回调、供应商状态同步、平台盖章和归档不受该冷却限制。

### 7.4 法大大状态映射

新增精确映射：

```text
result = 9999 AND result_desc = 待签署
  => SIGNING
```

该映射只接受已确认的完整组合，不把任意 `9999` 或任意 `UNKNOWN`放宽为可签署。其他未知响应继续关闭式失败。

如果供应商查询响应不回显请求中的合同、客户和事务编号，不使用缺失字段伪造身份匹配；身份安全仍由本地强绑定校验、经法大大签名的精确查询请求以及明确结果组合共同保证。任何冲突的回显字段仍必须拒绝。

### 7.5 错误表现

Portal 使用稳定错误码区分：

- 签署任务尚未就绪；
- 签署任务已失效；
- 重新进入仍处于 60 秒冷却期；
- 法大大状态暂时不可确认；
- 签署页面地址暂时无法生成；
- 当前客户无权访问。

不向 Portal 暴露法大大原始响应、客户供应商编号、事务编号或内部异常堆栈。

## 8. Field 状态投影

### 8.1 正常状态映射

| 权威事实 | 展示状态 | 中文标签 | 页签 |
| --- | --- | --- | --- |
| 现场尚未提交或客户尚未完成资料复核 | `FIELD_WORK_PENDING` / `CUSTOMER_REVIEW_PENDING` | 沿用当前现场或复核标签 | 进行中 |
| 客户已确认，交接单源文件尚未生成 | `HANDOVER_PDF_GENERATING` | 交接单生成中 | 进行中 |
| 源文件已生成，但尚无有效电子签任务 | `ESIGN_INITIATION_PENDING` | 待发起签署 | 进行中 |
| `PENDING_CUSTOMER_SIGNATURE` | `CUSTOMER_SIGNATURE_PENDING` | 待客户签署 | 进行中 |
| `PENDING_PLATFORM_SEAL` | `PLATFORM_SEAL_PENDING` | 平台盖章中 | 进行中 |
| `SIGNED` 且尚未归档 | `ARCHIVE_PENDING` | 签署完成，归档中 | 进行中 |
| 已签署但归档失败 | `ARCHIVE_FAILED` | 归档异常 | 进行中 |
| `ARCHIVED` 且归档事实完整 | `COMPLETED` | 已完成 | 已完成 |
| 已取消、作废或不可恢复失败 | 对应终态 | 已取消／已作废／处理失败 | 已完成 |

“客户已确认”可以作为资料流程事实存在，但电子签阶段开始后不得继续作为卡片主状态。资料数量和完整度继续通过现有独立字段显示。

### 8.2 完成口径

Field 的“已完成”以以下事实同时成立为准：

- 客户签署完成；
- 平台盖章完成；
- 交接单签署文件完成归档；
- `VehicleDeliveryHandover.status = ARCHIVED`；
- 归档关联文件和哈希事实完整。

完成归档后立即进入已完成页签，不等待 Admin 最终交付确认。

### 8.3 矛盾状态

如果资料工单、交接单、电子签任务或归档事实互相矛盾，不猜测为已完成，返回：

```text
displayStatus = INCONSISTENT
displayStatusLabel = 状态异常，请联系运营
taskGroup = ACTIVE
```

服务端记录脱敏告警，供运营和开发排查。

### 8.4 排序

进行中页签按以下优先级排序：

1. 待现场处理；
2. 待发起签署；
3. 待客户签署；
4. 平台盖章或归档处理中；
5. 异常待处理。

同优先级保持现有时间排序。已完成页签按权威完成时间倒序；归档时间优先，没有归档时间时再使用安全的终态更新时间。

## 9. 历史数据兼容

服务端投影在读取时计算，因此以下历史组合会在发布后自动修正：

```text
workOrder.status = CUSTOMER_CONFIRMED
handover.status = ARCHIVED
archiveStatus = ARCHIVED
```

它将显示“已完成”并进入已完成页签。无需数据库迁移或一次性回填。

## 10. 可观测性与安全

- 签署重进记录脱敏的操作结果、映射后的供应商状态及稳定错误码。
- 不记录或回传完整签署地址。
- 不记录供应商密钥、完整客户编号、手机号或原始响应正文。
- 状态投影矛盾记录实体 ID、内部状态代码和关联完整性结果，不记录客户敏感资料。
- Field 列表继续遵守手机号掩码、VIN 后缀及最小字段原则。

## 11. 测试策略

### 11.1 API

- 使用真实生产响应结构固定样本验证 `9999 / 待签署 -> SIGNING`。
- 不完整或不匹配的 `9999`响应仍为 `UNKNOWN`。
- 首次进入、退出后再次进入、多次重复进入均返回新鲜且安全的签署地址。
- 首次进入不受冷却限制；成功生成入口后 60 秒内服务端拒绝重复生成，并返回准确剩余时间。
- Portal 在冷却期保留“继续签署”按钮、显示倒计时，并在倒计时结束后自动恢复。
- 刷新页面、切换浏览器和并发请求不能绕过冷却限制。
- 入口生成前失败不启动冷却；服务端已生成但客户端未收到响应时冷却仍生效。
- 原地址过期后仍可重新生成入口。
- 已签署时推进对账，不再返回签署地址。
- 取消、失败、过期及绑定不一致时拒绝入口。
- Field 投影覆盖全部正常状态、归档失败和矛盾状态。
- 历史 `CUSTOMER_CONFIRMED + ARCHIVED`组合归入已完成。
- Field DTO 不包含签署地址、供应商账号或原始响应。

### 11.2 Web

- `PENDING`显示“去签署”。
- `SIGNING`显示“继续签署”。
- 请求期间按钮不可重复点击。
- 冷却期间按钮禁用并显示服务端剩余秒数，倒计时结束后自动恢复。
- 返回 Portal 后重新拉取权威状态。
- Field 卡片使用服务端展示状态，不回退到原始工单状态。
- 页签数量、排序和已完成归类正确。

### 11.3 回归验证

- API/Web 聚焦测试；
- lint、类型检查和生产构建；
- Stage 2 PDF 生成、Field 发起签署、客户签署、平台盖章、归档原链路回归；
- Staging 真实法大大“进入—退出—继续签署—完成签署”人工验收。

## 12. 验收标准

1. 客户进入法大大后未签署即退出，返回 Portal 可看到“继续签署”。
2. 成功生成入口后 60 秒内，“继续签署”按钮禁用并显示准确倒计时，服务端拒绝重复请求。
3. 60 秒结束后，客户点击“继续签署”可重新进入同一有效签署事务。
4. 刷新页面、切换浏览器或并发点击不能绕过 60 秒限制。
5. 原页面地址过期后仍能通过 Portal 获取新的有效入口。
6. 客户完成签署后入口关闭，流程推进到平台盖章和归档。
7. Field 待发起签署任务显示“待发起签署”，不显示“客户已确认”。
8. Field 待客户签署、平台盖章、归档中分别显示准确标签。
9. 已归档任务显示“已完成”并进入已完成页签。
10. 现有已归档历史任务无需迁移即可正确显示。
11. 状态矛盾时不误报已完成，页面显示安全异常提示。
12. Portal 和 Field 响应不泄露供应商敏感信息或签署地址。

## 13. 发布与回滚

本轮无需数据库迁移。发布 API 和 Web 后即可生效。

回滚时恢复上一版 API/Web 镜像即可；由于不改数据库状态和结构，不需要数据回滚。
